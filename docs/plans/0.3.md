# `0.3.0` development plan

Status: Phase 0 through Phase 3 complete; Phase 4 not started

Target: the next minor release after `0.2.x`. No calendar date is promised.

## Release outcome

`0.3.0` will turn the first completed production migration into a reusable
adoption baseline. The release should make common structured queries easier to
express, make risky migration residue easier to detect, and strengthen the
library's internal and public-contract safeguards before more applications are
migrated.

The release remains a query-builder release. It will not absorb application
model helpers, an ORM, connection routing, retry policy, or every SQL feature
that can be written through trusted raw SQL.

## Production evidence baseline

One major attendance and payroll application completed a direct migration from
Pixie to SimpleQuery `0.2.0` and is live in production. The source review was
read-only. This plan records only aggregate, non-secret observations; it does
not record the private checkout path, repository name, schema, customer data,
credentials, hostnames, or proprietary SQL.

The migration changed 79 files with 956 additions and 900 removals. That near
one-for-one result is encouraging: most fluent query code survived with
explicit construction, binding, and insert-return changes rather than an
application redesign.

The current production-derived source profile contains:

| Observation | Count or result |
|---|---:|
| Application source files constructing or wrapping SimpleQuery queries | 42 |
| Test and CLI files exercising the integration | 25 |
| `table()` calls | 485 |
| ordinary `where()` call candidates | 587 |
| object `get()` / `first()` terminal candidates | 344 / 123 |
| inner/left join calls | 153 |
| `insertGetId()` / affected-row `insert()` calls | 56 / 15 |
| `update()` / `delete()` calls | 96 / 80 |
| trusted `raw()` expressions | 235 |
| raw projections / raw predicates / raw join conditions | 170 / 30 / 6 |
| direct `pdo()` access / manual transaction-control calls | 13 / 9 |
| managed `transaction()` calls | 0 |
| associative, streaming, and `insertMany()` terminals | 0 |
| union and right-join use | 0 |

Lexical counts identify review candidates, not executed call paths. The
release work must recreate representative shapes with synthetic names and data
before making a contract or performance claim.

### What worked

- The fresh-builder and mutable-clause model mapped cleanly to a large model
  layer.
- Ordered positional bindings replaced interpolated values in trusted
  predicates without a compatibility facade.
- Explicit `insert()` versus `insertGetId()` semantics made affected rows and
  generated IDs visible at call sites.
- MySQL, MariaDB, and SQLite construction could be centralized with explicit
  driver selection and connection labels.
- The consumer needs no SimpleQuery-specific PHPStan suppression at its
  current analysis level.
- Direct PDO remains available for deliberate application-owned escape paths.
- The review found no reported SimpleQuery data-integrity, binding-order, or
  connection-state defect in this production migration.

### Friction and remaining risk

1. Raw expressions remain overused. Of 180 projection calls, 170 use `raw()`,
   including many identifier, wildcard, and alias lists that the structured
   API can represent. Thirty predicates embed the complete comparison in raw
   SQL because a trusted expression cannot currently be used as the left
   operand while keeping the compared value separate.
2. Function-wrapped date predicates and one function-wrapped join survived
   migration and were later replaced in performance work with range predicates
   or indexed identifier joins. New expression ergonomics must not encourage
   non-SARGable query shapes.
3. Ordinary application transactions and a specialized row-lock workflow use
   direct PDO. The lock workflow needs MySQL `FOR UPDATE` behavior and SQLite
   immediate-write behavior in tests; this is evidence for a transaction-mode
   investigation, not permission to weaken transaction ownership.
4. A remaining `insert()` followed by direct `lastInsertId()` shows that the
   migration analyzer does not yet recognize generated-ID use split across
   statements.
5. Lock-conflict inspection is duplicated in application code across raw PDO
   exceptions and SimpleQuery execution exceptions. Portable error
   classification needs evidence before adding a public helper.
6. The application uses full object hydration exclusively, including reporting
   workloads. There is no demonstrated cursor memory incident, but future
   migrations need clearer guidance for streaming and batch operations.
7. A configured read connection does not demonstrate that the library should
   route reads. Connection selection remains an application responsibility.

### What this baseline does not prove

The deployment is strong evidence for a real MySQL application workload. It is
not, by itself, evidence for arbitrary proxy configurations, MariaDB-specific
behavior, unbuffered cursors, associative hydration, generic upsert, unions,
right joins, or transparent retry. Existing direct/proxy fixtures remain the
compatibility authority.

## Priorities and decision rules

Priority order for `0.3.0`:

1. prevent migration ambiguity and unsafe raw/value boundaries;
2. reduce justified raw-predicate pressure with the smallest coherent API;
3. preserve index-friendly SQL and exact binding order;
4. clarify managed transaction adoption versus deliberate PDO ownership;
5. strengthen public-API, architecture, documentation, and benchmark guards;
6. validate a release candidate against a synthetic production-shaped corpus
   before using it in another migration.

A feature enters implementation only when it has a synthetic use case, exact
SQL and binding expectations, failure semantics, all-engine behavior or an
explicit engine boundary, and a maintenance-cost assessment. A trusted raw
query remains the preferred solution for isolated vendor-specific behavior.

## Estimates and complexity

Estimates are engineering time for one maintainer familiar with the codebase.
They include implementation, focused tests, and documentation, but exclude CI
queue time, external review latency, and application deployment observation.

| Complexity | Meaning |
|---|---|
| Low | Local documentation, fixture, or mechanical change; up to 1 day. |
| Medium | One-layer behavior or tooling change; about 1–3 days. |
| High | Public API or multi-layer compiler/executor work; about 3–6 days. |
| Very high | Transaction or cross-engine state work; about 6–10 days. |

| Phase | Estimate | Scope status |
|---|---:|---|
| 0. Baseline and scope freeze | 3–4 days | Complete |
| 1. Adoption evidence and migration tooling | 6–8 days | Complete |
| 2. Structured expression and projection pressure | 10–14 days | Required, API gated |
| 3. Transactions and exception ergonomics | 5–12 days | Complete; managed mode rejected by compatibility evidence |
| 4. Architecture, code quality, and style | 7–12 days | Required; refactors conditional |
| 5. Production-shaped performance work | 5–8 days | Required |
| 6. Documentation and next-consumer readiness | 3–5 days | Required |
| 7. Release certification | 3–5 days | Required |
| **Total** | **42–68 days** | About 9–14 focused weeks for one maintainer |

If the transaction-mode feature is rejected after investigation and no large
internal extraction is justified, the expected path is approximately 42–52
engineering days. Scope additions require a revised estimate before work.

## Phase 2 — Structured expression and projection pressure

Goal: reduce complete raw predicates without creating a general SQL expression
language or weakening the identifier/value boundary.

### Preferred contract to validate

The starting design is to extend existing overloads rather than add a parallel
builder family:

```php
$query->where($db->raw('LOWER(users.email)'), '=', $normalizedEmail);
$query->whereColumn('events.owner_id', '=', 'users.id');
```

The left raw expression remains trusted code. The comparison value remains a
binding. Identifier-to-identifier comparisons remain explicitly structured.
Complete raw predicates continue to use the one-argument `where($raw)` and
`on($raw)` forms. This design is provisional until the ADR and compiler tests
resolve null, expression-binding, and join-right-operand semantics.

- [x] **SQ-0321 — Write the expression-comparison ADR.** Specify overloads,
  trust boundaries, supported operators, null behavior, binding order, join
  behavior, engine portability, and rejected expression-tree alternatives.
  Estimate: 1.5 days. Complexity: High.
- [x] **SQ-0322 — Add an internal expression-comparison predicate.** Represent
  trusted expression-to-bound-value and structured column-to-column comparisons
  without exposing AST types. Estimate: 1.5 days. Complexity: High.
- [x] **SQ-0323 — Extend condition overloads.** Support expression/value
  comparison in `QueryBuilder`, `ConditionGroup`, and `HAVING`, plus explicit
  `whereColumn()` and `orWhereColumn()` forms if the ADR accepts them. Preserve
  fluent `static` return types. Estimate: 2 days. Complexity: High.
- [x] **SQ-0324 — Extend join expression operands only as justified.** Allow a
  trusted expression on one side and a structured identifier or bound value on
  the other without allowing ambiguous string interpretation. Estimate: 1.5
  days. Complexity: High.
- [x] **SQ-0325 — Prove exact binding order.** Cover bindings inside the left
  expression, comparison value, later predicates, nested groups, joins,
  subqueries, raw projections, and `HAVING` for every dialect. Estimate: 1.5
  days. Complexity: High.
- [x] **SQ-0326 — Cover validation and execution.** Test unsupported operators,
  empty SQL, null semantics, keyed binding rejection, non-mutation, clone and
  snapshot behavior, SQLite execution, and direct MariaDB/MySQL behavior.
  Estimate: 2 days. Complexity: High.
- [x] **SQ-0327 — Run a projection ergonomics spike.** Rewrite representative
  raw projection lists with variadic `select()` and `Identifier::as()`. Add a
  small `selectList()`-style API only if the structured rewrite remains
  materially noisy and the new method does not parse SQL-like strings.
  Estimate: 1.5 days. Complexity: Medium.
- [x] **SQ-0328 — Add index-friendly query guidance.** Show range predicates
  for date/time filtering, explain when function-wrapped columns prevent index
  use, and keep vendor functions behind trusted raw expressions. Estimate: 1
  day. Complexity: Medium.
- [x] **SQ-0329 — Update public contracts and static-analysis fixtures.** Cover
  every accepted overload in the API reference and independent PHPStan
  consumer. Estimate: 1 day. Complexity: Medium.

Gate: production-derived raw predicate fixtures become smaller and safer;
structured SQL and bindings are exact; no existing one-argument raw condition
changes meaning; and no accepted API encourages a known non-SARGable rewrite.

Completion evidence: [ADR-019](../adr/019-expression-and-column-comparisons.md)
defines the accepted boundary; the
[projection ergonomics spike](../evidence/0.3-projection-ergonomics-spike.md)
rejects a new list API; compiler tests cover exact SQL and bindings for every
dialect; SQLite integration and disposable MariaDB 11.8/MySQL 8.0 direct and
proxy probes execute the accepted shapes; and the independent level-9 consumer
fixture covers every public overload. The normal, line-coverage, and
branch-coverage gates passed after implementation.

## Phase 3 — Transactions and exception ergonomics

Goal: determine which direct PDO transaction paths can safely become managed
without adopting external work or implying retry safety.

- [x] **SQ-0331 — Classify manual transaction cases.** Separate ordinary
  atomic write groups, MySQL row locks, SQLite immediate-write test behavior,
  schema/migration control, and intentionally external ownership. Estimate: 1
  day. Complexity: Medium.
- [x] **SQ-0332 — Convert ordinary cases in the synthetic corpus.** Demonstrate
  `Connection::transaction()` callbacks, nested savepoints, exception identity,
  active-cursor rejection, and generated-ID timing. Estimate: 1 day.
  Complexity: Medium.
- [x] **SQ-0333 — Probe SQLite immediate transactions.** Record `PDO::inTransaction()`,
  commit/rollback behavior, savepoint ownership guards, busy failures, and
  connection reuse for supported PHP/SQLite combinations. Estimate: 1.5 days.
  Complexity: High.
- [x] **SQ-0334 — Decide transaction-mode scope.** Either reject a new mode and
  document the deliberate PDO-owned escape path, or approve a narrow
  engine-declared transaction mode through a new ADR. Estimate: 1 day.
  Complexity: High.
- [x] **SQ-0335 — Resolve the conditional transaction-mode implementation.**
  SQ-0333/SQ-0334 rejected a managed mode because PHP 8.2/8.3 do not report a
  manual SQLite immediate begin through PDO transaction state. No mode API is
  retained; the escape path remains application-owned. Original conditional
  estimate: 4–6 days. Complexity: Very high.
- [x] **SQ-0336 — Review exception inspection ergonomics.** Test SQLSTATE and
  driver-code access for deadlock, lock timeout, SQLite busy/locked, constraint,
  and transport failures. Add a public classifier only if portable semantics
  are proven; otherwise publish an application-owned recipe. Estimate: 1.5
  days. Complexity: High.

Gate: no API adopts externally started transactions, hides an ambiguous commit,
or labels an operation safe to retry. Conditional transaction work can be
rejected without blocking the rest of `0.3.0`.

Completion evidence: [ADR-020](../adr/020-sqlite-immediate-transaction-mode.md)
rejects a managed SQLite mode after the supported PHP matrix exposed differing
PDO transaction-state tracking.
The [transaction and exception ergonomics record](../evidence/0.3-transaction-and-exception-ergonomics.md)
classifies manual cases and rejects a public retry classifier. The synthetic
adoption corpus covers ordinary conversion, nested savepoints, generated-ID
timing, exception identity, cursor refusal, and application-owned error
inspection. SQLite integration and compatibility transaction probes cover
manual immediate begin/commit/rollback, busy evidence, savepoints, tracking
differences, and reuse. The ordinary transaction matrix remains green across
SQLite, direct MariaDB/MySQL, ProxySQL, and MaxScale.

## Explicit non-goals

Unless new evidence is added and this plan is revised before scope freeze,
`0.3.0` will not add:

- unions or right joins; the production baseline contains no observed use;
- generic upsert, `INSERT IGNORE`, `REPLACE`, or cross-engine DML returning;
- an ORM, schema/migration API, identity map, relationship loader, or model
  base class;
- connection pooling, read/write routing, replica selection, or global
  connection state;
- transparent reconnect, automatic retry, transaction replay, or an assertion
  that a failed write is safe to repeat;
- a public compiler, dialect, AST, middleware, or plugin extension platform;
- named-placeholder support in the structured API;
- arbitrary class hydration or mutable global fetch modes;
- prepared-statement or builder-compilation caches;
- a Pixie compatibility facade or unsafe automatic SQL rewrite.

## Release-level definition of done

`0.3.0` is complete only when:

- all required phase gates pass and conditional rejections are documented;
- every public API change has a demonstrated use case, tests, documentation,
  changelog entry, upgrade note when needed, and ADR when it changes a prior
  decision;
- SQL and bindings remain deterministic and ordered by placeholder occurrence;
- raw SQL remains visibly trusted code and dynamic identifiers remain
  application-allowlisted;
- the current coverage floors remain enforced with focused high-risk tests;
- affected `v0.2.0` comparisons have no unexplained material regression;
- direct engine, proxy, soak, and no-dev checks required by the
  [release process](../maintainers/release-process.md) pass;
- production-derived evidence remains synthetic, redacted, and reproducible;
- published guides describe implemented behavior, while incomplete work stays
  only in this plan.

Scope changes must be made here before implementation and include supporting
evidence, revised estimates, and updated gates. Published tags remain
immutable.
