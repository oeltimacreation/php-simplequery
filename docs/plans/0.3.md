# `0.3.0` development plan

Status: draft for scope validation

Target: the next minor release after `0.2.x`; no calendar date is promised.

## Release intent

`0.3.0` will evolve the query-builder surface only where a concrete consumer
case, portable semantics, and maintenance cost are understood. The release is
not a container for every previously unsupported SQL feature. Correctness,
ordered bindings, explicit connection ownership, and closed internals remain
hard constraints.

This document is the single active plan. Released behavior stays in the user
guides and API reference; completed work is summarized in `CHANGELOG.md` and
supported by ADRs or evidence when needed.

## Scope intake

Before feature implementation, each candidate must provide:

1. a minimal application query that cannot be expressed cleanly with the
   current structured API;
2. expected SQL and binding order for MariaDB, MySQL, and SQLite, or an explicit
   reason the feature must be engine-specific;
3. return, mutation, validation, and failure semantics;
4. a comparison with a small trusted raw query;
5. an estimate of public API, test, documentation, and long-term maintenance
   cost.

The initial candidates for evaluation are composable `UNION` queries and right
joins. They are candidates, not commitments: prior migration evidence found no
meaningful consumer demand, so they enter implementation scope only after a
current use case passes this intake. See the historical
[feature-usage evidence](../evidence/feature-usage-verification.md). New
evidence may replace either candidate.

## Work packages

### 0.3-A — Baseline and scope decision

- run `composer check`, line/branch coverage, SQLite probes, and the maintained
  benchmark suite on the `0.2.0` tag and the `0.3` branch;
- generalize release-comparison metadata that still names `v0.1.0`, then
  establish `v0.2.0` as the tagged reference for affected `0.3` scenarios;
- review public issues and refresh only the synthetic consumer evidence needed
  to validate candidate use cases;
- record accepted features, rejected alternatives, compatibility impact, and
  measurable acceptance criteria;
- add an ADR before implementation when an accepted feature changes a prior
  architectural decision or public lifecycle rule.

Gate: every accepted feature passes the scope intake, has an owner, and has
testable semantics. It is valid for this gate to reject all initial candidates
and return the release to planning rather than manufacture scope.

### 0.3-B — Contract and compiler vertical slices

For each accepted feature:

- define the smallest public API and immutable internal representation;
- implement complete MariaDB, MySQL, and SQLite compilation behavior;
- preserve placeholder/binding occurrence order through nested queries;
- reject invalid, ambiguous, and unsupported shapes before execution;
- verify cloning, snapshotting, cross-connection rejection, and terminal
  non-mutation where composition is involved.

Gate: independent compiler fixtures cover success, validation, binding order,
identifier quoting, nesting, and every documented engine difference.

### 0.3-C — Execution and compatibility evidence

- add SQLite execution tests for portable behavior;
- add direct MariaDB/MySQL tests for engine-sensitive behavior;
- run the supported native/emulated prepare and buffered/unbuffered profiles
  when statement shape or result handling can differ;
- run ProxySQL and MaxScale smokes when the feature affects preparation,
  routing, transactions, cursors, or session state;
- characterize failure behavior without adding reconnect or replay.

Gate: all advertised engine paths pass and no fixture result is generalized
beyond the tested version and configuration.

### 0.3-D — Public contract and documentation

- update the API reference and relevant task guides;
- add a runnable example when a new user benefits from one;
- add an `[Unreleased]` changelog entry for every public change;
- add an upgrade section for every breaking or behavior-sensitive change;
- update static-analysis consumer coverage for new public signatures.

Gate: examples execute, links resolve, released behavior is described in one
canonical location, and plan language has not leaked into reference pages.

### 0.3-E — Hardening and release readiness

- run the complete quality, coverage, direct-engine, proxy, benchmark, soak,
  and clean no-dev consumer checks required by the release process;
- compare affected compiler and execution scenarios with `0.2.0` using the
  same harness and correctness digests;
- investigate any repeated median regression greater than 10% in an affected
  scenario and record an explicit waiver if the tradeoff is accepted;
- review security boundaries, resource cleanup, transaction ownership, and
  redaction before opening `release/0.3.0`.

Gate: all required checks pass, no correctness or resource-safety blocker is
open, and release evidence is attached or linked without secrets.

## Explicit non-goals

Unless a separately approved plan revision supplies new evidence, `0.3.0` will
not add:

- an ORM, schema or migration API, connection pool, routing layer, or global
  connection state;
- transparent reconnect, automatic retry, transaction replay, or ambiguous
  write recovery;
- a public compiler, dialect, middleware, or plugin extension platform;
- generic cross-engine upsert or DML-returning abstractions;
- prepared-statement or builder compilation caches;
- a compatibility facade for Pixie or another framework.

Trusted raw SQL remains the narrow escape hatch for deliberate engine-specific
behavior that does not justify a maintained structured API.

## Change control

Scope changes are made in this document before implementation and must include
the supporting use case and revised gate. Public API changes require tests,
documentation, a changelog entry, and an ADR when they alter an accepted
decision. Release publication follows the
[maintainer release process](../maintainers/release-process.md); tags are
immutable.
