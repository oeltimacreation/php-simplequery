# `0.7.0` development plan

Status: Proposed; Phases 0–6 are pending. Baseline: immutable released
`v0.6.0` (`6a9b22ea827888aac3818d7ea5ddddde01a66f11`).

Target: the next minor release after `0.6.x`. No calendar date is promised.

Audit date: 2026-09-04.

## Release intent

`0.7.0` is an evidence-backed resilience, compatibility-lifecycle, and release-
integrity release. Its purpose is to keep the small public query-builder
contract dependable as upstream runtimes and database fixtures age, make rare
PDO and resource-failure behavior explicit, improve the ability of tests and
repository checks to detect real drift, and ship a deliberately bounded
Composer distribution.

The release starts with a public-contract freeze. No new public query method,
result terminal, driver, extension point, or compatibility claim is accepted
by default. A public addition requires demonstrated consumer demand, exact
cross-engine semantics, a maintenance-cost assessment, tests, documentation,
changelog and upgrade coverage, and an explicit revision of this plan. Trusted
raw SQL remains the narrow escape path for unsupported syntax.

The current architecture is not a rewrite target. The connection, builder,
compiler, executor, cursor, transaction, capability, and observability
boundaries generally enforce the accepted ownership and security contracts.
Work enters `0.7.0` only where the audit identified a concrete lifecycle risk,
an under-specified failure boundary, or a quality gate that can agree with
itself while missing real drift.

## `v0.6.0` baseline and audit method

The audit reviewed public and internal source, adjacent unit/compiler/
integration tests, golden and public-API fixtures, examples, ADRs, support and
security policy, release evidence, Composer metadata, CI workflows, database
probes, benchmarks, and public issue state. It also exercised a clean no-dev
installation and local archive creation. Time-sensitive lifecycle findings use
first-party upstream sources accessed on the audit date.

## What the audit found

### Strengths to preserve

- Structured values remain ordered parameter bindings, while identifiers and
  raw SQL retain explicit trusted-code boundaries.
- Fresh-builder ownership, terminal non-mutation, nested-builder snapshots,
  cross-connection rejection, cursor accounting, transaction ownership, and
  quarantine behavior have broad focused coverage.
- Dialect compilation is deterministic and backed by exact SQL and binding
  fixtures for MariaDB, MySQL, and SQLite.
- Public concrete classes are final, internal compiler and state types remain
  closed implementation details, and no framework coupling has entered the
  package.
- The normal quality gate, coverage floors, static analysis, examples,
  benchmarks, SQLite probes, public-API drift check, and dependency audit are
  healthy.
- Public issue and retained consumer evidence do not currently justify a new
  feature family or broader public API.

## Proposed compatibility transition

Phase 0 must accept or revise this table before implementation. Until the
corresponding live gate passes and documentation is updated, every new entry is
a candidate fixture rather than a supported target.

| Surface | Current contract or fixture | Proposed `0.7.0` action |
| --- | --- | --- |
| PHP | 8.2 floor; CI through current PHP | Keep 8.2–8.5 coverage. Retain the 8.2 package floor, add an upstream-EOL warning, and decide the earliest policy-compliant future floor separately. |
| MariaDB | 11.8.2 minimum / 11.8.8 current | Keep the 11.8.2 floor and qualify 11.8.9 or the then-current 11.8 patch. |
| MySQL | 8.0.11 minimum / 8.0.46 current | Keep 8.0.46 as a legacy compatibility lane, qualify MySQL 8.4 LTS as the maintained current lane, and start—not complete—the policy process for any future 8.0 removal. |
| SQLite | 3.39.2+ runtime floor | Produce reproducible evidence against the actual minimum, not only a version-rejection double and the runner's newer linked SQLite. Keep the floor unless accepted evidence and notice policy justify a change. |
| ProxySQL | 3.0.1 single-backend fixture | Qualify 3.0.10 stable (or a newer reviewed 3.0 stable patch at implementation time), then remove 3.0.1 from active CI while preserving historical evidence. |
| MaxScale | 23.02.17-2 single-backend fixture | Qualify a maintained 25.10 fixture, retain a direct MariaDB control, and retire 23.02 from active certification only after parity is demonstrated. |

Adding MySQL 8.4 to the public support matrix is the only anticipated target
expansion. It remains conditional on Phase 0 acceptance and Phase 1 evidence.
ProxySQL and MaxScale stay configuration-sensitive fixtures rather than SQL
dialects or general topology guarantees.

## Decision rules and release gates

Priority order is correctness and data safety, resource and transaction
ownership, security lifecycle, compatibility evidence, public clarity,
distribution integrity, and then workflow efficiency.

- `tests/Fixtures/Contracts/public-api.json` remains byte-identical by default.
  A PHPDoc-only manifest change still needs consumer static-analysis evidence
  and complete review; a behavioral or signature change additionally requires
  plan revision, documentation, changelog/upgrade notes, and an ADR when the
  accepted architecture changes.
- A database or proxy claim enters current reference documentation only after
  compiler coverage where applicable, live execution and transaction probes,
  a direct-engine control, exact version/configuration capture, and archived
  synthetic evidence all pass.
- `0.7.0` does not remove the PHP 8.2, MySQL 8.0, or SQLite 3.39.2 floors.
  Future removal must honor the project's existing breaking-release and
  12-month notice policy.
- Failure-path work must first classify a state as reachable with supported
  PDO configuration, defensive-only, or synthetic-test-only. A test is added
  for a contract or regression risk, not merely to cover a line.
- Exception messages and evidence must not expose values, credentials, DSNs,
  hostnames, topology, or raw driver diagnostics beyond the accepted
  redaction contract. Cleanup errors must never erase an earlier primary
  operation failure.
- Structured binding order, SQL text, builder mutation rules, nested snapshots,
  cross-connection rejection, terminal reuse, cursor accounting, transaction
  ownership, and the no-hidden-retry rule remain non-negotiable.
- Coverage floors remain 90% overall line, 80% overall branch, 95% compiler
  line, and 90% compiler branch. Path and mutation results guide targeted work;
  neither receives a repository-wide percentage gate until the method is
  stable, affordable, and shown to catch a real defect class.
- Performance comparisons move to immutable `v0.6.0`. Existing correctness
  digests, source-order controls, the greater-than-5% regression review rule,
  the measured noise floor, 256 KiB retained-allocation bound, and flat file-
  descriptor requirement remain in force.
- The release artifact must be built from a clean tree, contain all runtime and
  licensing material, exclude dependencies and generated/development output,
  install without dev dependencies, and reproduce its source commit. Size and
  file-count budgets are set from Phase 0's clean baselines rather than an
  arbitrary target.
- Maintainer automation may be simplified or parallelized only after its
  unique signal and wall time are measured. The PHP matrix, consumer analysis,
  coverage, live database/proxy controls, and release artifact checks may not
  be silently narrowed.

## Phase 2 — Make execution and resource failure semantics explicit

- [ ] Build one data-driven state matrix spanning connection creation/profile
  validation, prepare, bind, execute, fetch, row count, generated ID, statement
  cleanup, cursor exhaustion/early close, transaction control, observer
  delivery, and connection close. Mark each false return and exception as
  reachable, defensive, or impossible under the supported profile.
- [ ] Reconcile non-cursor and cursor `closeCursor()` behavior. Decide and test
  whether false returns and thrown cleanup failures quarantine the connection,
  what remains usable, and how an earlier operation failure retains precedence.
- [ ] Define the cursor observation boundary: statement execution, iteration,
  natural exhaustion, fetch failure, cleanup, and early close must have an
  intentional event count and success/failure meaning without retaining rows
  or allowing observer failure to affect database behavior.
- [ ] Specify `PDO::PARAM_LOB` resource ownership, current-position semantics,
  repeated terminal calls, cloned builders, nested snapshots, closed streams,
  and retry expectations. Test supported drivers before promising reusable or
  one-shot behavior.
- [ ] Recheck connection quarantine, explicit close, destructor cleanup,
  active-cursor accounting, nested transaction/savepoint ownership, and manual
  PDO-state divergence for every newly reachable failure path.
- [ ] Keep exception evidence lazy and redacted. Test chained causes and
  cleanup/observer failures without adding raw SQL values, credentials, DSNs,
  private hostnames, or topology to public diagnostics.
- [ ] Add live SQLite evidence and direct MariaDB/MySQL/proxy probes wherever a
  conclusion depends on real PDO or transport behavior. Controlled PDO seams
  remain appropriate for otherwise unreachable return values.

Gate: every supported terminal has deterministic success, primary-failure,
cleanup-failure, observer, and post-failure connection-state semantics;
resource ownership is documented; no uncertain write is replayed; and normal
successful SQL, results, and performance remain non-regressed.

Expected evidence: `docs/evidence/0.7-phase-2-execution-and-resource-semantics.md`.

## Phase 3 — Improve contract precision and test effectiveness

- [ ] Run a bounded mutation or equivalent fault-injection pilot over binding
  order, compiler write validation, executor cleanup, cursor state,
  transaction ownership, connection-profile validation, and exception
  redaction. Record surviving meaningful faults; do not add a vanity global
  mutation threshold.
- [ ] Cover only reachable or contract-defining gaps exposed by the pilot and
  Phase 2 matrix. Prioritize invalid-input ordering, partial mutation,
  snapshot isolation, cross-connection composition, active-resource teardown,
  and primary-error preservation over extra happy-path permutations.
- [ ] Make compiler golden fixtures self-validating: require stable unique case
  IDs, documented schemas, complete dialect membership where intended, exact
  SQL/binding/type order, and a feature-to-case relationship that cannot pass
  by repeating the same hard-coded list on both sides.
- [ ] Review public PHPDoc callback, list/non-empty-list, scalar, and resource
  shapes against runtime behavior and the no-dev consumer analyser. Treat a
  manifest diff as a reviewed contract change even when native signatures do
  not move.
- [ ] Add deterministic boundary/property tables for identifiers, comparison
  operators, aggregate conversion, multi-row inserts, limits/offsets, and
  nested conditions where they provide more signal than example duplication.
  Keep random fuzzing out of required CI unless failures are reproducible.
- [ ] Align test ownership with repository layout. Either populate the empty
  engine/proxy integration placeholders with real orchestration entry points
  or remove the placeholders and document probes as the single source of live
  behavior.
- [ ] Re-audit control-flow hotspots after accepted changes. Extract a helper
  only when it gives one responsibility an independently testable boundary and
  reduces invariant coupling; retain cohesive compiler and transaction state
  machines otherwise.

Gate: targeted injected faults are killed or explicitly justified, fixtures
prove their own structural relationships, public annotations match tested
runtime behavior, coverage floors hold, and no test relies on production data
or a mocked internal compiler/transaction object.

Expected evidence: `docs/evidence/0.7-phase-3-contract-and-test-effectiveness.md`.

## Phase 4 — Harden distribution and release integrity

- [ ] Define a reviewed distribution manifest. At minimum retain `src/`,
  `composer.json`, `LICENSE`, essential readme/support/security material, and
  any file actually needed by Composer; exclude tests, benchmarks, probes,
  internal plans/evidence, CI configuration, agent guidance, local caches,
  coverage, results, and `vendor/` unless a documented consumer need wins.
- [ ] Implement and test the exclusion mechanism used by each real path:
  Composer's local archive command, VCS/source archives, and Composer/Packagist
  dist installation. Do not assume one exclusion setting governs all three.
- [ ] Build artifacts from clean detached worktrees. Fail when generated or
  ignored output, credentials, private paths, dev dependencies, or unexpected
  executable/configuration files enter the package.
- [ ] Install the built artifact with `--no-dev`, validate optimized autoloading
  and platform requirements, run a compact public-API/compile/SQLite consumer
  smoke, and prove the installed source maps to the recorded commit and
  checksum.
- [ ] Set a justified file-count and byte budget from Phase 0, then require a
  material reduction without deleting licensing, security, support, or needed
  usage guidance. Report package size separately from installed dependencies.
- [ ] Extend release consistency to relate current release metadata, the sole
  active plan, current evidence classification, benchmark baseline, support/
  security series, upgrade guidance, and workflow artifact labels. Historical
  changelog, ADR, and evidence references remain valid and exempt.
- [ ] Replace the monolithic repository existence list with discovered
  structural invariants and schema/content checks where possible. Keep an
  explicit manifest only where membership itself is a reviewed contract.
- [ ] Define build-tool provenance: record the Composer version used for

Gate: clean source, local archive, hosted dist, and installed no-dev views are
understood and tested; the runtime artifact contains no development/generated
material; semantic release drift fails deterministically; and a release can be

## Risk register

| Risk | Mitigation |
| --- | --- |
| Qualifying MySQL 8.4 expands an ongoing support obligation. | Accept it only with a complete parallel matrix, explicit maintenance owner, and evidence that the shared compiler remains semantically correct. |
| Keeping legacy MySQL 8.0 compatibility may be mistaken for upstream security support. | Label it as a tested legacy lane, link upstream EOL guidance, and avoid deployment-security guarantees. |
| Proxy version changes can alter routing behavior independently of SQL compilation. | Use fixed single-backend fixtures, direct controls, exact configuration, and no general proxy/topology claim. |
| Rare cleanup faults are hard to induce with a real exception-mode PDO. | Separate real-driver probes from controlled PDO seams and state which conclusion each can support. |
| Tightening cleanup or observation semantics could break consumers relying on incidental behavior. | Characterize current behavior first; require ADR, changelog, and upgrade notes for an intentional semantic change. |
| Mutation tooling could add slow or fragile dependencies. | Start with a bounded pilot, pin it only if useful, and keep the normal gate independent until stability is demonstrated. |
| Archive exclusions differ between local Composer and hosting providers. | Test each produced artifact directly and gate contents, rather than trusting configuration presence. |
| A larger compatibility matrix can lengthen CI materially. | Measure unique signal, use scheduled/service jobs where appropriate, parallelize independent lanes, and never remove a control solely for speed. |

## Explicit non-goals

Unless this plan is explicitly revised before implementation, `0.7.0` does
not add:

- an ORM, model/relationship layer, schema or migration system, identity map,
  connection pool, router, or framework integration;
- transparent reconnect, automatic retry, failover replay, or hidden replay of
  an uncertain write or commit;
- a new query-builder feature family, result terminal, overload, public
  compiler/AST/dialect/executor/transaction hook, or middleware/plugin API;
- PostgreSQL, SQL Server, Oracle Database, or another SQL dialect;
- removal of the PHP 8.2, MySQL 8.0, MariaDB 11.8.2, or SQLite 3.39.2 floor;
- a universal ProxySQL/MaxScale compatibility or topology guarantee;
- statement or compilation caching, retained binding values, global mutable
  connection state, automatic batch sizing, or automatic transaction policy;
- broad class splitting, framework dependencies, code deletion for a size
  metric, 100% path coverage, or a repository-wide mutation-score target;
- a general performance claim without an isolated workload, direct control,
  correctness gate, and reproducible result outside the noise floor;
- automatic publishing, mutable release tags, secrets, production topology,
  customer data, private source inspection, or user telemetry.

## Release-level definition of done

`0.7.0` is complete only when the support-lifecycle transition is explicit and
backed by reproducible live controls; rare execution, cleanup, cursor,
transaction, observer, and stream-binding ownership paths have intentional
