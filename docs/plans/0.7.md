# `0.7.0` development plan

Status: Accepted scope; implementation in progress. Release certification is
pending. The accepted delivery decisions below supersede audit proposals.

Audit updated: 2026-09-05. Reviewed branch: `feature/0.7-candidate`, commit
`5a24c2b42754e62bcf6ff057a123a348247ccb7d`.

Release baseline: immutable `v0.6.0`
(`6a9b22ea827888aac3818d7ea5ddddde01a66f11`). The reviewed source, tests, and
Composer metadata match that tag. The intervening commit transitions planning
and documentation to `0.7.0`.

Target: the next minor release after `0.6.x`; no calendar date is promised.

## Release intent

Improve the dependability and maintenance cost of the existing query builder.
Prioritize input rejection and failure evidence, make statement and stream
ownership explicit, remove demonstrated duplication, and measure narrowly
selected performance changes. Keep compatibility, packaging, documentation,
and test automation reliable without turning the release into a tooling
expansion project.

The library already has a small runtime dependency surface: PHP 8.2 and PDO,
with no third-party runtime package. Its connection, builder, compiler,
executor, cursor, and transaction boundaries are useful. A comprehensive audit
does not justify replacing them, deleting safety checks, or adding features to
make the release look larger.

The default scope preserves public signatures, supported floors, deterministic
SQL, ordered concrete bindings, fresh builders, terminal non-mutation, nested
snapshots, connection ownership, and the absence of hidden retries. Semantic
fixes still need compatibility review even if the public manifest is unchanged.
Proposed contract decisions below must be settled before dependent source work;
this planning revision does not approve new support claims or breaking changes.

## Reading and evidence rules

The improvement register is the scope index. Detailed workstreams describe the
problem, the narrowest useful change, validation, and reasons to stop. Phases
order that work; they do not create a second independent backlog.

Evidence labels mean:

- **Reproduced:** exercised during this audit, with the environment and limits
  stated below. A controlled PDO failure is not proof of real-driver frequency.
- **Confirmed:** directly visible in source, tests, configuration, or retained
  release evidence. It may be intentional behavior rather than a defect.
- **Candidate:** a plausible improvement requiring profiling, characterization,
  or a public-contract decision. No benefit is claimed yet.
- **Historical:** a prior result retained for context, not rerun or recertified
  by this document.

Priority expresses work order: P0 requires early disposition because it can
alter query meaning or lose failure evidence; P1 is core release work; P2 is a
bounded candidate. Priorities are not security severity ratings. Effort is
relative: S is a local change with focused tests, M crosses a few boundaries,
and L needs multi-engine or release infrastructure. These are not time estimates.

## Workstream A — Input correctness and failure stability

### S1: Reject malformed overloads instead of dropping supplied arguments

[ConditionFactory::rawCondition()](../../src/Internal/Ast/ConditionFactory.php)
returns a raw predicate when `operatorOrValue` is missing without checking
whether `value` was supplied. The following currently compiles to `WHERE 1 = 1`
with no binding for `123`:

```php
$db = CompilerConnection::for(Driver::Sqlite);
$query = $db->table('items')->where(
    subject: $db->raw('1 = 1'),
    value: 123,
)->compile();
```

This is an invalid overload, not an SQL-injection demonstration. Silently
ignoring caller intent is the defect. Prefer a local rejection in the shared
factory; do not introduce a generic argument parser or a new overload.

Acceptance:

- Cover positional, named, unpacked, missing-middle, excess positional, and
  unknown named arguments for `where`, negated/OR variants, condition groups,
  `having`, and join shapes where their signatures allow them.
- Assert exception type, no predicate attachment on rejection, and unchanged
  valid raw/value/column comparison SQL, binding order, and null semantics.
- Keep intentional differences: a bare raw condition is allowed; a join value
  comparison does not adopt the condition factory's null rewrite.
- Record the stricter invalid-input behavior in the changelog and appropriate
  query-builder/upgrade guidance. Review it as a semantic correction.

### S2: Preserve callback evidence through transaction inspection failure

[TransactionManager::requireOwnedPhysicalTransaction()](../../src/Internal/Transaction/TransactionManager.php)
accepts a callback failure, but its call to `physicalTransactionActive()` can
throw a new state exception whose `callbackFailure` is null. Reproduction:
inside a managed callback, enable `ControlledTransactionPdo`'s
`failTransactionInspection`, then throw a synthetic application exception.
The reported rollback state exception marks the connection unusable but loses
the original callback in the structured evidence.

Carry callback context through this specific inspection boundary, or wrap the
inspection failure at the recovery boundary. Preserve the established meaning
of `callbackFailure`, `controlFailure`, `recoveryFailure`, `managedDepth`, and
`operation`; do not collapse all failures into one message or retry the write.

Acceptance covers outer and nested callbacks, inspection failure before any
callback, inspection during successful completion, callback plus inspection
failure, and post-failure execution rejection. Assert identity of the original
callback where promised, the control cause, depth before reset, and no extra
commit/rollback/savepoint command after ownership becomes uncertain. Retain
existing successful rollback behavior: rethrow the application exception itself.

### S3: Make statement cleanup an explicit ownership transition

[Executor::attempt()](../../src/Internal/Executor.php) calls `closeCursor()` on
the success path and again in `finally` for non-cursor operations. Its false
return is ignored. [Cursor::finalize()](../../src/Cursor.php) already handles
false/throwing cleanup, quarantine, idempotence, and cursor accounting.
The existing failure tests establish part of this contract; do not rewrite it
as if no policy existed.

Recommend one cleanup attempt per owned statement, explicit transfer only after
a cursor has been constructed successfully, and conservative quarantine when
cleanup leaves state uncertain. Confirm the false-return and quarantine policy
before implementation because it changes currently observable behavior.
Never move cleanup entirely into a `finally` block that masks a primary error,
emits success too soon, or changes a completed write into an implicit retry.

| State | Required characterization / target |
| --- | --- |
| Prepare failure | No acquired statement; translated error where applicable, correct event count. |
| Bind/execute failure | Cleanup the statement even when a requested cursor was never handed off; original failure stays available. |
| Successful ordinary terminal | Read the result, complete cleanup, then emit one outcome and return. |
| Successful operation, cleanup false/throws | Intentionally report cleanup failure and connection usability; a write may already have occurred. |
| Operation and cleanup both fail | Preserve the primary failure; quarantine according to the accepted policy. |
| Cursor handoff | Register and transfer ownership once; executor must not close a live cursor. |
| Cursor exhaustion/early close | Close/release once; repeated close is harmless. |
| Cursor fetch and cleanup both fail | Preserve fetch failure and still release accounting/quarantine. |
| Destructor | Best effort, no escaping destructor exception; do not rely on destruction for normal cleanup. |

Extend [ConfigurableStatement](../../tests/Unit/ConfigurableStatement.php) with
only the call counts and failure controls needed for these regressions. A
single static `closed` Boolean cannot distinguish one close from two. Separate
real PDO behavior from synthetic returns. Include native/emulated and
buffered/unbuffered direct/proxy probes when changing transport-sensitive
cleanup behavior. Prior measurements rejected cleanup as a standalone speed
optimization; the justification here is simpler, consistent failure handling.

### S4: Treat LOB resources as caller-owned state

[Binding](../../src/Binding.php) accepts any resource for `ParameterType::Lob`;
concrete bindings are reused, and readonly wrappers do not freeze stream
contents or position. This applies to raw queries, writes, cloned builders,
compiled subqueries, and raw expressions holding the same resource.

The live SQLite reproduction used one raw query twice with a stream positioned
inside its payload: the second result was empty because the first consumed the
remaining bytes. Do not generalize that exact behavior to MariaDB/MySQL.

Establish a matrix for open/closed streams, empty streams, current position,
rewind by the caller, repeated execution, shared bindings, seekable and
non-seekable streams, and non-stream resources if available on the test host.
Record whether each PDO driver consumes, converts, or rejects the binding and
which exception reaches the caller. Revalidate execution-time liveness only
if evidence shows that it prevents an otherwise obscure invalid-resource error.

Default design direction: retain caller ownership, avoid automatic rewind,
copying, buffering, or close, and document that snapshot isolation covers query
structure rather than external resource bytes. If a repeatable payload is
needed, the application supplies fresh state or deliberately manages stream
position. Rejecting non-stream resources or changing accepted resource types
needs explicit contract review, PHPDoc, tests, and upgrade guidance. No stream
change may introduce hidden write replay or unbounded memory retention.

### S5/S6: Profile validation and lifetime edges

[ConnectionProfile](../../src/Internal/ConnectionProfile.php) validates the PDO
at construction. Its SQLite busy-timeout check casts the fetched value to int;
a false result becomes zero and can match a declared zero timeout. Test that
case with a controlled statement and classify its reachability under exception
mode. Distinguish a valid driver integer/string zero from failed query/fetch.
Review other profile reads and PRAGMA writes for the same false/exception
confusion, preserving supported scalar shapes.

[Connection::pdo()](../../src/Connection.php) and injected PDO ownership permit
application code to change attributes/session state after validation. Document
which guarantees depend on callers preserving the profile. Do not add a hidden
profile round trip on each terminal. Cover predictable divergence and explicit
close on compiler-only, closed, quarantined, active-cursor, and active-transaction
connections using the existing state matrix.

A closed cursor retains readonly references to its PDO statement, query, and
connection. This is a retention hypothesis, not a demonstrated leak. Measure
retained closed cursors, large binding payloads, early-abandoned generators,
and short-lived connections with collection enabled/disabled. Distinguish
application-held references, collectable connection/executor/manager cycles,
PHP allocator arenas, driver buffers, and file descriptors. Change reference
release only if retention is material and the cursor's observable lifecycle
remains intact; do not redesign connection ownership for a microbenchmark.

### Existing semantics to preserve

[AssociativeHydrationTest](../../tests/Unit/AssociativeHydrationTest.php)
explicitly proves that cursor observation ends at handoff and a later fetch
failure emits no second event. Ordinary terminals observe their executor
attempt, while some aggregate result conversion happens in `QueryBuilder`
after execution. Document those boundaries; do not silently turn observation
into end-to-end iteration or application-validation telemetry.

[QueryBuilderStateIntegrityTest](../../tests/Unit/QueryBuilderStateIntegrityTest.php)
and the retained audit intentionally preserve partial `select`/`groupBy`
mutation. A failed multi-column call can retain earlier valid elements, while
many single-condition calls attach only after validation. Keep that behavior
and improve consumer guidance by default. An optional atomic implementation
would normalize into a temporary list before append, but needs an accepted
lifecycle decision, changed tests, upgrade notes, and a memory-cost check.
Callback-driven `when`/`unless` mutations do not acquire rollback semantics.

[ADR-009](../adr/009-exception-evidence-and-redaction.md) retains the previous
PDO exception. Binding values are not interpolated into library messages, but
raw SQL may contain literals and a chained driver exception can contain
sensitive diagnostics. Preserve the actual boundary in documentation and tests;
do not promise an entirely sanitized exception graph or log full traces as
part of new evidence collection. Review SQLSTATE fallback handling against
real driver shapes before tightening it.

The historical `0.6.0` certification's diagnostic-redaction statement claims
that diagnostic chains never disclose sensitive data. That is broader than
ADR-009 and the implementation, which deliberately retain the original PDO
exception. Record this discrepancy in the new release review and correct
current guidance; do not silently rewrite the historical certification or
remove the public cause chain as an incidental cleanup.

## Workstream B — Simplification and de-duplication

Prefer reducing the number of places that own an invariant. Similar-looking
code is not sufficient reason for abstraction: error context, validation
order, ownership, and dialect behavior may differ intentionally.

| Candidate | Narrow change to evaluate | Constraint / stop rule |
| --- | --- | --- |
| M1: raw binding normalization | Share ordered-list validation plus `Binding::fromValue()` mapping between `RawQuery` and `RawExpression`, preferably in an existing internal normalization boundary. | Keep contextual error text and timing; leave `CompiledQuery`'s concrete-binding validation distinct. Do not create a public normalizer. |
| M2: associative row validation | Share the array/string-key invariant between eager, first, and cursor reads using a small internal helper. | Keep contextual errors lazy, no per-row metadata allocation, no loss of numeric-key rejection; retain local code if helper dispatch costs more than it saves in maintenance. |
| M3: clone bookkeeping | Remove assignments already performed by `clone`; consider reusing readonly `ConditionTerm` objects whose predicates contain no mutable groups. | Deep-copy nested `GroupPredicate` collections, join conditions, and lock state. Preserve `copyForCompilation()`'s read-only sharing boundary. |
| Compiler write paths | Review repeated physical-table validation/quoting and short wrapper methods only beside relevant edits. | Preserve early write-shape rejection and row-local validation order; do not force inserts, updates, and deletes into one configurable operation engine. |
| Transaction reset helpers | Review `resetLogicalDepthOnly()` delegating to `resetManagedState()` for naming accuracy and useful intent. | Both currently clear depth and ownership. Do not merge error paths that differ in ownership, quarantine, or callback precedence. |
| Construction options | Review the two `RequestedBooleanOption` instances and multiple effective-option passes for readability. | Construction is a cold path; a typed descriptor can be clearer than positional arguments or untyped arrays. No generic option registry. |
| Public terminal wrappers | Keep explicit `QueryBuilder` and `RawQuery` forwarding methods. | Their compilation and first-row semantics differ. A trait/base terminal class adds coupling for little shared logic. |
| Predicate/compiler types | Keep typed predicates, the internal compiler interface, and MariaDB/MySQL distinctions. | Do not replace them with tagged arrays, a visitor framework, reflection dispatch, or a public dialect registry solely to reduce files. |
| Recording observer | Keep its bounded list at ordinary capacities. | A ring buffer adds indexing/order/reset complexity; require a measured high-capacity use case before adopting it. |
| Public PHPDoc | Add precise callback types for `when`/`unless`, and review non-empty ordered write-row shapes against runtime. | Annotations affect static consumers; inspect the complete public manifest and external consumer diagnostics. |

The two-pass [CompiledQuery](../../src/CompiledQuery.php) validation is not an
obvious duplication to remove. Historical evidence deliberately preserves
member validation before concrete-type validation. Merging passes changes
which invalid member is reported first for mixed bad input. Likewise,
`insertMany()` validates each row's ordered columns before its values, and
normalizes that row before inspecting the next. Preserve these precedences.

For every accepted extraction, show the repeated rule it removes, the remaining
call sites, exception behavior, and focused checks. For every rejected candidate,
record a short reason. Do not introduce a duplication-percentage gate, LOC
target, class-count target, or a second architecture layer to improve metrics.
Maintainability improvements can be accepted without a measurable speedup when
they simplify reasoning and do not regress performance materially.

## Workstream C — Performance with attributable results

### Start with work performed unnecessarily

[Executor::affectedRows()](../../src/Internal/Executor.php) reads `rowCount()`
inside its operation; `attempt()` reads it again for metadata. The second read
happens even when no observer exists. `insertGetId()` also causes a metadata
row-count read with observation disabled.

Evaluate reusing the required affected-row result and reading additional
metadata only when it will be observed. Keep the dispatch explicit and small;
do not create an operation/result class hierarchy to avoid one PDO call.
Assert returned counts, generated-ID timing, observer counts, and behavior when
a required `rowCount()` fails. Characterize the removed unnecessary second
failure opportunity. Add direct controls for writes because the existing
cleanup control measures close calls, not row-count acquisition.

After correctness work, use this experiment matrix:

| Surface | Existing control / workload | Question and guard |
| --- | --- | --- |
| Ordinary terminal cleanup | `execution_cleanup`, first rows, terminal reuse | Does the accepted single-cleanup implementation reduce work without changing primary failure or event ordering? |
| Write counts / generated IDs | `batch_execute`, write terminals, direct PDO | How much overhead is removed with observation off/on? Return the same counts/IDs and keep ID acquisition on the same connection. |
| Build vs compile | `compiler_shapes`, `compile_allocation`, `compiler_attribution` | Separate identifier normalization/building from prepared-builder compilation; do not claim compilation savings from cheaper setup alone. |
| Snapshot copies | Existing deep/shallow controls; nested-group clone case if needed | Does removing redundant clone work matter for complete snapshot/compile operations? No sharing of mutable attached groups. |
| High-cardinality inputs | `compiler_in_list_*`, `compiler_batch_insert_*`, predicate scaling | Check time and transient bytes per binding/row, SQL size, and scaling; no automatic chunking or new limits. |
| Result hydration | Narrow/wide object and associative results, first row, cursor drain/early close | Attribute key validation and closure dispatch while preserving result shape and cleanup. No return to an already-rejected hydration algorithm without new evidence. |
| Resource retention | `result_memory_*`, lifecycle and cursor soak | Separate full-result O(rows) retention from non-retaining consumption, and PHP memory from PDO buffering. |
| Observation | Off, no-op, bounded recording, throwing; 1 and 50 bindings | Preserve no timing/event construction when disabled and no effect of observer failures on database results. |
| Transactions / construction | Existing transaction and lifecycle controls | Distinguish PHP overhead from connection/profile and ownership-guard round trips; retain guards that detect transaction replacement. |

### Measurement and acceptance protocol

1. Use immutable `v0.6.0` and one candidate at a time with the same harness,
   fixtures, PHP/PDO, OPcache/JIT, extensions, and machine conditions. Keep fixture
   setup outside timing; ensure fresh LOB state if a scenario consumes streams.
2. Verify exact SQL, values/types, counts, IDs, or normalized result facts before
   timing. Keep the existing fresh-worker SHA-256 correctness gates. Direct PDO
   controls must perform equivalent work and use the same result/buffering mode.
3. Use the existing three warm-ups, nine samples, five identical-source noise
   runs, and both baseline-first and candidate-first comparisons. Record medians,
   raw samples, absolute changes, percentage changes, per-operation ranges,
   transient allocated/used bytes, retained growth, RSS, and descriptors.
4. Retain the [benchmarking policy](../maintainers/benchmarking.md): greater-than-5%
   median regressions require review when outside the applicable noise controls;
   a repeatable actionable regression in both orders cannot be dismissed. A
   tiny baseline can produce an impressive percentage without meaningful time
   saved. Never copy a historical host's noise floor to a new measurement.
5. Accept a performance claim only when the full relevant operation improves
   reproducibly outside noise, or a meaningful allocation reduction is
   demonstrated. Report absolute bytes/time and workload dimensions. Component
   controls explain attribution; they do not establish application throughput.
6. Preserve the 256 KiB retained-allocation soak bound and flat descriptor
   requirement. Investigate a meaningful RSS or transient-memory regression even
   if it does not cross a retained-growth limit. Do not reset baselines to hide it.
7. Stop an experiment when the effect is below noise, already rejected for the
   same workload, or requires more complexity than its demonstrated benefit.
   Retain an explanatory no-change outcome, not an optimized-looking rewrite.

Compilation/statement caching, binding interning, global state, automatic batch
sizing, and transparent reconnect/retry remain excluded. They add invalidation,
resource, lifetime, or atomicity obligations beyond this release. The previous
release already reduced high-cardinality intermediates and associative key
allocation; do not schedule those completed changes again.

## Workstream D — Tests and maintainer automation

### Q1/Q2: Prove contracts independently

[GoldenFixtureTest](../../tests/Compiler/GoldenFixtureTest.php) currently checks
types only when a non-empty expected list is supplied. Its feature-coverage
check compares a JSON feature list to another literal list; it does not prove
that each feature has an executable case.

Define a small fixture schema requiring unique case IDs, explicit dialect,
exact SQL, ordered values and types, matching binding/type cardinality, and
references from features to executable cases or focused rejection tests.
Require each intended dialect case or an explicit unsupported expectation.
Do not auto-generate expected SQL from the same production compiler under test.
Do not count `?` characters in arbitrary trusted SQL as a placeholder parser.
Cover unknown IDs, duplicate IDs, orphan feature references, missing types,
missing intended dialects, and malformed schema with negative fixture tests.

Extend the existing connection state, transaction failure, cursor failure,
associative hydration, compiler efficiency, and public-value tests before
adding new harnesses. Include newly reproduced S1/S2 paths and the S3/S4
ownership matrix. Use deterministic tables for comparison shapes, ordered batch
columns, aggregate overflow/scalar conversion, identifier quoting, and
pagination boundaries only where coverage is missing.

A bounded mutation/fault pilot should target dropped/reordered bindings,
bypassed invalid-input guards, lost callback causes, omitted quarantine,
double cleanup, broken snapshot copies, and observer interference. A manually
injected change with a demonstrated failing regression is an acceptable first
step. Record equivalent, unreachable, and meaningful surviving faults separately.
Do not add a repository-wide mutation dependency, random CI fuzzing, or 100%
path-coverage goal by default.

Coverage floors remain 90% overall line, 80% overall branch, 95% compiler line,
and 90% compiler branch. Maintain no-dev consumer analysis and native PHP 8.2
compatibility. Keep synthetic PDO seams reset between tests; do not multiply
nearly identical doubles or mock internal compilers/transaction managers.

### Q3: Make release checks fail for absent or contradictory facts

[ReleaseConsistencyChecker](../../tools/quality/ReleaseConsistencyChecker.php)
returns no error for several missing files, unmatched metadata regexes, or
unreadable facts. The baseline check proves only that documentation contains
the tag found in a particular workflow command. Both can remain at `v0.5.0`
after `v0.6.0` is released and still pass.

Establish explicit required facts and validate their schema before comparing
them. Relate dated changelog/current supported minor, security series,
recommended pin, active plan target, benchmark baseline, current evidence index,
and workflow artifact labels. Test missing, malformed, mutually stale, and
conflicting facts. Require an active plan during development and allow a
well-defined plan-free post-release state; do not demand a speculative next
plan immediately after publishing.

Tag existence and commit identity belong in a release context with full Git
history. A packaged installation or shallow checkout must not accidentally
fail a routine check because it lacks tags; require an explicit release input
or clearly state that verification is unavailable. Do not infer the intended
baseline from the highest-looking tag string. Historical evidence stays valid,
but current labels in an evidence index must still be checked.

The old `0.6` plan retirement and evidence reclassification are already complete
in the audited commit. Only the stale benchmark baseline and remaining semantic
relationships need work. Do not schedule completed transitions again.

### Q4/Q5: Reduce duplicated maintenance knowledge

## Workstream E — Distribution, compatibility, and user clarity

### D1: Certify what the consumer installs

[composer.json](../../composer.json) excludes only four directories from local
archives. Git ignores do not define the release distribution. The current
`no-dev-consumer` CI job installs dependencies in the project checkout and runs
checkout examples. The consumer PHPUnit tests also run under the repository
bootstrap. These are valuable checks, but do not prove the contents or behavior
of a separately installed hosted dist artifact.

Define an explicit package policy covering `src/`, Composer metadata, license,
README, support/security policy, upgrade guidance, and enough public usage
documentation to make the shipped entry points useful. **Keep `src/Testing/`:**
it is part of the public compiler/observer toolkit, distinct from the root test
suite. Inspect README links before excluding all guides or examples.

Certify separate paths: local Composer archive, Git/source archive, hosted dist,
and installation of that artifact into an external consumer. Test the actual
output from each path rather than assuming Composer exclusions and VCS
export-ignore rules have identical effects. Use a clean detached source tree
for release measurements. Also test exclusion rules against harmless synthetic
ignored output so accidental developer-tree archiving cannot absorb caches,
coverage, `vendor/`, local configuration, or environment files.

The external consumer must install without dev dependencies, load the public
namespace and testing toolkit, compile all declared dialects, and execute a
compact SQLite read/write/cursor/transaction/error lifecycle using its own
fixture. It must not import repository-only helpers. Check optimized autoload,
platform requirements, included files, source commit and artifact checksum.
Set a justified size/file budget from clean inputs; verify allowed roots so a
small unexpected file cannot pass solely by staying under the byte limit.

Before publication, validate locally built artifacts and an available hosted
source artifact. Verification of the final published release dist is a
post-publication checklist step, not a circular pre-release gate. Nothing in
this plan authorizes publishing, tagging, pushing, or changing external services.

would not prove the declared MySQL minimum. Respect the
[support policy](../../SUPPORT.md)'s breaking-release, 12-month notice, and
migration requirements for any future floor removal.

### Consumer documentation acceptance

Update only the guides/reference affected by accepted behavior. A clean
consumer should understand:

- which inputs are values, identifiers, or explicitly trusted SQL;
- malformed overload rejection and what to do after failed builder mutation;
- first/count/aggregate pagination semantics and precision-preserving scalars;
- full-result memory versus PDO buffering and caller-managed streaming;
- LOB ownership, current position, and repeated-terminal limitations;
- cursor handoff observation, cleanup failures, quarantine, and uncertain writes;
- exception messages versus raw SQL and chained driver diagnostics;
- supported floors, exact tested fixtures, and upstream maintenance status.

Use runnable examples where they resolve a real ambiguity. Public behavior
changes need changelog and upgrade entries even with identical signatures.
ADRs record accepted lifecycle, binding, observation, transaction, security, or
support decisions. Do not add release notes for routine internal extraction or
republish historical evidence merely because this plan changed.

## Risks, decisions, and stop conditions

| Risk / decision | Control |
| --- | --- |
| Cleanup simplification changes success to failure after a write completed. | Set outcome/connection policy first; explain uncertain/completed writes and forbid automatic replay. |
| A supported exception-mode PDO rarely returns a synthetic false value. | Mark reachability; keep tests proportional to a contract rather than assuming frequency or severity. |
| De-duplication erases context or changes error precedence. | Assert contextual errors and mixed-invalid-input ordering; retain intentional duplication. |
| Stream snapshots are mistaken for byte snapshots. | Explain external resource ownership and qualify real-driver behavior; no hidden materialization. |
| Partial mutation is treated as a newly discovered defect. | Preserve the tested historical contract unless a separate lifecycle decision changes it. |
| Timing noise encourages repeated speculative rewrites. | Reuse the accepted controls, stop below noise, and record rejected candidates. |
| Distribution slimming removes public tooling or useful documentation. | Explicitly retain `src/Testing`, inspect links, and exercise the installed consumer. |
| Upstream refresh grows permanent support obligations. | Keep minimum lanes, accept new targets separately, and qualify exact proxy fixtures. |
| Stronger release checks require unavailable Git history. | Separate source consistency from tag provenance with explicit release-context inputs. |
| Comprehensive planning becomes excessive release bureaucracy. | Require compact decision evidence, use existing tools, and allow measured no-change outcomes. |

Explicitly excluded: ORM/schema/migration features, additional query/result
families, new public extension hooks, additional SQL dialects, connection pools,
routers, automatic retries/reconnects, statement/compilation caches, automatic
batching or transaction policy, removal of existing floors, broad class splits,
framework dependencies, global mutable state, universal proxy guarantees,
unsubstantiated performance/security claims, private consumer inspection, and
automatic publishing.

The release is ready when the reproduced correctness gaps are resolved, resource
and failure boundaries are intentional and tested, accepted simplifications
reduce maintenance burden without weakening contracts, performance decisions
have attributable evidence, consumers receive a clean usable package, and
compatibility and release documentation describe only what was verified.
