# 0.10.0 analysis and implementation plan

Status: active candidate implementation, authorized on 2026-10-23.
Reviewed on 2026-10-23 against `193321ba393db4f19b291fbddddfb8a5bbdb8559`
(`master`, also the locally available `v0.9.0` tag). The starting worktree was
clean. This document proposes release scope; it does not change the released
public contract or certify a candidate.

## Release recommendation

Make 0.10.0 a focused reliability and consumer-typing release. Five findings
below have local reproductions. Prioritize cursor ownership and nested-lock
validation, then normalize lock-precondition inspection failures, resolve the
observer metadata contract, and improve existing conditional callback typing.
Do not add SQL features merely to populate a minor release.

Keep PHP 8.2, MariaDB 11.8, MySQL 8.0, and SQLite 3.39.2+ as the declared
compatibility floors. Retain the documented ProxySQL/MaxScale fixtures without
turning them into dialects or extending their topology claims. Follow the
[support policy](../../SUPPORT.md) and
[database support reference](../reference/database-support.md).

The 2026-10-23 implementation request accepts the recommended D1 rejection
policy and D2 nullable observation depth. Record their durable decisions in
ADRs with the corresponding implementation. No new supported target or
publication is authorized by this candidate plan.

## Prioritized findings

P1 denotes a release-blocking ownership or transaction-precondition gap. P2
denotes a bounded diagnostics or consumer-contract improvement. These are
engineering priorities, not vulnerability severity ratings.

| ID | Priority | Finding and confidence | Proposed disposition |
| --- | --- | --- | --- |
| R1 | P1 | Failed cursor attempts bypass explicit statement cleanup before handoff. Confirmed with the maintained statement double. | Fix ownership transfer in the executor. |
| R2 | P1 | A locked child retains lock SQL while its parent loses the transaction precondition. Confirmed by compilation and intercepted dispatch; live engine effects remain untested here. | Resolve D1, then reject unsupported composition or preserve the requirement internally. |
| R3 | P2 | Failed optional transaction-depth inspection suppresses the entire observer notification. Confirmed with the maintained PDO double. | Resolve D2 without changing the database outcome. |
| R4 | P2 | The lock guard propagates a raw PDO inspection failure without quarantining the owner. Confirmed with the maintained PDO double. | Use transaction-state evidence for this precondition; retain strict-close policy. |
| R5 | P2 | Untyped `when()`/`unless()` callback parameters infer as `mixed`. Confirmed by an independent level-9 consumer fixture. | Describe the existing callback type in PHPDoc and test inference. |

### R1: cleanup before cursor ownership transfer

In [Executor::attempt()](../../src/Internal/Executor.php), cursor mode sets
`retainStatement` before preparation. The `finally` block skips cleanup for that
mode even when binding or execution failed and no `Cursor` was constructed.
Successful cursor ownership and requested cursor mode are different facts.

Reproduce from the repository root after installing development dependencies:

```php
<?php
declare(strict_types=1);
require 'vendor/autoload.php';

use Oeltima\SimpleQuery\Connection;
use Oeltima\SimpleQuery\Driver;
use Oeltima\SimpleQuery\Tests\Unit\ConfigurableStatement;

ConfigurableStatement::reset();
$db = Connection::connect(Driver::Sqlite, 'sqlite::memory:', pdoOptions: [
    PDO::ATTR_STATEMENT_CLASS => [ConfigurableStatement::class],
]);
ConfigurableStatement::$executeReturnsFalse = true;
try {
    $db->query('SELECT 42 AS value')->iterateAssociative();
} catch (Throwable $failure) {
    echo $failure::class, ': ', ConfigurableStatement::$closeCalls, PHP_EOL;
}
$db->discard();
```

Observed: `QueryExecutionException` and zero `closeCursor()` calls. The same
failure through `firstAssociative()` attempts cleanup once. Both object and
associative cursor terminals reproduce the omission. PDO/statement destruction
may perform additional cleanup; this observation establishes the missing
explicit attempt, not a measured server-resource leak.

PDO documents [cursor cleanup](https://www.php.net/manual/en/pdostatement.closecursor.php)
as releasing a connection for subsequent statements. Qualify the practical
failure/recovery behavior with the live probes below.

Implementation should track actual handoff and keep failure cleanup owned by
the executor until that point. Preserve the original bind/execute failure,
single notification, and existing ordinary-cleanup policy. A successful cursor
must still be closed exclusively through its cursor lifecycle.

### R2: nested locks lose execution requirements

[Connection::table()](../../src/Connection.php) and
[ConditionFactory::in()](../../src/Internal/Ast/ConditionFactory.php) snapshot
children into `CompiledQuery`. That value carries SQL/bindings only.
[QueryBuilder::compiledForExecution()](../../src/QueryBuilder.php) checks only
the parent's top-level lock state.

For either MariaDB or MySQL compilation:

```php
$db = Oeltima\SimpleQuery\Testing\CompilerConnection::for(
    Oeltima\SimpleQuery\Driver::MySql,
);
$child = $db->table('jobs')->select('id')->where('state', 'ready')->forUpdate();
$parent = $db->table('jobs')->whereIn('id', $child);
echo $parent->compile()->sql;
```

Observed SQL:

```sql
SELECT * FROM `jobs` WHERE `id` IN (SELECT `id` FROM `jobs` WHERE `state` = ? FOR UPDATE)
```

The parent has no top-level lock. A controlled PDO with a declared MySQL profile
and intercepted preparation reports zero prepare calls for the direct locked
child outside a transaction (`TransactionStateException`), but one prepare call
for both an `IN` parent and a derived-source parent. The latter reach preparation
before failing at the interception. Update/delete predicates and scalar/count
terminals also need review because they use different execution paths or strip
only top-level locks.

This conflicts with the guide's active-transaction precondition for structured
locking reads. MySQL documents separate lock scopes for nested queries and the
transaction requirement in its
[8.0 locking-read reference](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html).
That source supports investigating the requirement; it does not establish
MariaDB or proxy behavior. Do not parse trusted raw SQL to infer lock intent.

### R3: optional observation metadata can erase an event

`Executor::notify()` constructs `QueryExecution` inside its observer-isolation
catch. `Connection::transactionDepth()` can call `PDO::inTransaction()` there.
When that call fails at unmanaged depth, construction stops and the observer is
never called, although the statement result is returned successfully.

Using `ControlledTransactionPdo` and `RecordingQueryObserver`, construct a
SQLite connection, set `failTransactionInspection = true`, and execute
`SELECT 42 AS value` through `firstAssociative()`. Observed: the expected row
and zero notifications. Restoring inspection permits normal cleanup.

Keeping the successful result is correct. Silently losing the event conflicts
with the guide's one-notification-per-attempt wording. `QueryExecution` currently
requires an integer depth, so an unknown depth cannot be represented honestly
without either a contract change or an explicit best-effort delivery policy.
Never fabricate depth zero or quarantine a successful query solely because
optional telemetry could not be collected.

### R4: lock-precondition inspection failure

With `ControlledTransactionPdo::failTransactionInspection = true`, the internal
lock guard throws the raw `PDOException`. After disabling the failure,
`isReusable()` returns true. By contrast, failure inside `isReusable()` or the
transaction manager produces structured `TransactionStateException` evidence
and quarantines the wrapper.

For the lock precondition, capture managed depth before quarantine, mark
uncertain state unusable, and throw the existing transaction-state exception
with the operation, driver, label, captured depth, and `controlFailure`. Keep
driver text out of the top-level message; retained
failure objects remain subject to the documented logging boundary. Do not add
rollback, reconnect, health checks, or replay. Apply this policy separately from
optional R3 metadata.

The same reproduction through `close()` also propagates the PDO failure, but
that behavior is explicitly retained by ADR-024 and `ConnectionDiscardTest`.
It is a deliberate policy, not an untested defect. Keep it outside R4 rather
than broadening this item into an unapproved lifecycle change.

### R5: conditional callbacks lack consumer inference

`QueryBuilder::when()` and `unless()` accept `Closure` without the callback
parameter annotations already supplied for joins, condition groups, and
transactions. The maintained consumer fixture explicitly types both callback
parameters, so it cannot detect this gap.

An external PHPStan level-9 fixture using the consumer configuration and this
callback fails `assertType(QueryBuilder::class, $query)` with actual `mixed`:

```php
$builder->when(true, static function ($query): void {
    PHPStan\Testing\assertType(Oeltima\SimpleQuery\QueryBuilder::class, $query);
    $query->where('active', true);
});
```

`unless()` produces the same result. Add callback PHPDoc describing the existing
builder argument and ignored return. Preserve truthiness, callback count,
exception propagation, builder identity, and runtime signatures. Do not add a
value argument, default callback, or replacement-builder behavior.

## Contract decisions before implementation

### D1: locked child-query composition

Recommended bounded scope: reject attaching a child with structured locking via
derived sources or `IN`/`NOT IN`, using the existing unsupported-feature exception
family before parent mutation. Keep standalone locking reads supported. This
narrows previously accepted input and needs an accepted ADR, changelog entry,
and upgrade guidance before implementation.

Alternative: preserve a transaction requirement in internal child snapshots
and carry it through groups, derived sources, clones, aggregates, count rewrites,
and writes. This avoids rejection but needs a larger execution-policy design
and live qualification. Do not add fields to the public `CompiledQuery` merely
to transport an internal capability, and do not guard only read terminals.

The recommended rejection policy is accepted for implementation. Acceptance must cover both MySQL and
MariaDB plus their documented proxy fixtures. If rejection is selected, test
that rejected attachments leave the original parent SQL/bindings unchanged.

### D2: observer depth when inspection fails

Accepted option: make unknown transaction depth explicitly representable in
observation metadata, then isolate that optional read so one notification can
still be delivered. A nullable public depth would change the constructor and
property contract; implement it with an ADR-010 amendment,
manifest review, consumer analysis, and upgrade guidance.

Alternative: retain the integer contract and explicitly document notification
delivery as best effort when metadata collection fails. That narrows an existing
guarantee and also requires a deliberate observation-contract decision. Moving
the inspection before the attempt alone cannot guarantee a notification when
the inspection itself is unavailable.

Neither option may replace a query result/failure, introduce extra statement
execution, emit a second cursor event after handoff, or collect binding values.
Keep disabled-observer execution free of metadata reads and allocations.

### 1. Cursor ownership and cleanup

- Extend the maintained `ConfigurableStatement` seam and focused executor/cursor
  tests for prepare failure, false/throwing bind and execute, both cursor row
  shapes, and builder/raw terminals. Do not mock compiler internals.
- Assert exactly one cleanup attempt when a statement exists but handoff fails;
  zero executor cleanup after successful handoff; no active-cursor count leak;
  idempotent cursor close; and unchanged primary failure/observer behavior when
  cleanup also fails. Preserve the explicit ordinary-cleanup behavior already
  tested in `AssociativeHydrationTest`.
- Exercise an actual failed SQLite cursor query followed by usable subsequent
  work. Extend execution probes for unbuffered direct/proxy recovery after a
  failed cursor attempt; use a direct engine as each proxy's control.
- Review the result/resource ADRs and update the results guide and changelog
  only for the final user-visible correction.

### 2. Nested-lock boundaries

- Add exact SQL and ordered typed-binding coverage for the selected D1 policy
  in both MySQL-family compilers and the appropriate golden cases/feature map.
- Cover derived sources, every `IN`/`NOT IN` variant, grouped conditions,
  multi-level attachment, snapshots and clones, and unchanged ordinary child
  queries. Test child mutation after attachment and cross-owner rejection.
- Cover read, first-row, cursor, count/scalar, update, and delete paths wherever
  the selected policy permits them. Top-level logical aggregates must retain
  their existing lock-stripping behavior.
- For rejection, prove no preparation occurs and parents remain unchanged.
  For propagation, prove rejection outside a transaction and actual lock scope
  inside one with two live sessions. Preserve SQLite lock rejection.
- Extend the maintained execution/vendor-write probes for both direct engines,
  then proxy controls. Update the query-builder guide, upgrade guide, changelog,
  and accepted ADR. Never infer live support from the compilation reproduction.

### 3. Lock-precondition state inspection

- Add cases to the controlled PDO lifecycle/state matrix for throwing lock
  inspections, alongside active/inactive success cases.
- Assert safe exception messages, operation/owner evidence, retained control
  failure, unusable status, execution rejection without another inspection after
  quarantine, stale builder rejection, and explicit discard/replacement behavior.
- Cover failure inside a managed callback: preserve its failure evidence and
  issue no subsequent transaction-control SQL on the quarantined owner.
- Preserve strict-close inspection/propagation, successful close idempotence,
  and rejection of active transactions/cursors. Keep transaction ownership/
  control-count tests green; an extraction must not add inspection calls to
  successful operations.
- Update lifecycle/exception guidance and the relevant ADR amendments for the
  final semantic change. Use the existing exception types.

### 4. Observation failure isolation

- Extend the maintained PDO/statement seams for metadata failure after successful
  read/write execution and after an original query failure. Include managed and
  unmanaged depth, cursor handoff, and an observer that itself throws.
- Assert the D2 delivery/depth policy, the original result or failure identity,
  no retries, redacted parameter types/counts, no duplicate cursor events, and
  zero optional metadata reads when observation is disabled.
- If a public type changes, update the independent consumer fixture, public
  reference, observability guide, upgrade guide, changelog, ADR-010, and reviewed
  API manifest together. Test valid known/unknown values and invalid metadata.
- Compare disabled/no-op/recording/failing observer scenarios against `v0.9.0`;
  do not restore per-attempt outcome allocations to the disabled hot path.

### 5. Conditional callback typing

- Add the precise callback annotation and remove explicit callback parameter
  types in focused consumer inference assertions for both methods.
- Retain assertions for the returned builder identity/type and ignored callback
  returns. Reuse existing behavioral tests rather than duplicating the
  implementation in new runtime tests.
- Document the inferred callback shape, update the changelog for consumer-facing
  typing, and regenerate/review the API manifest for the intentional annotation
  change. No new ADR is needed if the accepted semantics remain unchanged.

## Scope retained or deferred

The following reviewed behaviors are intentional, not defects to silently fix:

- `select()`/`groupBy()` retain earlier valid arguments when a later argument
  fails; the guide and `QueryBuilderStateIntegrityTest` explicitly record this.
  Atomic clause mutation would require a separate lifecycle decision.
- Ordinary statement cleanup and live cursor cleanup have different failure
  policies. Preserve the existing tests; R1 is about ownership before handoff.
- Strict `close()` may inspect PDO even after quarantine and propagates inspection
  failures. ADR-024 retains this policy; `discard()` is the inspection-free exit.
- LOB resources remain caller-owned and position-sensitive. Snapshots do not
  copy stream contents. Preserve the maintained LOB probes and guidance.
- Logical count, grouped/distinct scalar rejection, generated-ID timing,
  transaction ownership guards, no replay, and bounded observation remain in
  force. Do not revisit them merely because their implementation has a cost.

Defer new existence/keyset/chunking helpers, CTE/union/window APIs, generic
upsert/returning, result mapping/ORM behavior, connection pools/routing/retries,
framework integrations, and public compiler plugins. No demonstrated consumer
requirement in this review justifies expanding those contracts. Prefer the
existing trusted raw-query boundary when it already covers the task.

MySQL 8.4 qualification, replacement proxy fixtures, and floor changes need
separate scope and live evidence. Review upstream maintenance at certification:
as checked on 2026-10-23, PHP lists PHP 8.2 security support through
2026-12-31 in its [support schedule](https://www.php.net/supported-versions.php).
Package compatibility remains distinct from upstream maintenance; this plan
does not start a floor-removal notice or promise a new engine target.

Do not schedule speculative compiler/hydration optimizations. Use the existing
correctness-gated dimensional and observer benchmarks only to assess actual
changes. Retain fresh noise controls, both source orders, and the existing
review thresholds; do not refresh measured evidence merely to pass a gate.

## Validation and release gates

For each implementation change, run focused unit/compiler/SQLite checks first,
then `composer check`. Run line and branch coverage after source changes:

```bash
composer test:coverage
composer coverage:check
composer test:coverage:branch
composer coverage:check:branch
```

Retain 90% overall/95% compiler line and 80% overall/90% compiler branch gates.
The specific failure and non-mutation cases above remain mandatory even when
the percentages pass. Run `composer public-api:check`; regenerate the manifest
only for an accepted signature or annotation change and review its full diff.

Before candidate acceptance:

1. Resolve D1/D2, implement the selected scope, and record compatibility impact.
2. Pass PHP 8.2–8.5 and lowest-dependency CI, SQLite probes/contention, actual
   SQLite 3.39.2 execution via the maintained minimum runner, and the exact
   minimum/current MariaDB/MySQL fixture pairs.
3. Run `bash tools/database-probes/run-services.sh` for the maintained native/
   emulated and buffered/unbuffered direct/proxy matrix, including the focused
   new failure/lock cases. Review actual report contents and archive runtime,
   fixture, image, source, and mode identities.
4. Run the existing CI benchmark suite and both comparison source orders against
   immutable `v0.9.0`, with freshly measured identical-source noise controls;
   run the reference soak. Follow the maintained
   [benchmark workflow](../maintainers/benchmarking.md). Existing reports are
   not evidence for a new candidate.
5. Pass strict Composer validation/audit, line/branch gates, examples, public API,
