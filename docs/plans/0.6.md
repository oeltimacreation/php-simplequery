# `0.6.0` development plan

Status: Accepted; Phases 0–1 complete. Baseline: immutable released `v0.5.0`
(`902a18037303d7e28cefcad6859c157b98e2d05b`).

Target: the next minor release after `0.5.x`. No calendar date is promised.

## Release intent

`0.6.0` is an evidence-first performance, efficiency, code-quality, and user-
experience release. It should reduce demonstrated PHP-side costs, shorten
maintainer feedback loops, and make supported behavior easier to choose and
troubleshoot without weakening the library's deterministic SQL, binding,
resource-ownership, or security contracts.

The release begins with a public-contract freeze. No new public method, class,
driver, or compatibility claim is accepted by this plan. Phase 5 may recommend
one already-deferred feature family only when public usage evidence establishes
the need; accepting it requires an explicit plan revision, exact semantics,
tests, documentation, changelog coverage, and an ADR where required.

Database work normally dominates end-to-end latency, so `0.6.0` will not claim
a general speedup from isolated micro-benchmarks. Each optimization must name
the workload it improves and retain an appropriate direct-PDO control.

## `v0.5.0` baseline and audit findings

The initial clean-tree inventory and the released
[`0.5.0` evidence](../evidence/0.5-maintainability-and-performance.md) record
the following starting point. Phase 0 reproduced the quality and performance
results from the immutable tag before product implementation began.

| Baseline | `v0.5.0` result |
| --- | ---: |
| Product PHP files / lines under `src/` | 69 / 5,141 |
| Maintained PHP/shell files / lines under `tools`, `scripts`, `benchmarks`, and `tests` | 72 / 10,298 |
| Public manifest types / members | 30 / 199 |
| CI / soak benchmark scenarios | 19 / 4 |
| Overall line / branch coverage | 94.70% / 91.04% |
| Compiler line / branch coverage | 97.27% / 91.48% |

These counts are inventory, not reduction targets. Code or test deletion is
valuable only when it removes a demonstrated maintenance cost without losing
behavioral evidence.

The audit found the following opportunities:

| Area | Finding | `0.6.0` response |
| --- | --- | --- |
| Benchmark attribution | Some scenarios combine builder construction and compilation; repeated compilation is soak-only, and transient peak allocation is reported only at process level. | Separate build, compile, execution, and hydration costs before optimizing them. |
| Large structured queries | `IN` placeholder generation creates an intermediate array, while batch compilation repeatedly derives row keys and creates per-row value lists. | Add isolated scale and allocation evidence, then remove only material intermediate work. |
| Result hydration | Associative validation allocates a complete key list per row, while the maintained fixture covers one narrow three-column shape. | Measure narrow, wide, full-result, and cursor workloads before changing validation. |
| Resource cleanup | Terminal and cursor cleanup, observation, and quarantine behavior are correctness-sensitive and cross several success/failure paths. | Audit the state transitions and optimize only with exact failure and live-PDO evidence. |
| Responsibility hotspots | `AbstractDialectCompiler`, `TransactionManager`, and `QueryBuilder` remain the largest cohesive classes. The prior architecture audit deliberately retained their boundaries. | Track method-level complexity and invariant ownership; do not split classes because of line count alone. |
| Release consistency | The planning transition repaired the active-plan indexes, and Phase 1 repaired benchmark comparison labels and artifacts. Remaining drift includes `SUPPORT.md` calling `0.3.0` current and CodeScene configuration naming a retired duplication-gate path. | Repair the remaining drift in implementation and add a deterministic consistency check. |
| User journey | Topic guides are comprehensive, but exception recovery, terminal selection, batching limits, and first-response troubleshooting require navigation across several pages. | Add task-oriented decision and troubleshooting paths backed by runnable examples. |
| Maintainer efficiency | The repository has broad quality and compatibility coverage, but no current wall-time baseline identifies the slow or duplicated feedback steps. | Measure local and CI critical paths before changing their composition or parallelism. |

The audit found no evidence justifying query compilation caching, prepared-
statement caching, automatic chunk selection, or a broad internal rewrite.

## Decision rules and release gates

Priority order is correctness and data safety, resource ownership, user
clarity, measured performance, and then code volume.

- A performance change enters implementation only after a correctness-gated
  `v0.5.0` baseline reproduces the target workload and isolates the cost.
- A targeted optimization should improve median time or transient allocation
  by at least 10% in both source orders and outside the Phase 1 noise floor.
  Smaller results may be recorded, but do not justify extra complexity or a
  release-level performance claim.
- No accepted scenario may show an unexplained repeatable median regression
  above 5%. For sub-millisecond operations, the Phase 1 absolute noise floor
  must also be exceeded before a percentage is actionable.
- Correctness digests, exact SQL, placeholder order, binding types and values,
  exception/redaction behavior, terminal non-mutation, clone isolation, and
  nested-builder snapshots remain mandatory.
- Retained allocation remains bounded by 256 KiB in soak workers, and file-
  descriptor counts must stay flat. Phase 1 adds per-operation transient peak
  evidence instead of treating allocator retention as peak usage.
- Coverage floors remain 90% overall line, 80% overall branch, 95% compiler
  line, and 90% compiler branch. Test or assertion counts are not goals.
- `tests/Fixtures/Contracts/public-api.json` remains byte-identical unless the
  plan is explicitly revised for an accepted public contract change.
- MariaDB 11.8, MySQL 8.0, SQLite 3.39.2+, ProxySQL, and MaxScale claims remain
  unchanged and continue to require their current live controls.
- Maintainer-workflow optimization may remove or combine work only after its
  wall time and unique signal are recorded. It must not narrow the PHP matrix,
  coverage, no-dev consumer check, or direct/proxy evidence.

## Phase 1 — Make performance evidence attributable

  compile-only control to the CI suite so AST construction is not confused

- [x] Add isolated dimensional cases for `IN` lists and batch inserts at small,

- [x] Establish an absolute timing noise floor from repeated identical-source

## Phase 2 — Compiler and binding efficiency

- [ ] Replace high-cardinality `IN` placeholder construction only if the
  isolated case proves meaningful time or transient-allocation cost. Preserve
  empty-list truth semantics and exact binding order.
- [ ] Evaluate batch-insert column validation, placeholder construction, and
  binding normalization as separate costs. Avoid repeated intermediate arrays
  only where the scale evidence supports it.
- [ ] Profile identifier quoting, clause accumulation, and compilation
  snapshots before considering loop or allocation changes; reject changes
  whose benefit disappears in the prepared-builder control.
- [ ] Land one optimization at a time and compare it with `v0.5.0` in both
  source orders. Do not reuse mutable compilation contexts or retain query
  values between calls.
- [ ] Cover all accepted work with MariaDB, MySQL, and SQLite golden SQL,
  ordered binding/type assertions, invalid-input ordering, clone isolation,
  nested snapshots, and terminal non-mutation.

Gate: every accepted compiler change meets the performance decision rule and
all dialect contracts remain exact. If no candidate clears the threshold,
close the phase without a compiler change and make no compiler-speed claim.

## Phase 3 — Execution, hydration, and resource efficiency

- [ ] Measure and, if justified, remove intermediary associative-row key
  allocations while preserving duplicate/numeric-column rejection and the
  `array<string, mixed>` contract.
- [ ] Audit statement cleanup across successful terminals, operation failure,
  cleanup failure, cursor hand-off, natural exhaustion, and early close.
  Preserve the primary failure, connection quarantine, and active-cursor
  accounting rules before changing the path.
- [ ] Recheck disabled, no-op, bounded-recording, and failing observer costs.
  Keep observation lazy, redacted, post-attempt, and non-interfering.
- [ ] Verify full-result peak memory grows with retained result size while
  cursor consumption remains bounded. Retain buffered/unbuffered MySQL-family
  controls and direct-engine interpretation for proxy results.
- [ ] Add live SQLite coverage for accepted executor changes and direct
  MariaDB/MySQL probes when affected rows, generated IDs, buffering, or PDO
  cleanup behavior is involved.

Gate: result shapes, exception evidence, observer counts, cursor ownership,
transaction boundaries, and redaction are unchanged; any claimed latency or
memory improvement reproduces outside the noise floor.

## Phase 4 — Code quality and maintainer efficiency

- [ ] Re-audit method-level complexity, duplication, dead configuration, and
  responsibility boundaries. Keep the transaction state machine and compiler
  template cohesive unless a demonstrated defect or change makes extraction
  safer than retention.
- [ ] Add a compact, data-driven state-transition matrix for transaction,
  cursor, connection-close, and quarantine success/failure paths. Avoid test
  duplication that merely increases assertion counts.
- [ ] Audit whether rejected multi-input builder calls partially mutate state.
  Document current behavior or propose a deliberate semantic change with an
  ADR and plan revision; do not silently create a new guarantee.
- [ ] Add a deterministic release-consistency check for active plans, current
  support/security lines, benchmark baseline labels, maintained commands, and
  configuration paths. Historical changelog, ADR, and evidence references must
  remain valid and exempt.
- [ ] Remove stale configuration and documentation references found in Phase
  0, including rules for retired files, without deleting durable evidence.
- [ ] Improve local/CI feedback time only where the wall-time profile shows
  material duplication or serialization. Preserve minimum dependencies, PHP
  8.2 through current-PHP coverage, all quality gates, and failure artifacts.
- [ ] Accept new static-analysis or style rules only when the current tree has
  a zero/low-churn baseline and the rule prevents a concrete defect class.

Gate: all high-risk states have focused evidence, no dead active-tree reference
remains, release metadata agrees, and any workflow reduction retains every
unique compatibility signal while producing a repeatable wall-time benefit.

## Phase 5 — User experience and documentation

- [ ] Walk a clean no-dev consumer through installation, connection setup,
  query construction, result selection, streaming, writes, transactions,
  testing, and failure diagnosis. Record friction without relying on maintainer
  repository knowledge.
- [ ] Add a concise terminal-choice guide covering full object/associative
  results, first rows, aggregates, cursors, affected rows, and generated IDs,
  with memory and driver-return caveats.
- [ ] Add an exception troubleshooting matrix that maps configuration,
  invalid-query, execution, cursor, transaction-state, and connection failures

- [ ] Clarify batching, variable/packet limits, buffered versus unbuffered
  results, deterministic pagination ordering, and application-owned chunk or

- [ ] Review error messages for ambiguity and actionability. Change a message
  only for a demonstrated user problem and synchronize tests, reference docs,
  upgrade guidance, and changelog because consumers may log or assert it.
- [ ] Review the deferred feature families from prior plans against public

- [ ] Synchronize README, support/security policy, guides, references,

Gate: a new consumer can choose the correct supported path and diagnose common
failures from public documentation; all examples execute; no future API is

## Explicit non-goals

Unless this plan is explicitly revised before implementation, `0.6.0` does
not add:

- a new public query-builder method, result terminal, overload, class, or
  extension point from the deferred backlog;
- an ORM, schema/migration API, model layer, identity map, or relationship
  loader;
- connection pooling, routing, global connection state, transparent reconnect,
  automatic retry, or hidden transaction/write replay;
- prepared-statement or builder-compilation caching, retained binding values,
  or a mutable shared compilation context;
- a public compiler, AST, dialect, executor, transaction, or middleware plugin
  platform;
- named placeholders in the structured builder, automatic batch sizing, or
  automatic transaction/chunk policy;
- a new database/proxy target or a raised PHP/database floor;
- broad class splitting, framework dependencies, test-count targets, or source
  deletion performed only to improve a metric;
- user telemetry, private consumer inspection, production data, credentials,
  DSNs, hostnames, or proprietary SQL in fixtures or evidence.

## Release-level definition of done

`0.6.0` is complete only when at least one user-relevant efficiency or
maintainer-feedback improvement clears its measured acceptance threshold; all
other targeted paths remain non-regressed; public behavior, security
boundaries, engine support, and resource ownership remain intact; documentation
and release metadata agree; and the full release certification is green.
