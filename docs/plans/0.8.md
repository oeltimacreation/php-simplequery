# 0.8.0 release plan — worker lifecycle and consumer interoperability

Date: 2026-09-18. Status: active development; W1–W3 implemented and locally
validated. W4–W6 and consumer/FrankenPHP qualification remain pending.

## Release objective

Prioritize the internal consumer that migrated from `pecee/pixie` and is the
first consumer running FrankenPHP worker mode. Make connection loss recoverable
at an explicit application boundary, preserve transaction and write safety,
and turn the migration's remaining integration workarounds into tested recipes
or small, deliberately accepted library improvements.

This document consolidates the former improvement backlog, including its
deferrals. It describes intended work, not shipped behavior or an expanded
support promise. `0.7.0` remains the released baseline; `0.8.0` is the target.
There is no release date or performance improvement commitment yet.

Modernization means improving the lifecycle, diagnostics, typing, and tests
needed by this consumer. It does not authorize a framework integration layer,
an ORM, a connection pool, or a general rewrite.

## Analysis baseline and evidence limits

The read-only review covered SimpleQuery at `894e299` and the internal backend
at `bf102fc6`, plus the supplied 2026-09-18 incident backlog. The backend's
Composer manifest pins `0.7.0`; its lock resolves `v0.7.0` to
`a335eb19dad9b12222cca36e5412996494eed0b9`. Its declared PHP floor is 8.3;
SimpleQuery retains PHP 8.2. No Pixie dependency or namespace reference was
found in the reviewed backend manifest, lock, source, or documentation.

Consumer inspection included connection registration, the connection holder,
model injection and write adapters, HTTP error handling, the worker loop,
route resolution, timeout helpers, representative transaction/answer-save
paths, batch writes, generated IDs, and database/worker operational notes.
Public records must use synthetic examples, without copying private paths,
schema identifiers, SQL, credentials, or production topology.

The supplied incident record describes server-side idle expiry followed by
repeated `HY000` / driver `2006` failures on a cached connection; a fresh
connection worked. The current consumer source already contains a mitigation:
an application holder replaces sufficiently idle handles and discards cached
handles after selected connection failures. The incident predates that
mitigation; do not describe current source as having no recovery at all.

The initial source review did not reproduce the production incident, inspect
a live server, or qualify FrankenPHP. Operational versions, timings, and load
results in consumer notes are reported evidence, not new measurements. W1's
subsequent disposable-fixture validation is recorded separately below.

These explain the review risks; they do not prove the consumer passes cleanup.

## Scope and decision boundaries

Keep the existing [database support matrix](../reference/database-support.md):
MariaDB 11.8, MySQL 8.0, and SQLite 3.39.2+, with configuration-sensitive proxy
fixtures. FrankenPHP is an execution environment, not a database dialect.
Persistent PDO remains outside the supported profile; retaining an ordinary
non-persistent PDO object in a worker is a separate lifecycle question.

Preserve these invariants throughout the release:

- No global connection, concurrent sharing of a PDO, transparent reconnect,
  automatic statement/callback retry, or hidden replay of uncertain writes.
- Replacement creates a new connection through an application-owned factory.
  Existing builders and raw queries never silently move to that connection.
- An active request/transaction/cursor retains its owner until completion or
  explicit abandonment. Loss during a write or commit can leave the outcome
  unknown; a healthy replacement does not resolve that uncertainty.
- Values stay bound, bindings retain placeholder order, terminals do not
  mutate builders, and cross-connection composition stays rejected.
- Request/session cleanup, HTTP status policy, retry budgets, routing, and
  business idempotency belong to the application. Core remains framework-free.

The guide assigns exclusive connection ownership to an execution unit and
recommends fresh ownership and cleanup. Accepted
[ADR-024](../adr/024-explicit-connection-lifecycle.md) defines the conditional
sequential-reuse boundary and explicit invalidation surface. Session cleanup,
factory policy, and consumer adoption remain application-owned under
[ADR-016](../adr/016-maintainer-led-scope-control.md).

| Decision | Direction and status | Alternatives / condition |
| --- | --- | --- |
| D1: lifecycle policy and public state | Accepted in ADR-024: `isClosed()` and `isReusable()` inspect wrapper/local state; application owns sequential reuse and factories. | Fresh connections remain the conservative default. Inspection sends no ping, cannot prove session cleanliness, and quarantines on PDO inspection failure. |
| D2: strict close versus terminal invalidation | Accepted in ADR-024: strict `close()` remains; `discard()` permanently closes the wrapper without state inspection or explicit cleanup SQL. | Discard accepts abandoned active work but cannot complete a transaction successfully, fetch another cursor row, revoke escaped PDO, or prove rollback. |
| D3: connection failure evidence | Accepted and implemented in amended ADR-009: normalized `sqlState`/`driverCode`, driver/context, and `operation` (`connect`/`closed`/`compiler_only`) with a safe top-level message and no retained PDO exception chain. | Query execution keeps its previous `PDOException` for execution diagnostics; retaining one for construction would change disclosure behavior and was declined. |
| D4: connection lifecycle observation | Decided and implemented in W3: application-owned lifecycle counters plus documented observer limits; no lifecycle observer ships in `0.8.0`. | A lifecycle observer still needs a demonstrated gap that counters cannot cover and an [ADR-010](../adr/010-non-interfering-observation.md) amendment. |
| D5: ownership-guard cost | Measure the current guard; retain its guarantee by default. | Optional/profile-controlled guards or another ownership check need an ADR and equivalent failure evidence. A documented decision to retain the cost is a valid outcome. |

D1/D2 were accepted for W1 and D3 for W2; the implemented public surface is
`isClosed()`, `isReusable()`, and `discard()`, with normalized
`ConnectionException` evidence described in W2 below. The former illustrative
`canDiscard()` was not added: terminal discard and possible reuse answer
different questions. D4 was decided and implemented in W3; D5 remains a W5
measurement. Library-controlled idle reconnect/reset is deferred; opt-in alone
does not remove scope or transaction-safety concerns.

### W1 — Explicit lifecycle and recovery

Status: complete for the library workstream, 2026-09-18. See
[W1 validation evidence](../evidence/0.8-connection-lifecycle.md) for the tested
source, exact runtime/engine profiles, results, and qualification limits.

The lifecycle/state tests and direct probes cover reuse, idle expiry, failed
cleanup, and next-unit recovery. They distinguish open/closed, quarantined,
active managed transaction, external physical transaction, live cursor, and
compiler-only wrappers. A connected-looking
object or depth zero is not evidence that the transport is alive or reusable.

D1/D2 are implemented through ADR-024. Local inspection failure produces
`TransactionStateException` with `operation=is_reusable`, retained control
evidence, and `connectionUnusable=true`. Explicit discard does not inspect PDO
state. Keep health-check I/O outside active work; a successful check cannot
guarantee the subsequent statement succeeds. Core retains no reconnect factory
or credentials for reopening wrappers.

Acceptance:

- [x] Reproduce idle expiry in disposable MariaDB and MySQL sessions with a
  short **session** `wait_timeout`; record failure, eviction/invalidation,
  replacement, and successful work in the next execution unit.
- [x] Cover proactive replacement at an application boundary before server
  idle expiry, abrupt disconnect independent of that policy, failed replacement
  construction, and repeated failure/recovery cycles. No failed user statement
  is replayed.
- [x] Test managed/external transactions, active/partially consumed cursors,
  quarantined wrappers, close/state-inspection failures, repeated cleanup,
  stale builders/raw queries/models, and retained PDO references.
- [x] Specify terminal invalidation semantics if accepted: later execution
  cannot resurrect the wrapper; callback completion cannot report false
  success; cursor cleanup and transaction evidence remain deterministic.
  Do not claim dropping references proves rollback or revokes an escaped PDO.
- [x] Existing strict-close and compile-after-close behavior remains covered;
  any deliberate difference receives an upgrade entry and contract review.
- [x] Default request-scoped behavior gains no health-check round trips or
  automatic recovery. SQLite tests cover state, not network-idle claims.

Coverage retains [ConnectionLifecycleTest](../../tests/Unit/ConnectionLifecycleTest.php)
and extends
[ConnectionStateMatrixTest](../../tests/Unit/ConnectionStateMatrixTest.php),
[TransactionFailureTest](../../tests/Unit/TransactionFailureTest.php), and
[CursorFailureTest](../../tests/Unit/CursorFailureTest.php), using the existing
controlled PDO seams and maintained database probes. The focused
[discard tests](../../tests/Unit/ConnectionDiscardTest.php),

[direct lifecycle probe](../../tools/database-probes/connection-lifecycle.php)

Validation passed: `composer check` (670 tests / 2,007 assertions), line and

### W2 — Safe evidence and application failure decisions

Status: complete for the library workstream, 2026-09-18. See
[W2 validation evidence](../evidence/0.8-connection-failure-evidence.md) for the
tested source, commands, results, and qualification limits.

D3 is implemented through the amended
[ADR-009](../adr/009-exception-evidence-and-redaction.md).
`ConnectionException` now carries `operation`, `sqlState`, `driverCode`,
`driver`, and `connectionLabel`. Construction failures use `operation=connect`
with a fixed safe message and no retained `PDOException`, driver message, or
trace; closed and compiler-only misuse use `operation=closed` and
`operation=compiler_only`. The `Connection::connect()` DSN joins the credential
parameters as `#[SensitiveParameter]`. Query execution keeps its previous
`PDOException` and shares the missing/malformed `errorInfo` normalization.

The library still classifies nothing: eviction, retry eligibility,
reconciliation, and logging/HTTP redaction remain application-owned. The
application inspection recipe and the eviction-versus-replay table live in the
[worker guide](../guides/concurrency-and-workers.md#failure-inspection-and-eviction)
and the [transaction guide](../guides/transactions.md).

Acceptance:

- [x] Normalize synthetic PDO error shapes for 1040, 1045, 2002, 2003, 2006,
  2013, and the W1-observed MySQL idle-timeout code 4031, including
  missing/malformed `errorInfo`, string/integer codes,
  SQLite construction failure, and non-PDO configuration rejection.
- [x] Preserve existing constructor call compatibility where possible. Define
  how closed/compiler-only misuse differs from failed construction without
  requiring applications to match human-readable messages.
- [x] Test redaction of DSNs, credentials, host/path details, messages, traces,
  and any retained chain. Keep safe top-level diagnostics; document sensitive
  lower-level evidence and verify consumer logging/HTTP responses accordingly.
- [x] Provide an application inspection recipe for query loss and
  `TransactionException::connectionUnusable`, including callback, control,
  recovery, and previous evidence. Cursor cleanup quarantine is included.
- [x] Separate eviction from retry eligibility: authentication/configuration,
  capacity exhaustion, transport loss, lock timeout/deadlock, and ambiguous
  write/commit outcomes are different decisions. `HY000` alone is insufficient;
  neither 503 nor `Retry-After` establishes that replay is safe. Capacity
  exhaustion is not categorically permanent or automatically retryable.
- [x] Update the public troubleshooting matrix, focused tests, API manifest
  when signatures change, changelog, upgrade notes, and ADR-009 as required.

Keep classification application-owned; do not add a portable retry classifier.
Use the [security checklist](../maintainers/security-review-checklist.md) and
[ADR-009](../adr/009-exception-evidence-and-redaction.md).

Focused coverage adds
[ConnectionFailureEvidenceTest](../../tests/Unit/ConnectionFailureEvidenceTest.php)
and extends
[QueryExecutionExceptionTest](../../tests/Unit/QueryExecutionExceptionTest.php)
and [ConnectionLifecycleTest](../../tests/Unit/ConnectionLifecycleTest.php);
the consumer static-analysis fixture asserts the new properties. The
troubleshooting matrix, worker/transaction guides, upgrade notes, changelog,

Validation passed: `composer check` (698 tests / 2,161 assertions), line and

### W3 — Worker integration, session hygiene, and observation

Publish an executable framework-free ownership example, with a FrankenPHP
integration recipe that uses the accepted W1/W2 contract. Keep the client
framework/container outside core. The example must make request entry,
lazy acquisition, work, failure handling, and `finally` cleanup visible.

Status: complete for the library workstream, 2026-09-18. See
[W3 validation evidence](../evidence/0.8-worker-lifecycle.md) for the tested
source, commands, results, and qualification limits.

Acceptance:

- [x] Cache-only requests open no database connection. Models participating in
  one unit share a pinned connection; a second lazy model cannot trigger
  replacement during an existing transaction or after an earlier model has
  acquired its owner. New requests do not retain old models/builders/cursors.
- [x] Reuse, if accepted, occurs only after verified cleanup at the request
  boundary. Test early returns, thrown `Throwable`, handled HTTP errors,
  partially consumed streams, and shutdown with outstanding resources.
- [x] Reapply required initialization on every replacement before publishing
  it. Restore temporary session changes in `finally`; if restoration fails,
  evict the session and preserve the original failure. Test a report request
  followed by an ordinary request on the same worker, including report failure.
- [x] Distinguish connect timeout, server idle timeout, statement limit,
  transaction/lock timeout, and transport/read timeout. Do not advertise one
  portable deadline or assume a SELECT limit bounds writes/commit.
- [x] Use a monotonic elapsed-time source for idle policy. Account for direct
  PDO work, transaction controls, failed statements, and delayed cursor fetches
  being absent from successful-query observations. An idle threshold is a
  policy, not a liveness guarantee; document server/proxy configuration inputs.
- [x] Separate primary/read lifecycle state. Define whether an uncertain
  failure requires one or both holders to be evicted; do not reconnect an
  unused role solely to discard it. Preserve application routing and
  authoritative-read requirements.
- [x] Record bounded connection creation/replacement/failure counters,
  role/reason labels, active cursor/transaction leaks, and recovery outcomes
  without credentials, bindings, unbounded query history, or automatic logging.
  Avoid an always-on ping per query. Measure acquisition and initialization cost.
- [x] Decide OBS-1 explicitly. If a lifecycle observer ships, prove immutable,
  redacted, non-interfering events, disabled-path cost, and observer failure
  isolation; query observers must not reconnect as a side effect.

The session timeout distinction is engine-specific: MariaDB documents seconds,
scope, and limitations for
[max_statement_time](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/aborting-statements);
MySQL documents a millisecond limit for read-only SELECTs under
[max_execution_time](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html#sysvar_max_execution_time).
MariaDB's [wait_timeout documentation](https://mariadb.com/docs/server/server-management/variables-and-modes/server-system-variables#wait_timeout)
describes session idle expiry. Verify effective session settings in probes.

Update the [worker guide](../guides/concurrency-and-workers.md),
[transaction guide](../guides/transactions.md),
[observation guide](../guides/observability.md), and relevant examples together.
The consumer must separately adopt its request cleanup, timeout restoration,
and error-handler changes before the integration can be called qualified.

Coverage adds the executable
[worker request lifecycle example](../../examples/worker-request-lifecycle.php)
with its application holder/request-scope classes, executed by
`composer examples:check`, and the direct
[session-hygiene probe](../../tools/database-probes/session-hygiene.php), which
the service runner executes for both direct engines in all four
prepare/buffering profiles. The worker, transaction, and observation guides and
the upgrade notes record the recipe, the OBS-1 decision, and the
engine-specific timeout boundaries.

Validation passed: `composer check` (703 tests / 2,171 assertions), line and
branch coverage gates (95.75% line and 92.46% branch overall; 97.00% compiler
line and 92.04% compiler branch), SQLite probes, and the full direct/proxy
service matrix (67 reports, 928 passed and 241 observed outcomes, no failed
observations; MariaDB 11.8.8, MySQL 8.0.46, ProxySQL 3.0.1, MaxScale
23.02.17-2). The eight new session reports each passed 16 observations.
MariaDB bounded both `SELECT` and DML under `max_statement_time` (`1969`);

### W4 — Post-Pixie interoperability and focused modernization

Build small synthetic fixtures from the observed patterns; do not import the
private application or rewrite historical migration evidence. The consumer has
static analysis but no automated backend test suite, so a green library suite
alone is insufficient adoption evidence.

Acceptance:

- [ ] Characterize lazy connection injection and two-model transactions through
  the public API, including nested failure, rollback, same-owner row locks,
  no query on cache-only paths, and terminal non-mutation.
- [ ] Cover `insert()` affected rows versus `insertGetId()` string IDs,
  adapter boolean write returns, zero-row updates/deletes, nullable results,
  object/associative rows, aggregates, and rejected value types.
- [ ] Review raw upserts, ignored duplicates, batch column ordering, chunk
  boundaries, bind-count/payload limits, oversized single rows, and partial
  batch failure. Preserve explicit caller-owned atomicity; do not promise
  atomicity across chunks outside a transaction.
- [ ] Test generated IDs immediately on the same session after vendor-specific
  insert/upsert, including the existing-row case, with direct-engine evidence.
  Replacement must not occur between the write and ID read. Do not infer ID
  safety or duplicate behavior from SQLite or affected-row counts alone.
- [ ] Test grouped predicates, aliases, empty lists, joins, pagination/order,
  deferred raw execution, and exact SQL/binding order for representative shapes.
  Review dynamic identifiers separately from bound values.
- [ ] Reconcile synthetic answer-save versus completion races, duplicate
  submissions, and failure after dispatch. Unique keys, authorization,
  transaction locks, and application ordering stay consumer-owned; upsert
  alone is not evidence of end-to-end idempotency.
- [ ] Add public-consumer static-analysis coverage for accepted APIs and run
  the backend's PHPStan and representative development endpoint checks during
  adoption. Preserve response keys/types and existing business behavior.
- [ ] Update migration/upgrade guidance with the demonstrated pitfalls. Keep
  raw SQL as the narrow solution unless a typed feature has accepted semantics
  for every declared engine and a separate scope decision.

Prefer [existing consumer fixtures](../../tests/Fixtures/Consumer/), compiler
goldens, [application testing tools](../guides/testing-applications.md), and
maintained probes. Narrow typing/resource fixes discovered here may enter
scope with evidence; blanket model rewrites, dependency upgrades, PHP-floor
changes, and application business refactors do not.

### W5 — Transaction cost without lost guarantees

Measure the root `SAVEPOINT` / `RELEASE SAVEPOINT` pair, nested scopes, commit,
connection acquisition, and session initialization separately. Compare with
the immutable `v0.7.0` baseline using the existing
[benchmark method](../maintainers/benchmarking.md). Consumer query-count/load
notes motivate this work but do not establish library-attributable savings.

- [ ] Use controlled PDO call-count assertions and direct MariaDB/MySQL
  workloads for successful root/nested writes and failures. Record latency,
  statement/control counts, connection churn, and correctness gates.
- [ ] Preserve external-transaction rejection, implicit-commit/ownership-loss
  detection, begin/commit/rollback recovery evidence, cursor rejection, and
  quarantine. Exercise relevant proxy session behavior independently.
- [ ] Record D5: retain cost, optimize with equivalent guarantees, or propose
  an explicit contract change through
  [ADR-008](../adr/008-transaction-ownership-and-savepoints.md). No guard is
  removed or disabled by default merely to improve a benchmark.

## Execution order and acceptance matrix

1. Reproduce and characterize the existing library/consumer boundary with
   synthetic fixtures. Resolve D1–D3 before new public lifecycle behavior.
2. Implement W1/W2 in focused changes with their tests, ADRs, API review, and
   documentation. Build W3 against that accepted contract.
3. Complete W4 consumer characterization and adopt the recipe in a development
   consumer checkout. Record D4/D5; pursue W5 optimization only if justified.
4. Run direct/proxy fault probes and an actual FrankenPHP worker rehearsal;
   then certify the candidate and prepare release finalization.

| Scenario | Required evidence | Pass condition |
| --- | --- | --- |
| Fresh/lazy acquisition and warm reuse | Unit/application fixture; real worker | No connect on cache-only work; one owner per role/unit; documented initialization only. |
| Idle expiry and abrupt loss | Direct MariaDB/MySQL; relevant proxy paths with direct controls | Original failure preserved; explicit replacement lets a later unit succeed; no endless dead-handle reuse or replay. |
| Failed connection construction/bootstrap | Synthetic PDO shapes plus disposable unavailable target | Safe diagnostic evidence, no half-initialized cached connection, no unbounded reconnect loop. |
| Loss during statement/commit or rollback failure | Controlled PDO; live fault injection and reconciliation | Outcome uncertainty stays visible; no callback/statement replay; next unit gets a fresh owner. |
| Quarantine without a connection-loss code | Transaction/cursor failure seams; consumer handler fixture | Unusable connection evicted even when message matching would miss it. |
| Cursor, external transaction, stale model/builder/PDO | Lifecycle/state matrix; SQLite and direct engines where relevant | Cleanup/invalidation follows the accepted contract; old artifacts never bind to a new owner. |
| Session contamination and multiple models/roles | Consecutive worker requests; direct session inspection | Ordinary request settings restored, transaction connection identity stable, roles isolated. |
| Migrated writes and save/completion races | Compiler bindings; direct execution; synthetic consumer endpoints | Expected IDs/types/rows and acknowledged writes reconciled; no accidental change in atomicity. |
| Sustained worker use | Same-worker failure/recovery followed by multi-worker soak | Bounded connection count and memory, no accumulating cursors/transactions, recovery across repeated idle periods. |

Use short disposable session timeouts instead of changing production globals.
Extend the maintained [database probes](../../tools/database-probes/), including
the existing [ambiguous-write probe](../../tools/database-probes/ambiguous-write.php)
and a direct reconciliation control. A single successful query or a mock
cannot qualify network, worker, or proxy behavior. Record proxy retry/replay
settings and prepared/buffered profiles with each claim.

The worker rehearsal must pin/report the actual PHP ZTS, PDO client,
FrankenPHP, and engine versions; exercise classic request mode as a control;
force consecutive requests through the same worker; and include a one-hour
mixed-workload soak with idle gaps, replacement failures, and recovery. Set
latency/memory/connection budgets from the baseline before comparison. Worker
recycling is an operational fallback, not a substitute for passing lifecycle
tests. Unavailable environments remain pending, never inferred passes.
