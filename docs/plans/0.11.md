# 0.11.0 release plan

Planning started on 2026-11-20 from `v0.10.0` (`450bb9b` on `master`). Use the
[0.10.0 release review](../evidence/0.10-candidate-review.md) as the historical
baseline for quality, database behavior, and package checks. Qualifying stable
PHP 8.6 is the first milestone and a release gate. Feature and optimization work
depends on evidence from the investigations below.

## 1. Qualify PHP 8.6

PHP 8.6.0 was released on 2026-11-19. Review the migration guide and changelog
against library code, tests, and maintained tools. PHP 8.6 adds form feed to
the default `trim()` character set. Compare validation of comparison operators
and empty SQL across PHP 8.2 and 8.6 before proposing any change to that behavior.
[PHP changelog](https://www.php.net/ChangeLog-8.php) ·
[PHP 8.6 migration guide](https://www.php.net/manual/en/migration86.php) ·
[PHP 8.6 incompatible changes](https://www.php.net/manual/en/migration86.incompatible.php)

- Add a PHP 8.6 compatibility job with `pdo_sqlite` and `pdo_mysql`. Verify that
  the pinned CI installer actually supplies stable PHP 8.6, and record the
  exact versions of PHP, PDO drivers, and linked SQLite. Run the locked dev
  toolchain, PHPUnit with deprecations treated as failures, executable examples,
  and the SQLite behavior, execution, and transaction probes. Exercise an
  independent no-dev consumer on the same runtime.
- Run the maintained direct-engine PDO probes on PHP 8.6 against the current
  MariaDB and MySQL fixtures, covering native and emulated prepares and
  buffered and unbuffered results. Review binding types, generated IDs, cursor
  cleanup, and transaction ownership alongside PHP 8.2 results. Capture any
  PHP 8.6-specific difference in a focused test or probe.
- Keep CI coverage for PHP 8.2–8.5, the PHP 8.2 lowest-dependency lane, and the
  PHP 8.2 syntax and analysis targets. Resolve tool-only incompatibilities at
  the tooling layer while preserving the `^8.2` package constraint. Use the
  established coverage runtime until PCOV and Xdebug have qualified builds.
  Publish PHP 8.6 compatibility after the stable-runtime checks pass.

## 2. Target code quality work

- Start with the PHP 8.6 findings and revisit child snapshots, cursor handoff
  and cleanup, and exception and observation behavior from the previous
  release. Turn verified gaps into focused regression checks using the
  existing controlled PDO seams and live SQLite fixtures.
- Review PHPStan level 9, independent consumer inference, and CodeScene for
  the paths touched by each change. Refactor where a review finding or a proven
  bug gives a concrete reason. Verify exception type and redaction, terminal
  state, and failure ordering wherever the affected code owns those behaviors.
- Use `composer check` and the current coverage gates for candidate acceptance.
  Line thresholds are 90% overall and 95% for compilers. Branch thresholds are
  80% overall and 90% for compilers. Review public API drift and explain any
  intentional consumer-visible change in its supporting documentation.

## 3. Evaluate structured `EXISTS` and `NOT EXISTS`

The proposed feature is a structured way to filter reads by the presence or
absence of related rows. Use a synthetic case that lists customers with at
least one paid order, and a companion case that finds customers without one.
These cases exercise correlation, a bound status, and one result row per
customer even when several orders qualify. Confirm a representative consumer
need and approve the public shape before implementation, following
[ADR-016](../adr/016-maintainer-led-scope-control.md).

- Start with read-side `WHERE` and nested condition groups. Decide the public
  spelling and AND/OR composition after reviewing the call sites. Defer
  `HAVING`, join conditions, and write predicates until each has a use case and
  defined semantics. Check update/delete validation explicitly because they
  share the builder's predicate state.
- Use the existing same-connection child snapshot boundary. Preserve child
  SQL and ordered typed bindings, including their position between parent
  bindings. Reject cross-connection and locked children before parent mutation.
  Test child and parent mutation after attachment, clone isolation, and stable
  compile and read terminals, including logical `count()`.
  [Child locking policy](../adr/026-locked-child-queries.md)
- Verify both predicates with zero, one, and multiple matching rows, nullable
  data, correlated references, and grouped predicates. Require exact compiler
  fixtures for each dialect, live SQLite at its minimum, and direct MariaDB
  and MySQL probes at the maintained minimum/current versions. Use the direct
  results as controls for the maintained proxy fixture checks.
  [MariaDB](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/subqueries/subqueries-and-exists) ·
  [MySQL](https://dev.mysql.com/doc/refman/8.0/en/exists-and-not-exists-subqueries.html) ·
  [SQLite](https://www.sqlite.org/lang_expr.html#the_exists_operator)
- If accepted, document the supported contexts, add a runnable example, and
  review the generated API manifest, changelog, and any applicable ADR or
  upgrade entry. Defer the feature if the consumer case or portable scope
  remains unresolved. Defer broader SQL composition and new engine targets to
  their own scope reviews.

## 4. Measure and improve efficiency

- Establish a fresh comparison against `v0.10.0` with both source orders and
  identical-source noise controls. Run both sources on the same PHP/PDO/SQLite
  configuration with timing instrumentation disabled. Compare runtimes in
  separate runs when investigating an upstream PHP effect.
- Start with large `IN` list and batch-insert compilation, then review wide
  associative hydration and cursor drain. Use the existing component controls
  to localize repeatable time or allocation costs. Select one hotspot for an
  initial optimization based on those results.
- Require exact SQL and ordered typed binding parity for compiler work, and
  equivalent results and resource lifetimes for execution work. Keep a change
  when the measured improvement repeats beyond noise on the full operation
  and the paired regression gate and reference soak pass. Record the workload,
  runtime, time or allocation delta, and repeatability. Retain current code
  when the change does not clear those checks.
  [Benchmark method](../maintainers/benchmarking.md)

## Candidate and release gates

Start with a PHP 8.6 baseline and a comparison against `v0.10.0`. Address
confirmed compatibility and correctness issues first. Review the query feature
scope and performance measurements before deciding which of those changes enter
the candidate.

Certify the candidate using the maintained runtime matrix, lowest dependencies,
actual SQLite 3.39.2, minimum/current direct and proxy fixtures, coverage,
focused regression tests, dependency audit, security review, paired benchmarks
and soak, and independent no-dev archive consumers.
Retain reports with the exact candidate revision and fixture versions. Apply
the established PHP 8.2 and database support floors throughout qualification.
[Support policy](../../SUPPORT.md) ·
[Database support](../reference/database-support.md) ·
[Release process](../maintainers/release-process.md)

At release finalization, record shipped changes and migration impact, link
the qualification evidence, and retire this plan. Publication and tag/dist
provenance follow the maintained release process.
