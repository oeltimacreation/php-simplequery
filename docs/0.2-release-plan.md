# `0.2.0` release plan

Status: in progress; correctness and resource-safety packages `0.2-B`, `0.2-C`,
and `0.2-D` completed successfully on 2026-07-26.
Historical baseline: [`v0.1.0` performance and stability evidence](evidence/v0.1.0-performance-baseline.md).

Detailed audit: [`post-0.1 audit and remediation plan`](post-0.1-audit-and-remediation-plan.md).

## Release intent

`0.2.0` is a correctness, resource-safety, performance-evidence, and type/test
hardening release. ZeroVer permits documented compatibility changes, but the
release should still prefer the smallest behavior correction and avoid public
API expansion without a demonstrated use case.

The release has four outcomes:

1. scalar terminals never silently consume a multi-row aggregate shape;
2. uncertain cursor or transaction state is never exposed as safely reusable;
3. performance claims are backed by a reproducible timing, memory, soak, and
   profiling harness with a preserved `v0.1.0` comparison baseline;
4. branch coverage, public PHPDoc contracts, and high-risk behavioral tests
   match what documentation claims.

## Scope

### Required correctness and resource-safety work

- Reject grouped/HAVING non-count scalar aggregates. Decide and document
  `distinct()` aggregate semantics rather than returning an accidental first
  row.
- Treat `PDOStatement::closeCursor() === false` and thrown cleanup as uncertain
  physical state.
- Preserve fetch/query failure as primary when cleanup also fails.
- Quarantine a connection after uncertain cursor cleanup.
- Fail closed after ambiguous post-dispatch begin/savepoint failures unless
  recovery proves a safe inactive state.

### Required performance work

- Make benchmark setup, warm-up, correctness validation, and measurement
  separate phases.
- Emit raw samples, medians, correctness digests, environment metadata, PHP
  peak allocation, and fresh-process RSS.
- Implement the documented compiler-shape, hydration/cursor, observer, batch,
  transaction, lifecycle, and scheduled soak scenarios.
- Prototype a one-pass associative hydration path that validates rows while
  building only the final result list.
- Optimize only when the baseline comparison proves a meaningful improvement.

### Required quality and type work

- Run Xdebug branch/path coverage in CI and fail when configured branch metrics
  are absent.
- Preserve PCOV as the fast line-coverage job if desired.
- Correct positional binding PHPDoc to lists.
- Type join and condition/HAVING closure parameters for downstream PHPStan.
- Validate public `CompiledQuery` and `QueryExecution` constructor boundaries.
- Add a PHPDoc-generic cursor only if downstream inference improves without a
  runtime class hierarchy or casts.
- Add external-consumer static-analysis fixtures.

### Required tests

- grouped, HAVING, and distinct scalar aggregate shapes;
- cursor false close, dual failure, exhaustion failure, quarantine, and
  destructor behavior;
- post-dispatch begin/savepoint ambiguity;
- null-containing `IN`/`NOT IN` behavior on supported engines;
- oversized integer strings and duplicate/numeric result-column names;
- cursor observation timing and failure semantics;
- MySQL-family connection-policy failure branches;
- minimum/current supported engine fixtures where the strategy claims both.

## Work packages and review order

Each package should remain independently reviewable. Preserve behavior first,
verify, then optimize.

### 0.2-A — Reproducible baseline harness

Deliverables:

- small dependency-free benchmark scenario runner;
- environment and raw-sample JSON envelope;
- subprocess memory/RSS runner;
- correctness digests and AB/BA direct-PDO controls;
- CI artifact retention and documentation that distinguishes implemented from
  planned scenarios.

Gate:

- the runner reproduces the preserved `v0.1.0` workload shape and correctness
  results;
- the identical finalized runner is executed against both the `v0.1.0` source
  and the current `0.2.0` candidate in fresh, preferably interleaved processes;
- every timing is rejected when its correctness assertion fails;
- profiler/coverage extensions are demonstrably off during timing.

### 0.2-B — Aggregate shape correction

Status: **completed successfully (2026-07-26)**.

Deliverables:

- failing tests demonstrating grouped/HAVING scalar ambiguity;
- smallest compiler or terminal validation that rejects unsupported shapes;
- explicit `distinct()` policy;
- guide, changelog, and upgrade note.

Gate:

- no scalar aggregate terminal can silently return one row from a multi-row
  logical result;
- ordinary filtered/joined aggregates and grouped `count()` remain correct;
- terminals do not mutate builder state.

Result: all deliverables and gate conditions passed through compiler and
SQLite execution coverage, documentation, upgrade guidance, and changelog.

### 0.2-C — Cursor cleanup quarantine

Status: **completed successfully (2026-07-26)**.

Deliverables:

- one idempotent cursor finalization path;
- false-return and exception handling for physical close;
- deterministic primary/cleanup exception precedence;
- connection unusable/quarantine transition;
- controlled unit matrix and unbuffered direct/proxy verification.

Gate:

- uncertain physical statement state cannot execute another query or complete
  a transaction;
- a fetch failure is not hidden by cleanup failure;
- destructor cleanup never throws;
- SQLite, native unbuffered MariaDB/MySQL, ProxySQL, and MaxScale probes pass.

Result: all deliverables and gate conditions passed. Controlled tests cover
false close, thrown close, dual fetch/close failure, exhaustion, quarantine,
idempotence, and non-throwing destruction; the full disposable service matrix
passed.

### 0.2-D — Transaction ambiguity hardening

Status: **completed successfully (2026-07-26)**.

Deliverables:

- post-dispatch begin/savepoint fault injection;
- verified rollback/recovery where state can be proven;
- quarantine where it cannot;
- transaction failure documentation and changelog entry.

Gate:

- every uncertain transaction-control outcome is fail-closed;
- successful and ordinary callback-failure paths preserve identity and existing
  semantics;
- the complete live transaction matrix passes.

Result: all deliverables and gate conditions passed. Fault injection covers
pre- and post-dispatch begin/savepoint failures, verified begin recovery, and
quarantine when physical/savepoint state cannot be proven; the live direct and
proxy transaction matrix passed.

### 0.2-E — Associative hydration experiment

Deliverables:

- one-pass validated associative full hydration;
- optional no-copy associative cursor experiment measured separately;
- comparison report against the accepted `v0.1.0` baseline;
- retained invalid-row, exception, observer, and cleanup behavior.

Same-workstation acceptance gates for the 100,000-row reference fixture:

- reduce associative `get` PHP peak from 92.0 MiB to at most 70 MiB, or within
  1.30× the same-run direct PDO peak;
- treat an associative `get` time ratio of 1.50× or lower as an optimization
  goal, not a release blocker when the hard memory gate passes;
- introduce no greater than 10% median regression in object hydration or either
  cursor mode under repeated paired AB/BA measurements;
- preserve exact rows and result digest.

The memory requirement and correctness are hard gates; the time ratio is an
aspirational target. These are not topology-independent CI limits. If the
prototype cannot pass the memory gate without weakening validation or adding
complexity, discard it and retain the baseline implementation.

### 0.2-F — Coverage, contracts, and missing behaviors

Deliverables:

- Xdebug branch gate in CI;
- corrected public list/callback/generic PHPDoc where useful;
- boundary validation tests;
- high-risk path tests listed in scope;
- minimum/current engine matrix aligned with documentation.

Gate:

- overall branch coverage remains at least 80%;
- compiler branch coverage remains at least 90%;
- configured branch metrics cannot be silently absent;
- no arbitrary path-coverage percentage is introduced;
- PHPStan level 9 passes internally and against the external-consumer fixture.

### 0.2-G — Release comparison and evidence

Deliverables:

- final paired `v0.1.0` versus `0.2.0` correctness/performance/memory comparison
  produced by the same finalized harness;
- coverage, direct/proxy, soak, dependency, and no-dev consumer artifacts;
- dated changelog, upgrade guide, support/benchmark docs, and any required ADR;
- release branch evidence described by the release process.

Gate:

- all correctness and resource-safety blockers are closed;
- no greater than 10% median regression in the named scorecard scenarios
  survives repeated paired AB/BA measurement unless an explicit release waiver
  records the tradeoff and supporting evidence;
- compiler scaling remains approximately linear;
- soak tests show no retained-memory or descriptor growth;
- `composer validate --strict`, `composer audit`, `composer check`, line/branch
  coverage, direct/proxy probes, and clean no-dev installation pass.

## Explicit non-goals

`0.2.0` will not add:

- compiler or prepared-statement caches;
- global/persistent connection management;
- retries, reconnects, or transaction replay;
- automatic batch chunking;
- a benchmark framework dependency;
- a dialect/plugin platform;
- a cursor runtime class hierarchy solely for static analysis.

## Release policy

`0.2.0` follows the normal `release/0.2.0` branch and required-CI process. No
tag is created until the final comparison record, upgrade documentation, and
all release evidence are complete. Published `v0.1.0` evidence remains
immutable; corrections are recorded in the new release rather than rewriting
the old baseline.
