## Reproduction

```bash
# FrankenPHP classic/worker rehearsal with a short soak.
bash tools/worker-rehearsal/run.sh

# One-hour gate soaks.
REHEARSAL_RUN_ID=soak-mariadb REHEARSAL_ENGINES=mariadb REHEARSAL_PORT_BASE=18080 \
    REHEARSAL_KEEP_SERVICES=true REHEARSAL_SOAK_SECONDS=3600 bash tools/worker-rehearsal/run.sh
REHEARSAL_RUN_ID=soak-mysql REHEARSAL_ENGINES=mysql REHEARSAL_PORT_BASE=18090 \
    REHEARSAL_KEEP_SERVICES=true REHEARSAL_SOAK_SECONDS=3600 bash tools/worker-rehearsal/run.sh

# Direct session and proxy session probes.
php tools/database-probes/session-hygiene.php mariadb
php tools/database-probes/proxy-session.php proxysql
php tools/database-probes/proxy-session.php maxscale
bash tools/database-probes/run-services.sh
```

The rehearsal app is synthetic (`tools/worker-rehearsal/`): it owns its holder,
uses the documented lazy per-role lifecycle, and exposes cache, health, read,
write, transaction, report, failure, construction-failure, kill, and counter
routes. The worker config runs a single thread matched to every request so
consecutive requests share one application instance; the classic config is the
per-request control. Generated reports and version captures remain ignored
under `tools/worker-rehearsal/results/<run-id>/`.

## Worker rehearsal results

Both engines passed the classic control and the single-worker scenarios:
cache-only acquisition, warm reuse and session pinning, bound values,
transaction commit, report session restoration, query-failure eviction and
recovery, failed connection construction, proactive idle replacement, abrupt
`KILL CONNECTION` loss and recovery, and cursor ordering. Classic mode created
a fresh session and owner per request; worker mode kept one session across
requests and replaced only at idle/failure boundaries.

The corrected one-hour mixed-workload soak ran concurrently against both
engines and produced identical deterministic counts: 41,450 iterations,
1,658 idle-gap cycles, 414 failure/recovery cycles, 2,077 connection creations,
33,611 units, 33,610 reused units, 829 report restorations, and 417 evictions.

| Soak measure | MariaDB 11.8.8 | MySQL 8.0.46 |
| --- | --- | --- |
| Duration / iterations | 3600 s / 41,450 | 3600 s / 41,450 |
| Request errors | 0 | 0 |
| Cleanup / restore failures | 0 | 0 |
| Memory growth across 2,073 samples | 0 B | 0 B |
| Idle cycles / failure cycles | 1,658 / 414 | 1,658 / 414 |
| Connection creations | 2,077 (budget `idle + failures + 5`) | 2,077 (same budget) |
| p95 read / write / transaction | 1.4 / 1.3 / 2.1 ms | 1.0 / 2.0 / 2.6 ms |
| p95 cache | 0.4 ms | 0.4 ms |

An earlier soak run failed because the rehearsal report workload evaluated
`SLEEP` per table row, so the synthetic table outgrew even the raised statement
limit. The harness was corrected to evaluate `SLEEP` once and to record bounded
soak error details and final counters; the table above is the corrected run.
The corrected 120-second cross-check on both engines recorded zero request
errors and the same bounded connection formula before the gate soaks ran.

## Direct and proxy session observations

The direct session-hygiene probe passed in all four prepare/buffering profiles
(MariaDB `max_statement_time` `1969`, MySQL `max_execution_time` `3024`; MySQL
bounded `SELECT` only while a non-`SELECT` `DO SLEEP` completed). The proxy
probe passed in all four profiles for both proxies as well:

| Observation | ProxySQL 3.0.1 | MaxScale 23.02.17-2 |
| --- | --- | --- |
| Backend session identity over sequential statements | Stable | Stable |
| Bound values, prepared reuse, cursor ordering | Correct | Correct |
| Transaction commit visible / rollback hidden | Passed | Passed |
| User variable round trip | `42` | `42` |
| `SET SESSION wait_timeout = 1` forwarded | Native/emulated profiles differ; not forwarded in emulated-prepare profiles | Forwarded |
| Server-side idle loss after 2 s | `2006` | `1927` |
| Application-level recovery | Passed | Passed |

The idle-loss code difference (`2006` direct/ProxySQL, `1927` MaxScale) and the
profile-dependent ProxySQL session-variable handling confirm that proxy session
policy is configuration-sensitive. Applications must keep idle/eviction
decisions evidence-based and must not hard-code one idle-loss code or expect
transparent proxy reconnect.

The full service matrix passed with 75 reports (984 passed and 273 observed
outcomes, no failed observations) across MariaDB 11.8.8, MySQL 8.0.46,
ProxySQL 3.0.1, and MaxScale 23.02.17-2 in all four prepare/buffering profiles,
including the eight direct session-hygiene reports and the eight proxy-session
reports. `composer check` passed on the candidate; the line and branch coverage
gates recorded in the W3 evidence remain valid because no `src/` file changed
after that run.

## Consumer static-analysis and holder adoption

In a temporary copy of the internal consumer at `bf102fc6` (the private
checkout is read-only and untouched):

- the consumer's PHPStan level-5 analysis passes unmodified against the
  candidate package (`dev-feature/0.8-candidate`, reference `65bf8ee`);
- a focused migration slice replaced `microtime(true)` with monotonic
  `hrtime(true)` seconds, replaced the internal `transactionDepth()`/
  `hasActiveCursors()` check with `isReusable()`, and replaced the suppressed
  strict `close()` with `discard()`;
- PHPStan level 5 still passes, and a live smoke of the consumer's
  `DbConnectionHolder` against the disposable MariaDB/MySQL fixtures passed:
  acquire, idle replacement at the configured threshold, observed idle loss
  (`2006` MariaDB, `4031` MySQL), `discard()`, and successful recovery through a
  new connection.

This demonstrates that the accepted `0.8.0` lifecycle surface removes the
consumer's dependency on internal state without breaking its static analysis.
The private checkout has not been modified; staged adoption, database-backed
endpoint/race checks, HTTP redaction verification, and deployment rollout remain
W4/W6 work, and the follow-up read-only source audit is recorded in the
[consumer adoption analysis](0.8-consumer-adoption.md).

## Limits and remaining work

- The rehearsal uses a synthetic application and disposable fixtures. It does
  not qualify a production FrankenPHP topology, proxy configuration, or the
  private consumer's endpoints, business flows, or credentials.
- Soak results measure the synthetic mixed workload on this host; they are not
  a capacity claim, benchmark comparison, or latency budget for deployments.
- W4 consumer endpoint/race checks and HTTP diagnostic redaction, W5's
  transaction-cost decision, hosted CI/runtime lanes, clean no-dev package
  certification, minimum-version fixtures, and release-finalization checks
  remain open release gates. No support claim is created by this record.
