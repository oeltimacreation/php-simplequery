# `0.6.0` Phase 3 execution, hydration, and resource efficiency evidence

Date: 2026-08-24

Release baseline: immutable `v0.5.0`
(`902a18037303d7e28cefcad6859c157b98e2d05b`)

Candidate: `feature/0.6-candidate` working tree based on
`184515c5aea534a97eb39a6ed880b3f86a24425c`

Decision: accept one isolated transient-allocation reduction for associative
row validation. Retain the existing statement-cleanup and observer paths. Add
dimensional full-result/cursor memory evidence and live buffered/unbuffered
engine controls. No hydration-latency or product-wide memory claim is made.

## Scope and method

The local evidence host used Linux x86-64, PHP 8.4.24 CLI, PDO SQLite 3.45.1,
disabled CLI OPcache/JIT, Xdebug timing mode off, and PCOV disabled. Every CI
operation used a fresh PHP worker, three warm-ups, nine timed samples,
correctness digests, per-invocation transient allocation, RSS, retained growth,
and file-descriptor evidence.

The Phase 3 attribution surface added:

- equivalent eighteen-column `array_keys()` and direct key-iteration controls;
- retained full results and non-retaining cursors at 100, 1,000, and 10,000
  three-column rows with 256 payload bytes per row;
- single and redundant statement-close controls over 500 terminal calls;
- disabled, no-op, bounded-recording, and failing observers over 500 calls at
  one and fifty bindings; and
- direct-PDO/SimpleQuery full-result and cursor controls on native buffered and
  unbuffered MariaDB, MySQL, ProxySQL, and MaxScale connections.

Five immutable-baseline profiles established the candidate costs before the
single product edit. The final 36-scenario, 95-operation suite then ran five
identical-candidate controls and complete `v0.5.0` comparisons in both source
orders. Raw release-comparison JSON remains disposable under `/tmp`; live
engine and probe reports remain ignored generated artifacts.

## Associative key-validation decision

The released validator materialized `array_keys($row)` before checking each
key. The equivalent direct-iteration control checked the key while traversing
the same representative row and returned identical key-count and last-key
facts.

| Control | Five-run median range | Transient allocation |
| --- | ---: | ---: |
| `array_keys()` validation | 6.103124–6.291037 ms | 696 B |
| Direct key iteration | 5.571406–5.646122 ms | 376 B |

The isolated transient reduction is 46.0%, clearing the allocation rule in a
repeatable exact-output control. Time improved by 7.7–11.4% across the five
runs and does not clear the timing rule consistently. `Executor` therefore
uses direct iteration, but this phase makes no hydration-speed claim.

Complete result operations confirm the allocation is per validation rather
than a reduction in the retained result itself. Narrow full hydration moved
from 568,960 to 568,744 transient bytes and wide full hydration from 2,303,784
to 2,303,088 bytes. Narrow/wide first rows moved from 4,968/13,520 to
4,752/12,824 bytes. The 10,000-row full result moved from 7,630,720 to
7,630,504 bytes. Its median changed by only -5.6% and -5.3% in the two source
orders, below the release threshold.

PDO still collapses duplicate aliases before SimpleQuery receives the row, so
the documented last-value behavior remains unchanged. Full, first, and cursor
associative terminals continue to reject numeric keys, while object terminals
continue to accept numeric property names. Focused live SQLite coverage also
checks a reusable 32-column result and unchanged terminal state.

## Statement cleanup and cursor ownership audit

The audit retained the existing implementation. A 500-call direct-PDO control
closed each statement once; its paired control closed the same statement
twice. Four of five identical-candidate medians overlapped at approximately
0.54–0.80 ms, while one redundant-close sample group was a 1.62 ms host
outlier. The SimpleQuery terminal remained stable at 1.310796–1.368015 ms.
There is no repeatable benefit outside the 0.530881 ms host floor, so the
cleanup path was not changed.

The executable audit covers these state transitions:

| Path | Preserved outcome |
| --- | --- |
| Successful non-cursor terminal | Result is produced, the statement is closed, then one successful observation is emitted. |
| Fetch/result failure | The primary failure is translated or retained, one failed observation is emitted, and final cleanup is best effort. |
| Successful result plus throwing cleanup | Cleanup becomes the reported PDO-backed query failure and is observed once as failed. |
| Result failure plus throwing cleanup | The result failure remains primary; cleanup cannot replace it. |
| Cursor hand-off | The cursor registers ownership before the successful hand-off; the statement remains live and connection close is rejected. |
| Natural exhaustion or explicit early close | Physical cleanup is attempted once, cursor ownership is released, and repeated close is idempotent. |
| False/throwing cursor cleanup | The connection is quarantined, active-cursor accounting is released, and the cleanup failure is reported unless an earlier row failure is primary. |
| Destructor fallback | Cleanup is attempted without throwing from the destructor; a cleanup failure still quarantines the connection. |

The focused unit and live SQLite tests cover success, operation failure,
cleanup failure, dual failure, hand-off, exhaustion, generator cleanup, early
close, idempotence, quarantine, and connection reuse/rejection. No cursor
ownership, transaction, exception-evidence, or resource-ownership rule changed.

## Observer cost and behavior decision

Both source orders used 500 successful query attempts per sample. Candidate
medians were:

| Bindings | Observer off | No-op | Bounded recording | Failing |
| ---: | ---: | ---: | ---: | ---: |
| 1, baseline first | 1.356925 ms | 1.690922 ms | 1.736512 ms | 2.073860 ms |
| 1, candidate first | 1.312464 ms | 1.708031 ms | 1.736535 ms | 2.334298 ms |
| 50, baseline first | 16.914028 ms | 18.644037 ms | 18.483371 ms | 18.964095 ms |
| 50, candidate first | 16.930932 ms | 18.806690 ms | 18.345482 ms | 19.070970 ms |

The failing observer was a one-order review signal only and did not reproduce
in the opposite order. No observer implementation change is accepted. A null
observer still avoids timing and observation-value construction; enabled
observers receive SQL, parameter types, timing, outcome, affected rows when
meaningful, driver, label, and transaction depth only after the attempt. They
receive no binding values. A throwing observer remains suppressed on both
successful and failed database outcomes, and bounded recording retains its
ordered capacity and clear semantics.

## Full-result and cursor memory scaling

All four SQLite operations returned the same count, ID sum, payload-byte count,
and boundary IDs. Full-result transient allocation grew with the retained list,
while streaming allocation remained constant:

| Rows | PDO full | SimpleQuery full | PDO cursor | SimpleQuery cursor |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 76,904 B | 80,424 B | 2,568 B | 4,840 B |
| 1,000 | 757,224 B | 760,744 B | 2,568 B | 4,840 B |
| 10,000 | 7,626,984 B | 7,630,504 B | 2,568 B | 4,840 B |

This establishes PHP-side result retention versus consumption. It does not
claim that every driver streams from the server: PDO buffering remains a
connection property.

The live native-prepare controls used 1,000 three-column rows and shared one
correctness digest across MariaDB, MySQL, ProxySQL, and MaxScale:

| Mode | PDO full | SimpleQuery full | PDO cursor | SimpleQuery cursor |
| --- | ---: | ---: | ---: | ---: |
| Buffered | 735,088 B | 738,032 B | 172,632 B | 174,040 B |
| Unbuffered | 604,784 B | 607,728 B | 42,328 B | 43,464 B |

The buffered cursor remains lower than a retained full result but includes
driver-buffer cost. The unbuffered controls reduce that cost while occupying
the connection until exhaustion/close. Proxy numbers are interpreted only
beside the matching direct-engine mode; they do not create an independent
proxy performance claim.

## Final gates

Five identical-candidate runs established a 0.530881 ms absolute timing floor.
Both final source orders accepted all 36 scenario and 95 operation digests.
Baseline-first flagged only `lifecycle/simplequery`; candidate-first flagged
`compiler_batch_insert_high/binding_normalization_control`,
`observer/observer_failing`, and
`execution_cleanup/pdo_redundant_close_control`. Their actionable intersection
is empty.

Across the final candidate comparisons, maximum transient allocation was
7,630,504 bytes, maximum worker RSS was 52,121,600 bytes, retained growth was
zero, and every descriptor delta was zero. Four concurrent CI soak workers
also retained zero bytes and zero descriptors.

The complete service run passed:

- SQLite behavior (12 observations), execution (16), and transaction (16);
- MariaDB 11.8.8 and MySQL 8.0.46 native/emulated plus buffered/unbuffered
  behavior profiles (12 observations each), execution (18), and transaction
  (15);
- the same matrix through ProxySQL and MaxScale; and
- all eight native buffered/unbuffered direct/proxy result-memory reports.

Repository validation also passed:

- `composer check`: 455 tests and 1,301 assertions plus lint, the PHP 8.2
  platform gate, PHPStan project/consumer analysis, coding style, public API,
  documentation, examples, and 76 required repository records;
- line coverage: 94.64% overall and 97.00% compiler;
- branch coverage: 91.19% overall and 92.04% compiler; and
- `composer benchmark:soak`: four reference scenarios/five operations with
  zero retained growth and zero descriptor delta.

Phase 3 passes: associative validation clears the isolated allocation rule,
all result/exception/observer/cursor/redaction contracts remain exact, cursor
memory stays bounded in the controlled workloads, and the final suite has no
repeatable unexplained regression. Minimum supported direct-engine versions
remain part of Phase 6 release certification; this phase changes no support
claim.
