# `0.4.0` performance and stability evidence

Date: 2026-08-01

Baseline: `v0.3.0` (`2c5a1f231d12e06410a9fe8050b7a22906014618`)

Candidate: current `feature/0.4-candidate` head (SQ-0441–SQ-0445)

Decision: accept Phase 4. Every refactor preserves exact compiled SQL, binding
order, exception types, and results (correctness parity is enforced by the
benchmark harness before any timing is accepted). Compilation hot-path
allocations are removed at the source level, the paired terminal-path workload
is faster, the SQLite multiprocess lock-contention and busy-timeout probes pass
deterministically, and the memory soak shows flat retained allocation across
long streaming, batch-write, and lifecycle workloads.

## Method and environment

All measurements used PHP 8.4.24 with SQLite 3.45.1, Xdebug timing and PCOV
disabled, fresh subprocess per scenario, and two clean detached worktrees. This
development host was under concurrent load (load average 2.5–3.7 on 16 cores),
so the paired comparisons below were pinned to one CPU core
(`taskset -c 2`) with nine alternating samples and three warm-ups; absolute
values still describe this host only. The authoritative timing gate runs on
the CI benchmark-control job, which now compares `v0.3.0` and the candidate for
the `baseline` suite (PDO controls, ordered-predicate compiles, and the
migration query) and reports operation-level median changes.

## Allocation reductions (deterministic source metrics)

SQ-0441 and SQ-0442 remove allocations that previously happened on every
compile and every terminal call:

| Site | `v0.3.0` | `0.4` candidate |
|---|---|---|
| Dialect compiler allocations per `compile()` | 1 (`CompilerFactory::for()` per compile) | 0 (one compiler cached per connection) |
| Executor allocations per terminal | 1 (`new Executor()` per terminal) | 0 (one executor cached per connection) |
| Deep AST copy in `count()`/`sum()`/`avg()`/`min()`/`max()` | full `ConditionCollection`/`JoinState` tree copy | shallow `copyForCompilation()` sharing read-only condition/join state |
| Deep AST copy in `first()` | full tree copy | shallow `copyForCompilation()` (only the lock state is cloned) |
| `CompilationContext` allocations per non-count scalar aggregate | 2 | 1 |

The full deep `QueryState::copy()` remains for `__clone()` and the `@internal`
`snapshotForCompilation()` test hook, so clone isolation and the testing
toolkit contract are unchanged. `Connection` gained two `@internal` accessors
(`compilerForQueryBuilding()`, `executorForQueryBuilding()`) that lazily cache
the shared stateless compiler and executor; both appear in the regenerated
public API manifest as `compatibility: internal` and are not part of the
public contract.

## Paired medians (pinned host, `v0.3.0` vs candidate)

Positive values are slower; negative values are faster.

| Scenario / operation | Change |
|---|---:|
| `pdo_control_10` (direct PDO control) | -0.7% |
| `pdo_control_100` (direct PDO control) | -2.8% |
| `pdo_control_1000` (direct PDO control) | -1.3% |
| `pdo_control_5000` (direct PDO control) | noisy single sample (-46%; unchanged code path) |
| `compiler_predicates_10` | +3.5% |
| `compiler_predicates_100` | +1.9% |
| `compiler_predicates_1000` | +1.7% |
| `migration_query` (`simplequery` / `pdo`) | +1.7% / -0.5% |
| `compiler_repeated` (20,000 compiles) | +2.4% |
| `read_terminals` (first/count/scalar terminals) | **-27.6%** |

The compile-only scenarios stay inside the 5% gate; the extra `compileSelect()`
step and host noise account for the small positive values, while the retained
allocation in every repeated-compile sample is zero in both trees. The
terminal-heavy `read_terminals` workload (which exercises the shallow snapshot
and the reused executor/compiler) is materially faster. These numbers are
paired evidence, not a portable performance claim; CI repeats the comparison on
an isolated runner.

## SQLite lock-contention stress probes

`tools/database-probes/src/SqliteContentionProbe.php` (wired into
`composer probe:sqlite` as the `sqlite_contention_stress` observation and
exposed standalone as `composer probe:sqlite:contention`) spawns real PHP
subprocesses against a shared file-backed WAL database and verifies:

- `busy_surfaced`: a writer with `busy_timeout = 0` receives SQLITE_BUSY
  (sqlstate `HY000`, driver code `5`) while another writer holds the write
  lock.
- `busy_timeout_resilient`: a writer with a 2000 ms busy timeout blocks on the
  write lock and completes its 50-row transaction after the lock holder
  commits (observed wait ≈ 355 ms).
- `stress_complete`: four concurrent writers each commit 100 disjoint ids;
  the table holds exactly 400 rows with 400 distinct ids (no lost or
  duplicated writes).

The probe passed 5/5 consecutive local runs. The worker uses raw
`BEGIN IMMEDIATE`/`COMMIT` because a WAL-mode deferred-transaction upgrade
returns SQLITE_BUSY immediately instead of honoring `busy_timeout`, and it
retries connection establishment because the SQLite shared-memory recovery
lock is not covered by `busy_timeout`. These are probe-internal mechanics for
the disposable fixture; the library itself does not retry.

## Memory stability soak

The soak suite (`composer benchmark:soak`, reference profile, pinned, 5
samples, 2 warm-ups) now covers repeated compilation, lifecycle loops, a
50,000-row cursor drain, and a 2,000-row `insertMany()` + delete workload.
The benchmark harness records per-operation `allocated_after_sample_bytes`,
`retained_growth_bytes`, and `retained_peak_above_first_bytes`; the runner
fails any soak scenario whose retained allocation grows across timed samples
beyond a portable 256 KiB bound.

| Scenario / operation | Retained growth | PHP peak allocation |
|---|---:|---:|
| `compiler_repeated` (20,000 compiles) | 0 bytes | 4 MiB |
| `lifecycle_soak` (5,000 create/use/close loops) | 0 bytes | 6 MiB |
| `streaming_cursor_soak` (50,000-row drain) | 0 bytes | 4 MiB |
| `batch_write_soak` (2,000-row `insertMany()` per sample) | 0 bytes | 6 MiB |

All four soak scenarios also report zero retained file descriptors. The soak
memory gate passed on the reference profile.

## Gate verdict

- No median regression greater than 5% repeated in the pinned compile-path
  comparison; the CI `v0.3.0` comparison is added as an automated paired gate.
- Allocation-sensitive behavior improved (source-level per-compile/per-terminal
  allocations removed; `read_terminals` faster; retained allocation flat).
- SQLite multiprocess contention and busy-timeout probes pass deterministically.
- The memory soak shows constant retained allocation across streaming,
  batch-write, and lifecycle workloads.
