# 0.8 consumer adoption analysis

Date: 2026-09-18. Scope: read-only analysis of the internal consumer at its
current revision, plus static analysis and database-free endpoint comparisons
against the `0.8.0` candidate. It is not a production deployment, a support
claim, or proof that the consumer's race paths behave safely under load.

## Tested source and environment

- Candidate: `feature/0.8-candidate` at `a218b79`, including the W1–W4 library
  workstreams.
- Consumer: its checked-out `master` at `bf102fc6`, unchanged throughout this
  analysis; the shared user interface review is in the
  [candidate rehearsal evidence](0.8-worker-rehearsal.md).
- Consumer checks ran under PHP 8.3.33 (its declared platform) with the
  installed `pdo_mysql`, Redis, and XML/zip extensions. Library checks ran
  under PHP 8.4.24.

## Checks run

1. **Static analysis.** The consumer's unchanged PHPStan level 5 passes with
   its pinned `0.7.0`, and passes in a temporary copy that installs the
   candidate through a path repository. The candidate's narrower
   `min()`/`max()` return type is not used by consumer source.
2. **Database-free endpoint comparison.** Temporary 0.7.0 and candidate copies
   ran the classic entrypoint under PHP 8.3.33 with the route cache disabled.
   The root response, the public status endpoint, and an unknown route returned
   identical status codes, response keys, and bodies (including the
   `{message,class,status,code}` error envelope).
3. **Worker-mode smoke.** The real worker entrypoint ran under FrankenPHP with
   one worker thread matched to every request. Four consecutive requests across
   the root and status routes returned `200` with identical bodies for both
   0.7.0 and the candidate. This exercises the app bootstrap, `$_SERVER`
   merging, route resolution, and response envelopes, not database work.
4. **Read-only source audit** across connection registration and holders, model
   injection and write adapters, transactions and locks, answer/save and
   completion paths, the HTTP error handler, report/export paths, and the
   worker bootstrap and route cache.

## Findings and adoption actions

The table records generic descriptions; file-level line maps are deliberately
not published. All remediation is application-owned.

| Area | Observed | Candidate support | Adoption action |
| --- | --- | --- | --- |
| Holder idle policy | Uses wall-clock time plus successful-query observations, and inspects internal transaction/cursor methods with a suppressed strict close. | `isReusable()`, `discard()`, the monotonic worker recipe, and the OBS-1 counter guidance. | Migrate the holder to the public lifecycle surface; query observation cannot see direct PDO, transaction controls, or delayed cursor work. |
| Role eviction | A classified connection-loss error discards both primary and read holders. | The worker recipe evicts only the uncertain role and never connects an unused role to discard it. | Evict the affected role; let routing and authoritative-read policy decide the rest. |
| Quarantine handling | No inspection of `TransactionException::connectionUnusable`; an unusable or quarantined wrapper can stay cached until the idle threshold and surface repeated failures. | W2 evidence fields plus the inspection recipe. | Discard a quarantined wrapper even without a recognizable connection-loss code. |
| Failure classification | The pinned 0.7.0 construction exception has no normalized evidence, so the handler treats every construction failure as unavailable and also matches message text; idle code `4031` and some capacity/auth codes are not classified. | `operation`, `sqlState`, `driverCode`, `driver`, and `connectionLabel`. | Adopt normalized fields after upgrade; separate authentication, capacity, transport, and lock evidence before choosing a status or retry. |
| Statement timeout | Report/export paths raise the session statement limit to 15 s through direct PDO `exec` and never restore it; the raised value sticks to the reused worker session until replacement, contradicting the documented 5 s default. | The W3 session initialization/restoration recipe. | Restore in `finally`; if restoration fails, evict the session and preserve the original failure. Reapply initialization to every replacement. |
| Timeout command failures | Unsupported or failed timeout configuration is swallowed and logged as best effort without distinguishing a transport failure. | Unsupported configuration may remain best effort; transport failure must not publish a connection as ready. | Inspect the failure class before caching the initialized connection. |
| Model connection caching | Models cache the first resolved connection. A holder idle swap or discard can split two models across owners inside one transaction, so one model's writes can miss the other's transaction. | Pin one owner per unit and resolve lazily through a request scope; the transaction manager rejects cross-connection composition. | Adopt per-request pinning; do not resolve a replacement for an individual model or statement. |
| Write returns | A legacy adapter maps update/delete to `true`, so a zero-row transition or a no-op update is indistinguishable from success. Raw upsert ID sequences assume the same live session across calls. | Affected-row integers, state-guarded updates, and immediate same-session `insertGetId()` capture. | Keep legacy booleans only where a false positive is acceptable; use guarded transitions where completion must be exact, and never split a write from its ID read. |
| Batch chunking | Several multi-chunk imports and multi-write flows run without a wrapping transaction; others wrap correctly. | Explicit caller-owned atomicity with no cross-chunk promise. | Decide per workflow and wrap the chunks inside one transaction when all-or-nothing is required. |
| Answer/save versus completion | Strong modules serialize on the attempt row with row locks, completion guards, and affected-row scoring; weaker modules complete lock-free through always-true updates, so duplicate stops can rescore and a late save can land after scoring. | No retry or replay; transaction, lock, and reconciliation patterns are documented and tested. | Extend the strong pattern to the remaining modules; unique answer keys alone are not end-to-end idempotency. |
| Dynamic identifiers | One list endpoint forwards request ordering into a raw identifier position on a non-cached branch. | Dynamic identifiers must be allowlisted; values remain bound. | Allowlist ordering keys at the controller boundary. |
| Read-role writes | A public read-oriented controller injects the read handle into its models but performs several writes through them. The local configuration points both roles at the same server, so the split is latent until a read replica is configured. | Writes and authoritative reads belong on the primary owner. | Route those writes through the primary handle before enabling a replica. |
| Worker lifecycle | The app, holders, Redis client, and environment cache boot once per thread; only cycle GC runs between requests; there is no application health route, the service stop timeout is shorter than the documented drain budget, and worker recycling is disabled. | The FrankenPHP worker recipe, boundary cleanup, counters, and shutdown guidance. | Align stop timeouts and health checks, rehearse consecutive requests and idle recovery, and keep recycling policy documented. |
| Error redaction | The HTTP body includes the top-level exception message regardless of the display flag; this is safe for library exceptions, but a bare PDO exception from a direct PDO path can expose driver text. Sentry receives the full exception graph, including previous driver messages and traces. | Safe top-level messages plus normalized evidence fields; sensitive lower-level evidence stays application-owned. | Adopt normalized fields, keep direct PDO failures out of responses, and review error-reporting scrubbing. |

## Release implication

The library-side W1–W4 surface is sufficient for these adoption actions; no new
public API is required. The consumer adoption remains open until its holder,
error handler, timeout restoration, role eviction, and weak completion paths are
changed and rehearsed against a candidate pin. Database-backed endpoint checks,
payload comparisons, HTTP redaction verification, staged rollout, and rollback
remain separate work.

## Limits

- No database-backed endpoint was exercised: the consumer repository has no
  complete fresh-install schema, and its configured database is not
  disposable. No production data, credentials, or secrets were used.
- The worker smoke used the rehearsal image (PHP 8.4 ZTS) while static and
  classic checks used PHP 8.3.33. The smoke proves boot and response
  compatibility, not database behavior or long-run worker stability.
- The audit is a point-in-time read-only review. It does not reproduce the
  reported race or timeout conditions under load, and the consumer checkout
  was not modified.
