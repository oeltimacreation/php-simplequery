# `0.3.0` projection ergonomics spike

Date: 2026-07-28

## Question

Does rewriting production-shaped raw projection lists with the existing
structured API remain noisy enough to justify a `selectList()`-style method?

The source observations are aggregate and anonymized. The examples below use
synthetic identifiers and do not reproduce private SQL.

## Representative rewrite

A raw list can combine identifier syntax, aliases, wildcards, and real SQL in
one trusted string:

```php
$query->select($db->raw(
    'u.id, u.email AS contact, p.*, LOWER(u.email) AS normalized_email'
));
```

The accepted structured rewrite is:

```php
$query->select(
    'u.id',
    Identifier::of('u.email')->as('contact'),
    Identifier::wildcard('p'),
    $db->raw('LOWER(u.email) AS normalized_email'),
);
```

Long reporting projections use the same repeated form. Ordinary identifiers,
qualified wildcards, and identifier aliases stay structured; only actual SQL
expressions remain trusted raw code. Each entry is independently reviewable,
and formatting the arguments one per line keeps changes local.

## Decision

Do not add `selectList()` in `0.3.0`. Variadic `select()` and
`Identifier::as()` are materially clearer than a raw comma-separated list and
are not materially noisy in the representative short and long shapes. A list
method would either duplicate variadic calls or tempt parsing SQL-like strings,
without reducing the number of values callers must supply.

The public guide now shows the structured rewrite and the expression-comparison
example uses raw SQL only for the function expression. This result owns
SQ-0327 and is governed by [ADR-019](../adr/019-expression-and-column-comparisons.md).
