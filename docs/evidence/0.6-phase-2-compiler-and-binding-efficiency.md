# `0.6.0` Phase 2 compiler and binding efficiency evidence

Date: 2026-08-23

Release baseline: immutable `v0.5.0`
(`902a18037303d7e28cefcad6859c157b98e2d05b`)

Candidate: `feature/0.6-candidate` working tree based on
`b5899cd872688182722603260a8e9270f5422b6c`

Decision: accept three transient-allocation reductions for high-cardinality
compiler workloads. Reject alternative batch column iteration and identifier,
clause, or snapshot loop changes. The timing evidence does not support a
compiler-speed claim.

## Scope and method

The local evidence host used Linux x86-64, PHP 8.4.24 CLI, PDO SQLite 3.45.1,
disabled CLI OPcache/JIT, Xdebug timing mode off, and PCOV disabled. Every
operation used a fresh PHP worker, three warm-ups, nine timed samples, raw
correctness digests, per-invocation transient allocation, RSS, retained-growth,
and descriptor evidence.

The attribution pass added equivalent-output controls for the released and
candidate placeholder algorithms, batch column validation, batch placeholder
construction, scalar binding normalization, pretyped batch compilation,
identifier quoting, clause accumulation, and deep/shallow snapshots. Five
identical `v0.5.0` runs established component ranges before product edits.

Each product candidate was then applied separately and run baseline-first and
candidate-first against the immutable tag. The final tree repeated the full CI
suite in both source orders after a five-run identical-candidate control. Raw
JSON remains disposable under `/tmp`; CI archives equivalent reports from the
ignored `benchmarks/results/` directory.

## High-cardinality `IN` decision

The 5,000-placeholder component was material. The released
`array_fill()`/`implode()` control used 233,528 transient bytes; the exact same
placeholder string built with a repeated string used 32,768 bytes. Their five-
run median ranges were 0.020115–0.058659 ms and 0.002945–0.003062 ms,
respectively. Both controls asserted byte-identical complete SQL before
returning their normalized digest facts.

Replacing only that production placeholder construction reduced the prepared
compiler operation from 368,872 to 286,968 transient bytes (22.2%) in both
source orders. Removing the later duplicate validated-binding list brought the
final candidate to 168,144 bytes, a 54.4% reduction from `v0.5.0`.

| Final source order | `v0.5.0` median | Candidate median | `v0.5.0` transient | Candidate transient |
| --- | ---: | ---: | ---: | ---: |
| Baseline first | 0.476061 ms | 0.218939 ms | 368,872 B | 168,144 B |
| Candidate first | 0.494273 ms | 0.221526 ms | 368,872 B | 168,144 B |

The absolute timing differences, 0.257122 ms and 0.272747 ms, remain below the
host's 0.545785 ms Phase 1 floor. The timing percentages are retained in the
raw reports but are not interpreted as a speed result. Empty lists still emit
`0 = 1` or `1 = 1`, subqueries retain their SQL, and list bindings retain exact
occurrence order and concrete types.

## Batch-insert cost decisions

The released 1,000-row, three-column workload separated as follows. These are
attribution controls, so their times are not additive.

| Component or operation | Five-run median range | Transient allocation | Decision |
| --- | ---: | ---: | --- |
| Full scalar batch compilation | 1.085825–1.365137 ms | 457,424 B | Optimize intermediates |
| Pretyped batch compilation | 0.462835–0.779081 ms | 217,424 B | Normalization is material and required |
| `array_keys()` column validation | 0.047497–0.073797 ms | 216 B | Retain |
| Direct key iteration | 0.094027–0.098373 ms | 0 B | Reject; slower for negligible bytes |
| Placeholder array control | 0.013341–0.014728 ms | 32,864 B | Avoid retained arrays where possible |
| Placeholder string control | 0.001003–0.003239 ms | 24,616 B | Accept as buffer model |
| Scalar binding normalization | 0.714302–0.744546 ms | 309,688 B | Retain required normalization |

Two independently measured batch changes cleared the allocation rule:

1. `CompiledQuery` now validates the caller's list in place instead of copying
   every already-normalized binding into a second list. The original two-pass
   member-before-concrete-type validation order remains unchanged. This moved
   the full batch from 457,424 to 400,040 transient bytes (12.5%).
2. Batch compilation now appends each validated row directly to one SQL buffer
   instead of retaining per-row placeholder arrays and a complete row-group
   array. Row keys are still validated before that row's values, and each row
   is still normalized before the next row is inspected. Relative to the first
   accepted state this moved 400,040 to 339,504 bytes (15.1%).

The final source-order comparison was:

| Final source order | `v0.5.0` median | Candidate median | `v0.5.0` transient | Candidate transient |
| --- | ---: | ---: | ---: | ---: |
| Baseline first | 1.191732 ms | 1.128556 ms | 457,424 B | 339,504 B |
| Candidate first | 1.209843 ms | 1.154599 ms | 457,424 B | 339,504 B |

The final batch allocation reduction is 25.8%. The pretyped control fell from
217,424 to 99,504 bytes (54.2%), attributing the improvement to retained
compiler intermediates rather than skipped scalar normalization. Timing moved
by less than 10% and supports no speed claim.

## Identifier, clause, and snapshot profile

The equivalent 50-wide prepared shapes compiled to identical SQL, values, and
types. Repeated `v0.5.0` results were:

| Prepared operation | Five-run median range | Transient allocation |
| --- | ---: | ---: |
| Structured identifiers and clauses | 0.092658–0.144402 ms | 10,760 B |
| Raw identifier control | 0.047103–0.047961 ms | 10,760 B |
| Collapsed-clause control | 0.068682–0.104429 ms | 10,760 B |
| Deep snapshot then compile | 0.152776–0.189179 ms | 17,312 B |
| Shallow snapshot then compile | 0.091590–0.145798 ms | 11,064 B |

Every timing remains sub-millisecond and every difference is below the
absolute floor. Identifier quoting and clause dispatch add no incremental
transient peak in this shape. Deep copying has an expected 6,552-byte cost,
while the maintained shallow compilation snapshot adds 304 bytes. No loop,
quoting, clause, or snapshot implementation change is accepted; none has a
prepared-builder result that clears the rule.

## Correctness and resource gates

MariaDB, MySQL, and SQLite golden fixtures retain exact `IN` and multi-row
insert SQL and now assert ordered binding types for those cases. Focused
contracts additionally cover 5,000 mixed typed list values in every dialect,
raw-expression batch values, first-row binding failure before a later column
mismatch, row-column mismatch before that row's invalid value, clone isolation,
nested subquery snapshots, repeated write compilation, and terminal
non-mutation. Live SQLite executes and reuses the same batch terminal without
state accumulation.

No compilation context, placeholder string, row SQL, or query value is cached
or shared between calls. Values remain positional bindings, raw SQL remains a
trusted-code boundary, and exceptions do not include binding values.

The final identical-source control measured a 0.545785 ms absolute floor. Both
full comparisons accepted 30 scenario and 73 operation digests. Baseline-first
flagged only `compiler_batch_insert_high/binding_normalization_control` and
`hydration_wide/simplequery_object`; candidate-first flagged only
`cursor_exhaustion_wide/simplequery_associative_cursor` and
`observer/observer_noop`. Their actionable intersection is empty.

Across the final candidate suites, maximum transient allocation was 2,354,168
bytes, maximum worker RSS was 44,810,240 bytes, retained growth was zero, and
every file-descriptor delta was zero. The reference soak retained zero bytes
and zero descriptors across four scenarios and five operations.

Validation passed:

- `composer check`: 452 tests and 1,286 assertions plus lint, PHP 8.2 platform,
  PHPStan project/consumer, coding style, public API, documentation, examples,
  and repository checks;
- line coverage: 94.58% overall and 97.00% compiler;
- branch coverage: 91.11% overall and 92.04% compiler;
- `composer benchmark:soak`;
- `composer probe:sqlite`;
- `composer probe:execution -- sqlite`; and
- `composer probe:transaction -- sqlite`.

Direct MariaDB/MySQL and proxy services were not rerun because emitted SQL,
ordered bindings, public contracts, PDO execution, and engine/proxy claims are
unchanged. Their dialect compiler contracts are covered by the exact golden
fixtures; this phase makes only PHP-process allocation claims.

Phase 2 passes: every accepted change exceeds 10% transient allocation in both
source orders, the final candidate has no repeatable unexplained timing
regression, and all compiler contracts remain exact.
