# `0.6.0` Phase 4 code quality and maintainer efficiency evidence

Date: 2026-08-24

Release baseline: immutable `v0.5.0`
(`902a18037303d7e28cefcad6859c157b98e2d05b`)

Candidate: `feature/0.6-candidate` working tree

Decision: retain transaction manager and compiler cohesion without class extraction;
add a compact data-driven connection state-transition matrix; audit and document
builder mutation behavior; add a deterministic release-consistency quality tool and gate;
remove retired configuration paths; and preserve the verified CI/local feedback profile.

## Scope and method

Phase 4 evaluated code structure, state transitions, error boundaries, release consistency,
configuration hygiene, and workflow efficiency across the repository.

Checks were performed against the candidate working tree using PHP 8.4.24, PHPUnit 11.5.56,
PHPStan level 9 with strict rules, PHPCS, PCOV, Xdebug 3.5.3, and SQLite 3.45.1.

## Architecture and responsibility audit

The transaction state machine (`TransactionManager`) and compiler template hierarchy
(`AbstractDialectCompiler`, `MySqlFamilyCompiler`, `MariaDbCompiler`, `MySqlCompiler`,
`SqliteCompiler`) were re-audited for complexity, coupling, and boundary cohesion.

- The transaction state machine manages savepoint counters, physical transaction ownership,
  unusable state quarantine, and active cursor guards in a single cohesive unit. Splitting
  or extracting helper delegates would increase indirection and failure-path exposure without
  reducing complexity.
- The dialect compiler hierarchy uses single-pass generation with shared clause assembly.
  No defects or unhandled dialect variations warrant splitting the shared compiler template.
- Retention is accepted as safer and more maintainable than extraction.

## State-transition matrix

A compact, data-driven unit test (`ConnectionStateMatrixTest`) was added to cover all
connection states against all public operations:

| Connection state | `table()` | `query()` | `pdo()` | `execute_query` | `transaction()` | `close()` | `require_lock` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `Clean` | Builder | RawQuery | PDO | Result | Success (depth 1) | Closed | Rejected (`lock_query`) |
| `ActiveCursor` | Builder | RawQuery | PDO | Result | Rejected (`commit`) | Rejected (`close`) | Rejected (`lock_query`) |
| `ManagedTransaction` | Builder | RawQuery | PDO | Result | Nested savepoint | Rejected (`close`) | Success |
| `ExternalTransaction` | Builder | RawQuery | PDO | Result | Rejected (`begin`) | Rejected (`close`) | Success |
| `Quarantined` | Builder | RawQuery | Rejected (`use_connection`) | Rejected (`use_connection`) | Rejected (`use_connection`) | Closed | Rejected (`use_connection`) |
| `Closed` | Rejected (`ConnectionException`) | Rejected (`ConnectionException`) | Rejected (`ConnectionException`) | Rejected (`ConnectionException`) | Rejected (`ConnectionException`) | No-op | Rejected (`ConnectionException`) |

The test verifies that state guards reject unsafe operations with exact exception types
(`ConnectionException`, `TransactionStateException`, `ExternalTransactionException`) and correct
quarantine flags without duplicate boilerplate.

## Builder partial mutation audit

Multi-input builder methods were audited and covered by `QueryBuilderStateIntegrityTest`:

- Variadic projection and grouping methods (`select(...$columns)` and `groupBy(...$columns)`)
  process elements iteratively into mutable query state. When an element fails normalization
  (`InvalidQueryException`), preceding valid elements remain in the mutable builder instance.
- Single-predicate condition methods (`whereIn`, `whereBetween`, `join`) validate all inputs
  atomically before modifying internal condition collections; a failed call leaves the condition
  collection unmodified.
- Terminal compilation and execution methods do not mutate the query builder.
- SimpleQuery makes no transactional rollback guarantee for mutable builder clause failures.
  Throwing `InvalidQueryException` signals broken query construction; callers must discard or
  recreate the builder rather than assume partial clause rollback. This matches existing contracts.

## Deterministic release-consistency check

A new quality tool, `ReleaseConsistencyChecker`, and maintenance command, `composer release:check`,
were added and wired into `composer check` and `scripts/verify-repository.php`.

The check validates:
1. **Active plans:** Exactly one release plan (e.g. `0.6.md`) exists in `docs/plans/` alongside
   `README.md`, and all plan indexes (`docs/README.md`, `docs/maintainers/README.md`,
   `docs/plans/README.md`) reference it.
2. **Support and security alignment:** `SUPPORT.md` current minor and recommended pin agree with
   `SECURITY.md` supported release line (`0.5.0` / `~0.5.0` matching `0.5.x`).
3. **Benchmark baseline labels:** `.github/workflows/ci.yml` and `docs/maintainers/benchmarking.md`
   reference the active baseline tag (`v0.5.0`).
4. **Maintained commands:** Every `composer <command>` invocation in active markdown guides,
   maintainer documentation, and CI workflows exists in `composer.json` `scripts`.
5. **Configuration paths:** Every path configured in `.codescene/code-health-rules.json` exists in
   the working tree.
6. **Historical exemptions:** `CHANGELOG.md`, `docs/adr/*`, and `docs/evidence/*` remain durable
   records and are exempt from active consistency checks.
