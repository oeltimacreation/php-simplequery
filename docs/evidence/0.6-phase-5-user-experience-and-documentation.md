## Clean no-dev consumer walkthrough and friction log

A simulated clean no-dev consumer was walked through the complete library lifecycle:
1. **Installation & dependencies:** The package declares `php: ^8.2` and `ext-pdo: *`,
   with no required third-party runtime dependencies. Installation in a `--no-dev`
   consumer environment is lightweight with zero transitive dependency friction.
2. **Connection setup:** Verified instantiation via `Connection::connect(Driver::Sqlite, 'sqlite::memory:', connectionOptions: new ConnectionOptions(label: '...'))`.
3. **Query construction & testing:** Verified detached query building and SQL/binding
   assertions using `Testing\CompilerConnection` and `Testing\CompiledQueryAssertions`
   without opening a live database connection.
4. **Result selection & hydration:** Verified `get()` (`list<stdClass>`), `getAssociative()`
   (`list<array<string, mixed>>`), `first()`, `firstAssociative()`, and aggregate
   functions (`count()`, `sum()`, `average()`, `min()`, `max()`).
5. **Streaming & Cursors:** Verified `iterateAssociative()` with early termination and
   `finally { $cursor->close(); }` cleanup.
6. **Writes:** Verified `insert()`, `insertGetId()`, `insertMany()`, `update()`, and `delete()`.
7. **Managed Transactions:** Verified atomic commits, nested savepoints, and domain
   exception rethrow on rollback.
8. **Failure diagnosis:** Verified safe inspection of `QueryExecutionException` and
   `TransactionException` properties without credential or binding disclosure.

Automated coverage was added in `tests/Consumer/CleanConsumerLifecycleTest.php` (1 test,
37 assertions).

### Friction observations

- **Observation 1:** `insertGetId()` returns `string` rather than `int`. This is an
  intentional design invariant to prevent truncation on 64-bit unsigned integer IDs
  generated by databases. It is documented in the getting-started guide and the new
  terminal-choice guide.
- **Observation 2:** Associative hydration intentionally rejects columns with numeric-string
  names to preserve the strict `array<string, mixed>` return contract. Aliasing is clearly
  recommended in documentation when numeric column identifiers occur.
- **Observation 3:** Mutable query builder clause methods mutate internal state while
  terminal methods do not. Re-executing a builder after a clause failure leaves preceding
  clauses intact; callers must discard/recreate broken builder instances.

## Terminal choice guide and driver caveats

Added a comprehensive **Terminal choice guide** to [`docs/guides/results-and-writes.md`](../guides/results-and-writes.md)
providing a decision matrix across all 16 public terminals:
- Maps each terminal to primary use cases, return types, empty result shapes, PHP memory
  profiles, and driver/dialect caveats.
- Details memory behavior: O(1) row streaming with `iterate()`/`iterateAssociative()` versus
  full result set retention in `get()`/`getAssociative()`.
- Highlights driver return differences: MariaDB/MySQL changed-row counts vs matched-row counts,
  string generated IDs, and strict scalar rejection of `distinct()`, `groupBy()`, and `having()`
  on single-scalar aggregates (`sum()`, `average()`, `min()`, `max()`).

## Batching, limits, streaming, and deterministic pagination

Updated [`docs/guides/performance-and-streaming.md`](../guides/performance-and-streaming.md)
and [`docs/guides/query-builder.md`](../guides/query-builder.md):
- **Engine parameter limits:** SQLite host parameter limits (999 default, up to 32,766 in 3.32.0+)
  and MySQL/MariaDB 65,535 parameter ceiling for prepared batch statements.
- **Packet and statement limits:** Explains `max_allowed_packet` constraints for large multi-row inserts.
- **Buffered vs unbuffered streaming:** Compares default MySQL-family client memory buffering
  with unbuffered connection-locking streaming (`ConnectionOptions(buffered: false)`).
- **Chunking and transaction policies:** Details trade-offs between wrapping batches in a single
  atomic transaction (longer lock hold) versus independent chunk executions (partial progress with
  application reconciliation).
- **Deterministic pagination:** Explains why `forPage()`, `limit()`, and `offset()` require
  deterministic ordering with a unique tie-breaker column (e.g. primary key `id`) to prevent row
  shifting across pages.

## Error message audit and stability review

All `throw new` exception call sites across `src/` were audited for clarity, specificity,
actionability, and credential/binding redaction:
- Exception messages concisely explain the exact reason for rejection (e.g. "select() requires
  at least one projection", "SQLite busy timeout cannot be negative", "A derived source requires
  an alias").
- No ambiguous or misleading messages were found.
- All existing error messages are preserved unchanged to protect consumer log assertions and
  automated monitoring patterns.

## Deferred feature families review and recommendation

Prior development plans and consumer audits identified several deferred feature requests:
1. Automatic batch-write chunking / upsert (`ON DUPLICATE KEY UPDATE` / `ON CONFLICT DO UPDATE`).
2. Named query parameter placeholders in query builder.
3. Dialect/compiler plugin architecture.
4. Active Record / ORM abstractions.
5. Automatic connection pooling, retry policies, and transparent reconnect.

**Recommendation:** **Default to no API expansion** for `0.6.0`.
- Rationale: SimpleQuery's core architectural strengths are its bounded scope, predictable
  execution, and strict ownership invariants. Adding partial ORM, dialect plugins, or retry
  layers would violate core ADRs (ADR-001 through ADR-017) and create unsupportable surface area.
  Trusted raw queries (`Connection::query()`) provide safe, explicit escape hatches for advanced
  engine-specific needs without framework bloat.
