# Structured `EXISTS` evaluation

The 0.11.0 investigation tested native `EXISTS` and `NOT EXISTS` on disposable
fixtures on 2026-11-20. It used the existing trusted raw predicate API around a
compiled child. These results informed the accepted structured API.
[ADR-027](../adr/027-structured-exists.md)

## Findings

MariaDB 11.8.2 and 11.8.8 and MySQL 8.0.11 and 8.0.46 ran on PHP 8.6.0 with
mysqlnd 8.6.0. Each server ran native and emulated prepares with both buffered
and unbuffered reads. SQLite ran at 3.39.2 on PHP 8.2.36 and at 3.46.1 on PHP
8.6.0. Results agreed across the preparation and buffering modes for each
direct server. The fixture versions and runner are documented in the
[database support reference](../reference/database-support.md).

- Correlated `EXISTS` matched customer `1` once despite two paid orders.
  `NOT EXISTS` returned customers `2` and `3` with no paid orders. A row
  projecting `NULL` still satisfied `EXISTS`. A nullable child key did not
  affect the absence result for unrelated customers.
- A grouped child with `HAVING COUNT(*) >= 2` matched customer `1`. A child
  projecting `COUNT(*)` over no matching orders returned one row per outer
  customer, so `EXISTS` matched all three. Substituting `SELECT 1` for that
  projection would change the result.
- The grouped parent combined a bound tenant, a bound child projection, a
  bound child status, an `OR` sibling, and a trailing active flag. All
  fixtures returned `[1, 3]` and logical `count()` returned `2`. Bindings
  stayed `[11, 'projection', 'paid', 3, 1]` in `integer, string, string,
  integer, integer` order after child mutation and a separate parent clone.
  The clone's additional filter returned `[1]`.
- An outer `HAVING EXISTS` grouped by `c.id` matched customer `1` in this
  fixture. Other grouped shapes require their own qualification.

| Case | SQLite 3.39.2 / 3.46.1 | MariaDB 11.8.2 / 11.8.8 | MySQL 8.0.11 | MySQL 8.0.46 |
| --- | --- | --- | --- | --- |
| `EXISTS` with `LIMIT 0` | `[]` | `[]` | `[1]` | `[]` |
| `EXISTS` with ordered `LIMIT 1 OFFSET 1` | `[1]` | `[1]` | `[1]` | `[1]` |
| `EXISTS` with `DISTINCT` and the same pagination | `[1]` | `[1]` | `[1]` | `[1]` |
| Standalone `DISTINCT` child for customer `1` with the same pagination | No rows | No rows | No rows | No rows |
| Update with a child reading a different table | 1 row | 1 row | 1 row | 1 row |
| Update, delete, and nested `IN` update reading the write target | 1 row each | 1 row each | Error `1093` each | Error `1093` each |

MySQL documents its restriction on modifying a table while selecting from it
in a subquery. The nested `IN` case confirmed that an intermediate subquery
still reaches that restriction. Every write experiment used a transaction
that the harness rolled back. [MySQL 8.0 subquery restrictions](https://dev.mysql.com/doc/refman/8.0/en/subquery-restrictions.html)

## Original proposal

- Offer `whereExists(QueryBuilder $subquery)`, `orWhereExists()`,
  `whereNotExists()`, and `orWhereNotExists()` on `QueryBuilder` and `ConditionGroup`,
  matching the `IN` family. Accept them for a read's `WHERE`, including nested
  `WHERE` groups. Decide the policy for writes and other predicate sites before
  exposing these methods.
- Compile a same-connection child into an independent snapshot at attachment.
  Apply the structured-child lock check and reject any explicit child limit or
  offset before mutating the parent, including `limit(0)`. Preserve the child's
  SQL and ordered typed bindings, including projection values. Qualified
  identifiers can correlate with the parent. The database resolves their scope
  when it prepares the statement.
- Prefer a dedicated internal predicate over a factory returning
  `RawExpression`. A typed node lets the compiler enforce the supported
  contexts. A raw factory would lose that information as soon as callers used
  its result in a regular raw clause.
- Validate the parent predicate site, because a `ConditionGroup` can also
  enter through `having()`. For a read-only contract, reject structured
  occurrences in writes before preparing SQL, including an occurrence inside
  an attached `IN` child or one of its derived sources. Carry that fact in
  internal snapshot metadata, since `CompiledQuery` stores only SQL and
  bindings. Keep trusted raw SQL opaque and preserve the existing write
  contract for other predicates.
- If adopted, cover exact SQL and bindings for all four variants, nested
  groups, grouped reads and logical counts. Add rejection and state-isolation
  tests for cross-owner, locked, and paginated children, outer `HAVING`, and
  write terminals with direct and nested occurrences. Qualify live engine
  minimums and current fixtures first, then run the proxy checks with their
  direct controls.

The correlated paid-order case demonstrates how to compose a reusable child
without introducing duplicate result rows. The existing raw API can express
it with a compiled child. The maintainer accepted the structured API and its
context checks on 2026-11-21.

## Reproduce the boundaries

Use a disposable database and the maintained direct fixtures. For SQLite,
run the statements on the PDO connection that reports the intended linked
version. The same test data uses positional bindings in the live harness.
[Minimum SQLite runner](../maintainers/testing-architecture.md)

```sql
CREATE TABLE sq_exists_customers (id INT PRIMARY KEY, tenant_id INT, active INT);
CREATE TABLE sq_exists_orders (customer_id INT, status VARCHAR(20), amount INT);
INSERT INTO sq_exists_customers VALUES (1, 11, 1), (2, 11, 1), (3, 11, 1), (4, 22, 1);
INSERT INTO sq_exists_orders VALUES
    (1, 'paid', 4), (1, 'paid', 5), (2, NULL, 6), (4, 'paid', 7), (NULL, 'paid', 8);

SELECT c.id FROM sq_exists_customers AS c WHERE c.tenant_id = 11 AND EXISTS (
    SELECT o.amount FROM sq_exists_orders AS o
    WHERE o.customer_id = c.id AND o.status = 'paid' LIMIT 0
) ORDER BY c.id;

SELECT c.id FROM sq_exists_customers AS c WHERE c.tenant_id = 11 AND EXISTS (
    SELECT DISTINCT o.status FROM sq_exists_orders AS o
    WHERE o.customer_id = c.id AND o.status = 'paid'
    ORDER BY o.status LIMIT 1 OFFSET 1
) ORDER BY c.id;

SELECT DISTINCT o.status FROM sq_exists_orders AS o
WHERE o.customer_id = 1 AND o.status = 'paid' ORDER BY o.status LIMIT 1 OFFSET 1;

BEGIN;
UPDATE sq_exists_customers SET active = 0 WHERE id IN (
    SELECT o.customer_id FROM sq_exists_orders AS o WHERE EXISTS (
        SELECT c.id FROM sq_exists_customers AS c WHERE c.id = o.customer_id AND c.id = 1
    )
);
ROLLBACK;
```

Local JSON results, including the complete executed cases, are under
`tools/database-probes/results/0.11-exists.Ka13yk/`.

## Structured API validation

On 2026-11-21, the candidate passed the exact SQL and typed binding fixtures
for each dialect. SQLite tests exercised duplicate matches, nulls, aggregate
and grouped children, retained snapshots, and write rejection before PDO
execution. The actual SQLite 3.39.2 runtime on PHP 8.2.36 passed 56 integration
tests and the maintained execution probe.

The minimum MariaDB 11.8.2 and MySQL 8.0.11 probes on PHP 8.6.0 passed all 24
reports. The PHP 8.5.12 service runner passed all 99 reports for the current
MariaDB 11.8.8, MySQL 8.0.46, ProxySQL 3.0.1, and MaxScale 23.02.17-2 fixtures.
The structured read case passed across the native/emulated and
buffered/unbuffered combinations, with direct-engine results as the proxy
controls. Reports are under
`tools/database-probes/results/0.11-structured-exists.ULvR6m/`.
