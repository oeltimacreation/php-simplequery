# `0.3.0` production-shaped performance evidence

Date: 2026-07-28

Baseline: `v0.2.0` / `a9928769184c5a74f56da169022073b872889885`

Candidate: `ec830115ee2ef46d5d8848483e144a16145a437b`

Decision: accept the Phase 5 benchmark expansion. All compiler SQL/binding and
execution result digests matched across versions. No median regression greater
than 10% repeated in both source orders, so no performance waiver or production
optimization is justified.

## Method

Both source trees were clean detached worktrees. The finalized candidate runner
loaded each source through its own Composer autoloader and ran every scenario in
a fresh PHP process with PHP 8.4.23, SQLite 3.45.1, Xdebug timing mode disabled,
PCOV disabled, two warm-ups, and seven alternating samples. Absolute timings
describe this Linux x86-64 host only.

The paired command used `benchmarks/compare.php --suite=production
--profile=reference` once with `--source-order=baseline-first` and once with
`--source-order=candidate-first`, explicit `v0.2.0`/candidate labels, and the
two worktree autoloaders. Raw schema-version-2 JSON remains an ephemeral build
artifact under the project artifact policy.

## Paired medians

Values are candidate change relative to `v0.2.0`; negative values are faster.

| Scenario / operation | Baseline first | Candidate first | Decision |
|---|---:|---:|---|
| report compile | +3.028% | +9.548% | below review threshold |
| count compile | +48.924% | +0.017% | isolated source-order signal |
| object hydration | -11.092% | +14.687% | direction reversed with order |
| associative hydration | -11.743% | +12.689% | direction reversed with order |
| object cursor | -10.507% | +11.428% | direction reversed with order |
| associative cursor | -10.465% | +10.609% | direction reversed with order |
| direct PDO bulk-read control | -9.190% | +8.700% | direction reversed with order |
| `insertMany()` | -0.477% | -1.678% | stable |
| repeated individual inserts | +0.194% | -1.605% | stable |

The report-mode changes track the direction of the direct-PDO control and flip
when source order flips. The count-compile signal appears in only one ordering.
Neither is a repeated candidate regression, and correctness is identical, so
the result is attributed to host/source-order noise rather than accepted as a
code regression. This decision does not claim that timings transfer to another
host or workload.

## SQL shape and result gates

- `production_report_compile` checks exact SQLite SQL and ordered bindings for
  12 projections, three joins, nested conditions, trusted raw expressions, a
  half-open date range, 40 conditional filters, and 1,000 `IN` values.
- `production_count_compile` checks exact distinct-count SQL and ordered
  bindings over a 1,000-value filter.
- `production_report_execute` requires identical ordered rows and logical count
  from object/associative full hydration, object/associative cursors, and direct
  PDO bulk reads over a 50,000-row fixture.
- `production_batch_execute` requires identical affected rows and ordered table
  contents from a 1,000-row `insertMany()` and repeated individual writes.
- Fixture construction is excluded from timing and uses application-owned
  100-row setup chunks to remain below SQLite parameter limits.

## Query-plan explanation

`composer benchmark:plans` used 20,000 indexed synthetic rows. Both predicates
returned the same 714 IDs and digest
`5c9c0e0e0eb2cdf4df8cbc648d718e701390f14fcaed80b7dfe65a8dd2b83350`.

| Shape | SQLite plan |
|---|---|
| `created_at >= ? AND created_at < ?` | `SEARCH ... USING COVERING INDEX index_plan_events_created_at (created_at>? AND created_at<?)` |
| `date(created_at) = ?` | `SCAN plan_events USING COVERING INDEX index_plan_events_created_at` |

This plan is explanatory evidence for this SQLite version, schema, data, and
query pair. It does not claim that SimpleQuery controls indexes or that another
engine or dataset must choose the same plan.

## Memory and lifecycle gates

The complete 22-scenario reference suite passed every correctness check. Full
100,000-row hydration peaked at 82 MiB PHP allocation and about 130.4 MiB
process RSS. Cursor early-close peaked at 4 MiB, retained no PHP allocation,
and changed no file descriptors.

Four concurrent reference soak workers each completed 20,000 repeated compiles
and 5,000 connection create/use/close loops per sample:

- repeated compilation retained 0 bytes and 0 file descriptors in every worker;
- lifecycle soak retained one consistent 2 MiB PHP allocator block after
  first-use class loading and 0 file descriptors in every worker;
- lifecycle peaks were 6 MiB PHP allocation and approximately 40.1 MiB RSS.

The repeated allocator plateau is recorded rather than treated as a universal
zero-allocation claim. Zero descriptor growth and successful repeated close
cycles provide the lifecycle gate; no caching, global state, retry, or weaker
validation was added.
