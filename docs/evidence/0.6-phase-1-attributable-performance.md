# `0.6.0` Phase 1 attributable performance evidence

Date: 2026-08-23

Release baseline: immutable `v0.5.0`
(`902a18037303d7e28cefcad6859c157b98e2d05b`)

Candidate: `feature/0.6-candidate` working tree at
`698c909c8b2f3b2fd7d34b31b4de3789fe154cc1`

Decision: accept the attributable benchmark infrastructure as the baseline for
later optimization phases. Phase 1 changes no product source and supports no
latency, throughput, or memory-improvement claim.

## Scope and environment

The candidate and `v0.5.0` have byte-identical `src/`, `composer.json`, and
`composer.lock` trees. `composer public-api:check` also passed against the
unchanged reviewed manifest. The measured differences below therefore
characterize the new harness and host variance, not a product change.

The local evidence host used Linux x86-64, PHP 8.4.24 CLI, PDO SQLite 3.45.1,
disabled CLI OPcache/JIT, Xdebug timing mode off, and PCOV disabled. Fixture
setup was excluded from timing. Raw local JSON remained disposable under
`/tmp`; CI archives equivalent reports from the ignored
`benchmarks/results/` directory.

The release-grade sampling commands used five identical-source runs and both
source orders with three warm-ups and nine samples:

```bash
mkdir -p benchmarks/results

php benchmarks/noise.php \
  --suite=ci --profile=ci --iterations=9 --warmups=3 --runs=5 \
  > benchmarks/results/identical-source-noise-control.json

php benchmarks/compare.php \
  --suite=ci --profile=ci --iterations=9 --warmups=3 \
  --source-order=baseline-first \
  --noise-report=benchmarks/results/identical-source-noise-control.json \
  --baseline-autoload=/path/to/v0.5.0/vendor/autoload.php \
  --candidate-autoload=vendor/autoload.php \
  --baseline-label=release-baseline --candidate-label=candidate

php benchmarks/compare.php \
  --suite=ci --profile=ci --iterations=9 --warmups=3 \
  --source-order=candidate-first \
  --noise-report=benchmarks/results/identical-source-noise-control.json \
  --baseline-autoload=/path/to/v0.5.0/vendor/autoload.php \
  --candidate-autoload=vendor/autoload.php \
  --baseline-label=release-baseline --candidate-label=candidate
```

## Measurement attribution

The CI surface now contains 29 scenarios and 60 operations. Every suite
operation runs in a fresh PHP worker with its own equivalent synthetic fixture.
The scenario report accepts only when all independent operations return the
same SHA-256 JSON digest. Before every timed invocation the harness resets the
PHP peak counter and retains:

- raw elapsed samples and median time;
- PHP allocator-used transient peak and separately reserved-arena peak;
- allocated and used memory after each sample plus retained growth;
- current RSS samples and worker maximum RSS;
- worker allocated-memory and file-descriptor deltas; and
- the operation correctness digest.

The live engine harness keeps its operations in one configured target
connection, so only the SQLite CI/soak surface claims a fresh worker per
operation.

## Build and compile separation

The representative 50-predicate compiler shape retains its original
`build_and_compile` operation and adds
`prepared_builder_compile_only`. Both operations emit identical SQL, binding,
first-value, and last-value facts.

| Operation | Candidate median range | Transient allocation | Worker RSS range |
| --- | ---: | ---: | ---: |
| Build and compile | 0.135049–0.234974 ms | 50,720 B | 39,792,640–39,854,080 B |
| Prepared-builder compile only | 0.065235–0.066855 ms | 6,904 B | 39,956,480–40,013,824 B |

Both timings are below the measured absolute floor, so their relative
difference is not a performance conclusion. The control establishes that
future compiler work can be distinguished from AST construction.

## Dimensional compiler controls

The isolated `IN` cases compile an already-prepared builder. Batch cases reuse
one builder and a fixture constructed before timing. Time ranges are the two
candidate-source-order medians; transient allocation is the per-invocation
maximum and RSS is the fresh-worker maximum range.

| Workload | Items | SQL bytes | Bindings | Time/item | Transient allocation | Worker RSS range |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `IN` small | 10 values | 78 | 10 | 0.945–1.015 µs | 1,568 B | 39,780,352–39,813,120 B |
| `IN` normal | 100 values | 348 | 100 | 0.091–0.183 µs | 5,752 B | 39,714,816–39,800,832 B |
| `IN` high | 5,000 values | 15,048 | 5,000 | 0.093–0.099 µs | 368,872 B | 40,529,920–40,751,104 B |
| Batch small | 10 rows | 167 | 30 | 1.756–3.104 µs | 6,016 B | 39,677,952–40,050,688 B |
| Batch normal | 100 rows | 1,157 | 300 | 1.762–1.788 µs | 58,480 B | 39,895,040–40,017,920 B |
| Batch high | 1,000 rows | 11,057 | 3,000 | 1.181–1.325 µs | 457,424 B | 40,374,272–40,411,136 B |

All six operations recorded zero retained allocated growth and zero file-
descriptor delta in both source-order reports. Small and normal percentage
differences are noise-floor-bound; the values are workload baselines, not
optimization claims.

## Hydration and cursor controls

Narrow rows contain three columns and 96 payload bytes; wide rows contain
eighteen columns and 384 payload bytes. Full results and natural cursor
exhaustion use 1,000 rows. First-row and early-close cases consume one row from
the same 1,000-row fixture. Every mode has direct-PDO and SimpleQuery
associative/object operations normalized to the same result shape.

The following candidate medians come from the baseline-first report. Values
are `direct PDO / SimpleQuery`; they demonstrate that controls execute and are
not interpreted as portable ratios.

| Mode | Narrow associative | Narrow object | Wide associative | Wide object |
| --- | ---: | ---: | ---: | ---: |
| Full result | 0.218 / 0.381 ms | 0.449 / 0.325 ms | 1.100 / 1.530 ms | 1.459 / 1.498 ms |
| First row | 0.012 / 0.033 ms | 0.013 / 0.034 ms | 0.021 / 0.026 ms | 0.023 / 0.057 ms |
| Natural cursor exhaustion | 0.356 / 0.434 ms | 0.323 / 0.401 ms | 1.149 / 1.563 ms | 1.451 / 1.566 ms |
| Early cursor close | 0.012 / 0.011 ms | 0.012 / 0.012 ms | 0.022 / 0.027 ms | 0.010 / 0.028 ms |

All eight scenarios accepted direct/SimpleQuery digest parity. Across the full
29-scenario candidate run, maximum per-operation transient allocation was
2,354,168 bytes, maximum worker RSS was 44,621,824 bytes, retained allocated
growth was zero, and all 60 worker descriptor deltas were zero.

## Identical-source noise control

Five identical-candidate executions produced 44 operations whose maximum
median remained below 1 ms. The largest median range among them was
0.567579 ms, which is the local absolute floor. The largest contributors were
observer-off (0.567579 ms), SimpleQuery lifecycle (0.542644 ms), and narrow
associative cursor exhaustion (0.267979 ms).

The floor is intentionally conservative and host-specific. When both compared
medians are below 1 ms, a relative percentage is ignored unless the absolute
change exceeds this floor. At every duration the percentage remains in the
report, but a signal within that operation's own observed same-source median
range is classified as explained variance. A review signal must exceed the 5%
relative rule and the applicable absolute control. CI remeasures rather than
copying this local value.

## Paired release comparison

Both `v0.5.0`/candidate execution orders accepted all 29 cross-source digests.
Each order contained 60 operation comparisons and classified 46
sub-millisecond relative percentages under the absolute rule.

| Source order | Actionable one-order signals | Repeatable intersection |
| --- | --- | --- |
| Baseline first | `compiler_batch_insert_high/insert_many_compile` | None |
| Candidate first | None | None |

The batch signal was retained in its raw report and did not reproduce in the
opposite order. Several greater-than-5% percentages in both reports remained
inside their measured identical-source operation ranges and are recorded as
explained host variance. With an unchanged product tree, no signal supports a
product regression or improvement claim.

## Workflow and gate decision

CI now checks out immutable `v0.5.0`, runs the identical-source control, passes
that report into both paired comparisons, and intersects actionable signals
across orders. Labels and artifacts are release-neutral:
`release-baseline`, `candidate`,
`identical-source-noise-control.json`,
`release-comparison-baseline-first.json`, and
`release-comparison-candidate-first.json`.

Phase 1 passes:

- build and compile cost are independently measurable;
- `IN` and batch cardinalities expose SQL, binding, per-item time, transient
  allocation, RSS, retained memory, digest, and descriptor evidence;
- narrow/wide full, first, naturally exhausted, and early-closed hydration
  paths have like-for-like direct-PDO controls;
- paired comparisons use the immutable release baseline in both required
  orders; and
- identical-source controls define exactly when percentage signals are
  ignored or explained.

The gate establishes optimization baselines only. Product implementation and
any performance claim remain deferred to later evidence-gated phases.
