# `v0.1.0` performance and stability baseline

Status: historical local reference and sanity check; the finalized `0.2`
harness will rerun both revisions for the release-grade paired comparison.

Collected: 2026-07-18 from tag `v0.1.0`
(`16c59bf5fbf2490e19bbd05aa7ccbb7c274ab0dc`).

Machine-readable record: [`v0.1.0-performance-baseline.json`](v0.1.0-performance-baseline.json).

## How to use this baseline

This record answers two different questions:

1. **What was observed before `0.2.0` work began?** Use these measurements as a
   historical sanity check and to choose scenarios and targets.
2. **Does `0.2.0` improve portably?** Compare correctness, result digests,
   SimpleQuery/PDO ratios collected in the same run, complexity scaling, and
   leak invariants. Do not compare absolute workstation microseconds across
   unrelated machines.

The current maintained controls expose per-process medians rather than every
inner sample, and the ad hoc hydration/soak collectors are not yet committed.
Therefore the final comparison must first implement one harness, then run that
identical harness against both the `v0.1.0` source and the `0.2.0` candidate in
fresh, preferably interleaved processes. The JSON retains complete raw runs for
hydration, observer, and soak, and explicitly labels summarized controls.

The environment description intentionally contains no hostname, serial,
filesystem path outside the repository, user identity, or other machine-unique
identifier.

## Correctness and coverage baseline

- `composer check`: passed;
- PHPUnit: 287 tests and 1,141 assertions;
- all nine examples: passed;
- SQLite and disposable direct/proxy service probes: passed;
- Composer advisory audit: no known advisories.

Xdebug path coverage proves that the documented branch floors pass:

| Metric | Result | Floor |
|---|---:|---:|
| Overall lines | 92.57% (1,334/1,441) | 90% |
| Overall branches | 89.47% (1,088/1,216) | 80% |
| Compiler lines | 97.70% (255/261) | 95% |
| Compiler branches | 92.03% (277/301) | 90% |
| Paths | 6.43% (463/7,197) | none |

The low path percentage reflects combinatorial control-flow paths and is not a
release failure. `0.2.0` should add direct tests for known high-risk paths
rather than adopt an arbitrary path-percentage target. The weakest meaningful
branch areas are connection configuration/failure handling, executor cleanup,
join validation, and public compiled-value validation.

CI currently uses PCOV and therefore still skips branch thresholds. The 0.2
plan wires Xdebug coverage into the branch gate; Xdebug need not replace PCOV's
faster line-coverage job.

## Timing and scaling baseline

### Maintained control

Seven fresh-process runs produced these medians of each process's five samples:

| Workload size | PDO insert/fetch control | Ordered-predicate compile |
|---:|---:|---:|
| 10 | 0.013 ms | 0.021 ms |
| 100 | 0.065 ms | 0.160 ms |
| 1,000 | 0.618 ms | 1.554 ms |
| 5,000 | 3.152 ms | — |

Both controls scale approximately linearly. The harness still needs an
explicit untimed warm-up and raw-sample output in `0.2.0`.

### Migration query

Eleven process runs retained exact 100-row parity and one stable result digest.

| Metric | Median |
|---|---:|
| SimpleQuery | 0.0809 ms |
| Direct PDO | 0.0503 ms |
| SimpleQuery/PDO | 1.609× |

The approximately 0.03 ms absolute overhead is small compared with a network
round trip. `0.2.0` comparisons should prioritize the ratio and result digest.

## Hydration and memory baseline

Each mode ran five times in a fresh process over 100,000 rows containing an
integer ID, integer category, and 96-byte payload.

| Mode | Median query time | PHP peak | Median max RSS |
|---|---:|---:|---:|
| Direct PDO associative | 33.973 ms | 54.0 MiB | 98.8 MiB |
| SimpleQuery associative `get` | 64.423 ms | 92.0 MiB | 137.1 MiB |
| SimpleQuery object `get` | 51.312 ms | 62.0 MiB | 106.8 MiB |
| SimpleQuery associative cursor | 38.708 ms | 4.0 MiB | 49.7 MiB |
| SimpleQuery object cursor | 32.984 ms | 4.0 MiB | 49.7 MiB |

Primary ratios:

- associative `get` time / PDO: **1.896×**;
- associative `get` PHP peak / PDO: **1.704×**;
- associative `get` RSS / PDO: **1.389×**;
- associative cursor time / PDO: **1.139×**.

Streaming is already bounded and close to direct PDO. Associative full-result
hydration is the primary `0.2.0` optimization candidate.

## Observer baseline

Seven process runs executed 50,000 trivial in-memory SQLite queries per mode:

| Mode | Median | Approximate rate |
|---|---:|---:|
| Disabled | 139.462 ms | 358,520 calls/s |
| No-op observer | 170.982 ms | 292,429 calls/s |

The no-op observer adds **22.60%** in this deliberately database-free hot-path
control, equivalent to about **0.6304 µs per call**. The percentage will be much
smaller when network/database latency dominates. The disabled path already
avoids observer event construction.

## Soak baseline

Each soak ran three times with Xdebug and PCOV disabled.

| Scenario | Median | Memory/resource result |
|---|---:|---|
| 1,000,000 fixed-query compilations | 3.541 s | PHP allocated memory stayed 4 MiB |
| 250,000 build/compile/execute/fetch cycles | 2.167 s | PHP memory 4 MiB; FDs 5 → 5 |
| 50,000 connect/query/close cycles | 0.932 s | PHP memory 4 MiB; FDs 5 → 5 |

No retained-memory slope, descriptor leak, crash, deadlock, or result mismatch
was observed. These are single-process SQLite soaks; scheduled multiprocess and
network-engine soaks remain a `0.2.0` deliverable.

## Xdebug profile conclusions

Profiler times include substantial instrumentation overhead and are not
performance targets. Their value is hotspot ordering:

1. The associative executor validation/copy closure dominated library-owned
   work in the 20,000-row hydration profile. This confirms the full-result
   double-materialization hypothesis.
2. Repeated compilation distributed work across identifier quoting,
   `select()`, and predicate rendering. The profile shows expected linear AST
   traversal rather than one accidental algorithmic hotspot. It does not
   justify compiler or compiled-query caching.
3. `Executor::notify()` is the observer-specific hotspot. Optimize metadata
   creation only if a maintained realistic benchmark proves value.
4. The migration profile was dominated by fixture setup and batch compilation.
   The `0.2.0` harness must isolate setup, warm-up, and measured operations.

Raw Cachegrind files are not committed: they are several megabytes,
machine-specific, contain absolute local paths, and are unsuitable as stable
repository records. The machine-readable baseline retains the tool version,
scenario, and hotspot summary. Release comparisons may attach raw profiles as
ephemeral CI artifacts after secret/path review.

## `0.2.0` paired comparison protocol

1. Use the same row shapes, fixture sizes, result digests, sample counts, and
   process isolation.
2. Disable Xdebug/PCOV for timings and memory measurements.
3. Run direct PDO and SimpleQuery in alternating AB/BA order where practical.
4. Report all raw samples and the median; do not discard outliers silently.
5. Record PHP, engine, prepare/buffering mode, OPcache/JIT, OS, CPU governor,
   and dirty state.
6. Compare PHP peak memory and subprocess RSS in fresh processes.
7. Profile only after timing identifies a regression or opportunity.
8. Reject any faster result that changes SQL, bindings, row digest, exception
   behavior, cursor cleanup, or transaction ownership.
9. Run the finalized harness against both `v0.1.0` and the `0.2.0` candidate;
   do not compare a new warm-up/AB-BA protocol directly with this historical
   harness output.
