# `0.3.0` production-adoption baseline

Collected: 2026-07-28

Decision: use the first completed production migration as anonymized scope
evidence for `0.3.0`, while keeping application identity, paths, schema, data,
credentials, hostnames, and SQL outside the public repository.

## Method

The review was read-only and covered the migration change set, current PHP
source, tests and command-line integration, dependency metadata, and later
performance-related changes. Lexical counts were cross-checked against the
relevant call sites. Counts describe source candidates, not distinct executed
queries or production traffic.

The private source reference and exact revisions are retained only in the
ignored internal working record. No consumer file was copied. The committed
fixtures under `tests/Fixtures/Adoption/` use synthetic tables, columns, values,
and exception codes to reproduce only the review shapes.

The application is live on SimpleQuery `0.2.0`. The review found no reported
SimpleQuery data-integrity, binding-order, or connection-state defect. This is
useful evidence for one substantial MySQL-family workload, not a general
compatibility or performance claim.

## Findings mapped to release scope

- Structured clauses and the mutable builder model migrated without a
  compatibility facade; preserve those contracts.
- Raw projection lists contain many identifiers, wildcards, and aliases that
  can already be represented structurally. Guidance and tooling come before a
  new projection API.
- Some complete raw predicates exist because a trusted expression cannot yet
  be compared to a separately bound value. Phase 2 may investigate that narrow
  pressure without introducing a general expression parser.
- One `insert()` followed by direct `lastInsertId()` demonstrates a migration-
  audit gap. Phase 1 must report split and delayed generated-ID reads.
- Ordinary and specialized locking transactions remain application-owned PDO
  workflows. Phase 1 reports ownership residue; any new managed mode requires
  separate engine evidence and an ADR.
- Post-migration tuning replaced function-wrapped date or join expressions and
  repeated lookups with ranges, indexed identifiers, and batching. New APIs and
  examples must encourage index-friendly shapes.
- Result hydration is object-only in this consumer. Documentation must make
  associative and cursor choices visible, but no memory or routing feature is
  justified by this review alone.

## Accepted boundaries

The `0.3.0` scope does not include an ORM, application model helpers, automatic
read routing, retries, connection pooling, generic upsert, unions, right joins,
or an extensible SQL parser. Trusted raw SQL remains the explicit escape hatch
for isolated vendor-specific behavior. Direct PDO remains supported when the
application deliberately owns transaction or locking semantics.

## Limitations

Lexical matches can overcount unrelated methods, undercount indirect wrapper
calls, and cannot establish allowlisting, transaction nesting, execution
frequency, or SQL safety. Every audit finding therefore requires manual review.
Live engine probes and synthetic execution tests remain the compatibility
authority.
