# `0.6.0` Phase 0 baseline and scope freeze

Date: 2026-08-23

Baseline: immutable `v0.5.0`
(`902a18037303d7e28cefcad6859c157b98e2d05b`)

Phase 0 was run from a detached worktree at the tag before product
implementation began. At baseline capture, the candidate branch differed from
the tag only in the `0.6.0` planning transition. Raw benchmark, coverage, and
probe reports stayed in ignored or temporary directories and are not release
artifacts.

## Reproduction environment

The local control used PHP 8.4.24, PHPUnit 11.5.56, Composer 2.9.1, PDO MySQL,
PDO SQLite 3.45.1, and Docker 29.7.2 on x86-64 Ubuntu with an Intel Core
i5-13400 and 30 GiB RAM. Xdebug/PCOV timing instrumentation was disabled for
benchmarks. Coverage used PCOV for line coverage and Xdebug 3.5.3 for
branch/path coverage.

The released tree was also represented by three successful GitHub Actions CI
runs with the same Git tree: the final
[pull-request run](https://github.com/oeltimacreation/php-simplequery/actions/runs/32080239072),
[default-branch run](https://github.com/oeltimacreation/php-simplequery/actions/runs/32080332064),
and [tag run](https://github.com/oeltimacreation/php-simplequery/actions/runs/32080940831).
Their one-second step timestamps provide the hosted-runner timing control.

## Wall-time baseline

Local measurements are three sequential invocations in the installed detached
worktree. They exclude dependency installation and runner provisioning.

| Repository command | Median | Range |
| --- | ---: | ---: |
| `composer check` | 8.35 s | 7.95–14.78 s |
| Line coverage generation and gate | 2.94 s | 2.83–3.11 s |
| Branch/path coverage generation and gate | 22.66 s | 22.65–22.82 s |
| CI benchmark suite | 1.09 s | 1.08–1.09 s |
| Reference soak suite | 2.44 s | 2.42–2.44 s |

The first development dependency install took 4.10 seconds and is recorded as
provisioning, not repository work. The clean no-dev install took 0.15 seconds
with a warm Composer cache. A cold local current-engine/proxy invocation took
112.69 seconds including four image pulls; minimum-engine image pull and
startup took 36.91 seconds. Those cold infrastructure numbers are not compared
with the warm repository-command medians.

Hosted timings below use the three same-tree CI runs. Provisioning is job
setup, checkout, PHP setup, and dependency installation. Repository work is
the maintained commands or probe orchestration. Artifact upload, runner gaps,
and finalization explain why the columns do not sum exactly to job duration.

| CI surface | Repository median (range) | Provisioning median (range) | Job median (range) |
| --- | ---: | ---: | ---: |
| Quality job | 33 s (26–37) | 10 s (9–14) | 49 s (38–50) |
| Branch/path coverage job | 24 s (18–25) | 9 s (8–9) | 37 s (30–37) |
| Benchmark job | 12 s (9–12) | 10 s (10–13) | 27 s (25–27) |
| Direct probes / minimum | 22 s (22–26) | 9 s (9–11) | 37 s (34–41) |
| Direct probes / current | 28 s (28–29) | 8 s (8–15) | 39 s (39–48) |

Within the quality job, `composer check` had a 30-second median (22–32) and
line coverage a four-second median (3–4). Branch/path coverage had a 24-second
median (18–25). The equivalent-tree workflow critical path was 51 seconds
(43–53); the actual pull-request run was 51 seconds. Jobs execute in parallel,
so that workflow critical path has no single additive provisioning/repository
split.

Whole-suite local times were stable, but several unrelated sub-millisecond
operation medians moved together between the short five-sample benchmark
invocations. The two source orders also raised disjoint percentage-only review
signals. These results are treated as host/process-order noise, not as a
product regression or improvement. They establish why Phase 1 must add an
absolute same-source noise floor and attributable build/compile controls before
an optimization decision.

## Public demand, consumer tasks, and documentation gaps

The [public GitHub issue list](https://github.com/oeltimacreation/php-simplequery/issues?q=is%3Aissue)
was reviewed on 2026-08-23 and contains no issue tickets. The issue endpoint's
five closed records are release pull requests, not independent feature
reports. No telemetry was added and no private consumer source was accessed.

The retained [anonymized audit](consumer-requirements-audit.md) covers nine
materially different Pixie consumers. Its
[eight contract fixtures](../../tests/Fixtures/Migration/v1.json),
[five representative migration slices](../../tests/Fixtures/Migration/representative-slices.json),
31 query-parity cases, and 23 result-parity cases repeatedly exercise explicit
connection construction, fresh mutable builders, list filtering/pagination,
object and associative results, raw SQL/bindings, diagnostics, generated IDs,
affected rows, direct PDO, transactions, cursors, and batching. The independent
consumer static-analysis fixture also passed. This evidence supports improving
navigation around existing contracts; it does not support a new public API,
engine, or compatibility layer.

The documentation review found:

- installation, connection setup, query construction, writes, transactions,
  testing, and streaming are covered by guides and executable examples;
- terminal contracts exist in reference and result pages, but there is no
  concise task-oriented choice path spanning full/first/object/associative,
  aggregate, cursor, affected-row, and generated-ID outcomes;
- exception types and failure evidence are documented, but configuration,
  invalid-query, execution, cursor, transaction, and connection failures are
  not mapped to safe first-response actions in one troubleshooting path;
- batching limits, application-owned chunk/transaction policy, buffering,
  cursor cleanup, and deterministic pagination are accurate but distributed
  across several guides, making the supported choice slower to find.

These are Phase 5 navigation and troubleshooting tasks. They do not justify a
Phase 0 behavior change.

## Accepted scope freeze

The default `0.6.0` scope is accepted as written in the development plan:

- no new public method, type, overload, extension point, or breaking change;
- no new database/proxy target or raised runtime/database floor;
- no ORM, schema/migration, pool/router/retry, cache, automatic chunking, or
  public internal-plugin platform;
- no telemetry, private consumer inspection, credentials, production data, or
  proprietary SQL.

The public manifest stays byte-identical to `v0.5.0`, supported targets stay
unchanged, and the Phase 0 exception register is empty. Any later exception
requires an explicit plan revision before implementation, including exact
semantics and the required contract, documentation, changelog, and ADR review.

Phase 0 therefore passes: the immutable quality and compatibility baseline is
reproducible, coverage-environment variance and benchmark noise are bounded in
their interpretation, active drift is listed, recurring user tasks are
recorded without private data, and release scope is frozen.
